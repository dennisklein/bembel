Mapping to NetBox

NetBox is the best known open source IPAM. This chapter maps each bembel object to the NetBox 4.7 model that is closest to it. It names the fields, the direction and the loss. It also says where bembel is different on purpose, and it specifies the NetBox export and import. The mapping serves two groups of readers: sites that already run NetBox, and reviewers who ask why bembel is not just NetBox.

  • The IPAM core maps well: VRF, prefix, range, address, VLAN, ASN, team, tag and custom attribute have a NetBox model with the same job.
  • Four areas have no NetBox core model: DNS, DHCP, fabrics (InfiniBand partitions, RoCEv2 profiles) and claims. The export keeps fabric values in custom fields and tags. DNS and DHCP exist only in two separate plugins on their own release trains (netbox-plugin-dns and the beta netbox-plugin-dhcp). The export loses them, except for the DHCP pool range.
  • Four NetBox shapes have no bembel counterpart: generic foreign keys, free-text dns_name, Services and a global table that is not a VRF. The import turns each one into a plain value or a finding.
  • bembel export netbox writes NetBox CSV and JSON files in dependency order. bembel import netbox reads a NetBox over REST with natural keys and a read-only v2 token.
  • All numbers and names of NetBox come from the source of NetBox 4.7.4 (published 2026-10-27). A fact that was not verified in the source is marked.

Summary and model map

Both tools store the same kind of data, but they weigh it in different ways. NetBox is a DCIM and IPAM in one tool for a data centre team. bembel is an IPAM that also owns DNS and DHCP data, and it mirrors assets from another tool. The figure shows the objects side by side. Each arrow says what carries the mapping.

Rules of the mapping

  • The mapping is by natural key, not by id. A NetBox id is an external ref in bembel. A bembel id is a custom field in NetBox (bembel_id).
  • bembel stays the source of truth for the objects it owns. NetBox gets a copy. A re-run of the export updates the copy and never merges changes back.
  • The import runs once per source, like the ONA import. It writes objects with source=netbox-import and findings for what it cannot map.
  • A mapping that needs a decision, not a rule, is a proposal. This chapter marks it so.

Why the chapter maps by natural key

NetBox ids are database numbers. They differ between two NetBox instances. A natural key is the same in both: the rd of a VRF, the asn of an ASN, the pair (VRF, prefix) of a prefix. NetBox itself advises these keys for a bulk import. A re-run of the import then updates objects and makes no duplicates.

The global table is not a VRF

In NetBox, a prefix with no VRF lives in the global table. With the default ENFORCE_GLOBAL_UNIQUE=true a duplicate there is an error. A container in the global table can also find children in other VRFs (the source has this rule in get_child_prefixes()). In bembel, VRFs never see each other. If a NetBox site relies on the cross-VRF rule for its utilization numbers, the numbers differ after the import.

Fabrics, IB partitions and RoCEv2 profiles

NetBox does not know the words fabric, IB partition or QoS profile. A P_Key is a 15-bit number from 0x0001 to 0x7ffe. A NetBox VLAN ID stops at 4094, so a partition cannot be a VLAN. A port GUID has 8 bytes, and the 20-byte IPoIB hardware address does not fit the MAC field, which holds an EUI-48 value. The export therefore uses custom fields and tags. This is a proposal, because NetBox has no better place.

The command bembel export netbox --schema writes only the three schema files, each for its own endpoint: 00a the choice sets for POST /api/extras/custom-field-choice-sets/, 00b the custom fields for POST /api/extras/custom-fields/ (a select field names its choice_set), and 00c the tags for POST /api/extras/tags/. A full export writes them too. Without these definitions, NetBox refuses the data columns. A select or multiselect field needs its choice set first.

DNS and DHCP

NetBox core has no DNS zone, no record, no DHCP scope, no option, no lease and no reservation. This was checked in the source: no such model exists under netbox/ipam/models/. The only hooks are the text field IPAddress.dns_name, the address status dhcp and the IPRange. Sites that need more use the plugin netbox-plugin-dns (sys4) for zones and records (not verified here: web notes only), and the beta plugin netbox-plugin-dhcp (sys4, MIT, NetBox 4.7.0 or later, no documentation yet, aimed at Kea) or a Kea script for DHCP. The two plugins are separate projects on their own release trains.

Plugins versus built in

The plugins prove the demand. netbox-plugin-dns adds zones, records and a sync from dns_name. netbox-plugin-dhcp (beta) adds DHCP data. They are two separate plugins on their own release trains, and each follows the NetBox major releases (netbox-plugin-dns needs NetBox 4.5 or later, netbox-plugin-dhcp 4.7.0 or later). bembel keeps zones and DHCP data in the core, in the same transaction as the address, so a change of an address and its records is one commit. See differences.

Access: permissions and tokens

NetBox attaches an ObjectPermission to users and groups. A permission names object types, actions and constraints. A constraint is a JSON filter in the syntax of the database layer: a dict means AND, a list of dicts means OR, and several permissions on one model are OR-ed. bembel attaches a binding to a subject: a role and a scope. Both tools allow only. A scope in bembel is a closed list of types.

Why not just NetBox

NetBox is a good tool, and for many sites it is the right answer. It has a large community, plugins, a Terraform provider, an Ansible collection, a device type library of more than 400 vendors, cabling, power, circuits, config contexts, scripts and a read-only GraphQL API. bembel has none of the DCIM depth. It mirrors assets and does not manage cables.

The bembel requirements are different. The tool must replace OpenNetAdmin, which owns DNS and DHCP data. It must serve an OpenStack Neutron driver with claims and Cluster API with allocations, both safe to retry. It must model InfiniBand partitions and RoCEv2 profiles. It must tie access to IdP groups with scopes. With NetBox this means the core plus a DNS plugin, a beta DHCP plugin or a Kea script, a Python plugin for claims and custom fields for fabrics. The DNS and DHCP plugins are two separate plugins on their own release trains, and each part follows the NetBox release train. The decision chapter scores the options.

If a site runs NetBox for DCIM, the two tools can live together. The exchange section is for this case.

  • NetBox CSV refers to related objects by natural key columns such as vrf and tenant (by name) and status (by slug). It also resolves generic foreign keys by natural key.   • The export is a single pass. The option --resolve URL is only for update mode and for ambiguous scope names: it reads the numbers from the NetBox that already holds the earlier files, and it writes scope_id where a scope name matches more than one object.
  • An id column puts a NetBox bulk import in update mode, and only the given columns change. With --resolve, the export finds the NetBox id by the custom field bembel_id and writes it. A second run updates, and makes no duplicates.
  • The format json writes the same rows as REST bodies. The bulk call is POST of a list to the collection URL, and NetBox 4.7 reports an error for each object.
  • The command reads through the bembel API with the permissions of the caller. A user sees in the files what the scope of the user allows.
  • The option --permissions adds ObjectPermission rows from the bindings (see access). It marks each row as a proposal.

Import: NetBox to bembel

The import reads NetBox over REST. It does not need database access to NetBox. It uses a v2 token with read rights.

$ bembel import netbox --url https://netbox.example.org \
      --token-file ~/.config/bembel/netbox.token --dry-run
read 4 vrfs, 3 rirs, 41 aggregates and containers, 271 prefixes, 6 ip-ranges
read 9 912 ip-addresses (cursor pages of 1000), 118 vlans, 14 asns
mapped 10 290 objects; 48 findings
  12 mask-mismatch      address mask differs from its covering subnet
   9 dhcp-status        status dhcp without a covering dhcp-pool range
   7 duplicate-prefix   VRF with enforce_unique=false
   6 nested-subnet      child prefixes under a subnet with addresses, not imported
   5 nat-inside         kept as attribute nat_inside

   2 duplicate-address  same address twice in a VRF, lowest NetBox id kept
run imp-20261104-1017 written as a report only; use --apply to write
  1. The command reads each model with GET and the cursor start=ID&limit=1000 (NetBox 4.6 or later; offset paging on older versions).
  2. Select and multiselect custom field values are unwrapped to their raw value, so both shapes are accepted: an object {value, label} from NetBox 4.7 and a plain string from older versions.
  3. It maps each row with the tables of this chapter, prefixes bottom-up by mask length, and finds the object by natural key: VRF by rd then name, ASN by number, prefix and address by (VRF, value), VLAN by (group, VID), interface by (device, name).
  4. It writes a report of the objects it would create, update or skip, with the findings.
  5. With --apply it writes the objects with source=netbox-import and external_ref=netbox:INSTANCE:MODEL:ID. A re-run updates the same objects.
  6. It adds one audit event for the run with the origin netbox-import.

The import tests use both custom field shapes: a 4.7 payload with custom_fields.bembel_fabric = {"value":"infiniband","label":"InfiniBand"}, and a pre-4.7 payload with "infiniband".

Use cases

Evaluation: import a copy of a NetBox, read the findings, and see how clean the data is. Migration: a site that moves from NetBox runs the import once, adds DNS and DHCP data by hand or with the ONA import, and cuts over. Coexistence: a site keeps NetBox for cabling and power, and runs the export every night so that NetBox shows the current addresses.
