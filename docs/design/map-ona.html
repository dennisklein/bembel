Mapping from OpenNetAdmin

This chapter maps every table of the ONA 19.0.x schema to the bembel model. It gives the rules that bembel import ona applies, column by column, and the data problems that the import reports as findings. The migration chapter says how to run the import (migration.html).

  • ONA has no foreign keys. All links are integer ids, and 0 means "none". The import follows each link itself and reports a link that leads nowhere.
  • IPv4 and IPv6 share one DECIMAL(39,0) column. The import reads it as a big integer. The family comes from the subnet, never from the number alone.
  • A host has no name column. The name is the DNS record hosts.primary_dns_id. The import writes the full FQDN on the host.
  • One ONA interface row is one IP address. The import merges rows of one host with the same interface name into one bembel interface with many addresses.
  • The import writes A and PTR rows as the name of an address. bembel derives both records again. Only CNAME, MX, NS, SRV and TXT rows become manual records.
  • Only domains with a server row become zones. Blocks become containers, ranges or tags by a fixed rule.
  • ONA has coarse global permissions. Each subject gets a custom role with exactly the mapped permissions, in a global scope. Password hashes are never imported.
  • Each data problem has a finding code ona.* and a fix rule. Every imported object keeps the external ref ona:TABLE:ID.

Sources

The column names come from install/ona-table_schema.xml, docs/ona-schema.dbml and the PHP modules of ONA v19.0.3, and from the plugins build_bind and build_isc_dhcp. The research notes label what the authors did not verify. Guesses stay marked "not verified" in this chapter. The author did not read the ONA wiki.

Summary

The ONA schema is flat. It has no VRF, no prefix tree, no tenant, no history and no address status. bembel has all of them. The import therefore adds information that ONA cannot hold. It takes this information from a map file (migration.html#import), for example the VRF of a subnet or the fabric of a prefix.

Four rules apply to every table.

  1. Key. Every imported object gets the external ref ona:TABLE:ID and the source ona-import. A merged object keeps one ref per ONA row.
  2. Owner. Every imported object has managed_by = ona-import until the cutover. Users cannot edit it in bembel. ONA stays the writer.
  3. Order. The import reads the tables in the order of the next section. It never trusts the table sequences. It uses MAX(id).
  4. Error handling. A row with a data problem makes a finding. A finding with severity error keeps the row out of the model. A finding with severity warn imports the row with the stated repair. A finding with severity info imports the row as it is.

The import checks the schema before it reads data. It reads sys_config.upgrade_index and version. It compares the columns with the list from install/ona-table_schema.xml of v19.0.3, where each column is required or optional (legacy). Old databases miss dns.dns_view_id or still have INT columns for the IP address. Only a missing required column stops the import with a clear message. A missing legacy column is ok. An INT column is fine, because the import reads all numbers as big integers. The length and truncation checks use the column widths that information_schema.COLUMNS gives for the source database.

Decimal IP addresses

ONA stores every address as an integer. The columns subnets.ip_addr, subnets.ip_mask, interfaces.ip_addr, blocks.ip_addr_start and blocks.ip_addr_end are DECIMAL(39,0) unsigned. MariaDB returns them as strings. The import never uses a float. It reads the string into a 128-bit integer.

ONA has no family column. Its code treats a value up to 4294967295 (0xFFFFFFFF) as IPv4. An IPv6 address below 232 has the same number as an IPv4 address. The import uses this rule.

  1. A subnet mask bigger than 0xFFFFFFFF is IPv6. A prefix mask of /1 or more in IPv6 always has its top bits set, so a subnet is never unclear.
  2. An interface takes the family of its subnet. The import first uses interfaces.subnet_id. If that id is stale, it searches the containing subnet (ona.stale-subnet-id).
  3. A value bigger than 0xFFFFFFFF is IPv6.
  4. A small value that no subnet contains is IPv4 by default. If an IPv6 subnet in ::/96 also contains it, the import raises ona.ipv6-ambiguous and waits for a decision in the map file.

The other columns need the same care. dhcp_pools.ip_addr_start and ip_addr_end are still INT UNSIGNED, so they are always IPv4. ONA cannot store an IPv6 pool.

Subnet types

subnet_types has the columns id, short_name, display_name and notes. The seed has loopback, WAN, VLAN, p2p, VPN, Wireless LAN and LAN. The import does not create an object for it. It writes the tag subnet-type on each subnet. The notes go to the tag description once.

Parent and children

ONA has no parent. bembel computes the parent from containment. The import creates the subnets first and the container prefixes of blocks after them. The tree forms by itself. The map file can add container prefixes that ONA never had, for example 10.110.0.0/16 "osprey RoCE" in VRF hpc-fabric, the parent of the eight rail subnets:

prefixes:
  - cidr: 10.110.0.0/16
    vrf: hpc-fabric
    prefix_kind: container
    name: osprey RoCE
    team: hpc-ops
    site: Hall 2

A prefixes: entry follows these rules, in this order.

  1. An entry whose CIDR and VRF equal a prefix that the import creates from an ONA subnet or block does not create a second prefix. It fills only the fields that ONA lacks (site, team, fabric, the name when it is empty). The object keeps its ref ona:subnets:ID or ona:blocks:ID, and the filled fields go into its row hash. The ONA block "Hall 2 HPC" (10.20.0.0/16) gets its site in this way.
  2. An entry with no ONA match creates a container with the external ref map:prefixes:CIDR (for example map:prefixes:10.110.0.0/16), the source ona-import and managed_by = ona-import. A re-import finds it by that ref. When the entry is removed, the import marks the container deprecated.
  3. An entry that overlaps a subnet but does not contain it creates nothing. The import raises ona.map-prefix-overlap (error).

Hosts without names

The host row has no name. The name is the A record that primary_dns_id points to. The import builds the FQDN in this way.

  1. Read the dns row with the id primary_dns_id.
  2. Build the domain FQDN. Walk domains.parent_id up to the root and join the labels (domains).
  3. Join dns.name and the domain FQDN. Row 90211 has the name cn-004 in the domain kestrel. The host is cn-004.kestrel.example.org.
  4. If primary_dns_id is 0 or the row is missing, use the A record with the lowest id on an interface of the host. Raise ona.orphan-dns (warn).
  5. If the host has no A record at all, the host gets no name. The import raises ona.host-no-name (error) and keeps the host out of the model. Its addresses stay as addresses without an interface.

The host name must be unique. ONA checks this only in PHP, per domain. If two hosts have the same FQDN, the import keeps the one with the lower id and raises ona.dup-host for the other; its name gets the suffix -ID. In the story data this finding does not occur.

Virtual machines

ONA has no VM model. VMs are hosts with a device type such as "KVM guest" or an empty type. bembel has the host kinds physical, vm, hypervisor, appliance and container-node, and the link runs_on. The import cannot know the hypervisor. The map file rules set the kind:

hosts:
  host_kind:
    - match: {model: "KVM guest"}
      host_kind: vm
      platform: libvirt
    - match: {fqdn: "^hv-0[1-6]\\.example\\.org$"}
      host_kind: hypervisor
    - match: {role: "wireless-access-point|printer"}
      host_kind: appliance

Later the bembel-agent on hv-01.example.org reports its libvirt domains. A reported VM with a MAC that an imported host already has links to that host. The sync sets runs_on and platform. It does not create a second host.

Interfaces and addresses

An ONA interface row is one IP address on one host. The row also holds the interface name and the MAC. There is no address list, no free address and no status. A bembel interface is a NIC with a MAC and many addresses. The import therefore merges rows.

Merge rules

  1. Group the rows by host and by the lowercase interface name. This group is one bembel interface.
  2. If the name is empty, group the rows by host and MAC. A row without name and without MAC forms its own interface.
  3. The interface MAC is the MAC of the group. If the rows of one group have different MACs, the MAC with the lowest row id wins. The import raises ona.dup-mac (warn) with both values.
  4. A row without a MAC in a group with a MAC gets the group MAC. This case is normal for IPv6 rows.
  5. The VRF of an address is the VRF of its prefix. Two rows of one group in different VRFs stay in one interface only if the map file allows it. Otherwise the import splits the group and appends the VRF to the second interface name.

InfiniBand needs special care. The column mac_addr holds only 12 hex digits. An InfiniBand port GUID has 16 digits and the IPoIB address has 20 bytes. ONA cannot store them. Site admins often put the GUID in the description. The map file rule interfaces.guid_from: description reads a 16-digit GUID from the description and writes it to interface.port_guid (16 lowercase hex digits, for example 0c42a1030071a2b4). The map file puts the prefix 10.100.0.0/16 in the InfiniBand fabric kestrel-ib.

Derived records and manual records

bembel keeps the name on the address and derives A, AAAA and PTR (see dns.html#derived). The import follows these rules.

  1. The A row of an interface sets address.fqdn. The primary name of a host is the row that hosts.primary_dns_id names.
  2. If an address has more than one A row, the primary name wins. Each other A row becomes a manual record of type A with the same IP and an info finding. The extra name does not follow a later change of the address.
  3. The PTR row is checked, not imported. If its target is the same as the address name, the address keeps ptr = true. If the address has no PTR row, the import sets ptr = false. This is the effect of addptr=N in ONA.
  4. If the PTR target differs from the address name, the import raises ona.ptr-mismatch (warn). The address name stays the name of the A row. The PTR target becomes a manual PTR record, so the export keeps the old answer until a user decides.
  5. CNAME, NS, MX and SRV rows become manual records. The data is the target name from the dns_id link. TXT rows copy the text.

A CNAME that shares a name with other data is not valid in DNS. ONA blocks this only in PHP. The import raises ona.cname-conflict (error) and keeps the CNAME out. The same rule holds for a CNAME at the apex of a zone.

Views

ONA has the table dns_views (id, name, description). The seed has only DEFAULT. The switch is sys_config.dns_views = 1. A view is a label on a dns row. The ONA export ignores it (open ONA issue 169). Split-horizon DNS is therefore new in bembel. The map file names the views:

views:
  DEFAULT: internal          # records without a view
  external: external         # ONA view name to bembel view name
zones_in_views:
  example.org: [internal, external]

Which domain becomes a zone

A domain becomes a zone only when the table dns_server_domains has at least one row for it. This is the exact set of zones that build_bind exports. The SOA columns do not decide: ONA fills them from sys_config when it creates a domain, so they say nothing about whether the domain is a zone. The map file can override the rule: zones: [fqdn, …] forces a zone, and labels: [fqdn, …] forces a label.

All other domains are labels. Their records move into the nearest zone above. The record name gets the labels as a suffix. A record node1 in the domain hpc becomes node1.hpc in the zone example.org. ONA never published these records, because build_bind writes only the records of a served domain. The import therefore sets record.disabled = true on them and raises ona.unpublished-record (warn), so the export stays the same as ONA. If no zone exists above, the import raises ona.no-zone (warn) and creates a zone without a DNS server. bembel does not export a zone without a server.

Reverse zones

Reverse domains are ordinary rows, for example 20.10.in-addr.arpa. bembel computes reverse zones from the subnets (dns.html#reverse). The import creates no PTR records. It does these checks.

  1. For each reverse domain that is a zone, find the computed reverse zone with the same name. If it exists, attach the DNS servers of the ONA domain to it.
  2. If the name is not computable (a name of RFC 2317 style, such as 0-27.4.20.10.in-addr.arpa), the import creates a classless reverse zone for the subnet and maps the servers. The label style of the export follows the old name.
  3. If no subnet matches, the import keeps the zone as a plain zone and raises ona.no-zone.

Reservations

A bembel reservation is an address with the MAC of its interface in a scope that has a DHCP server. The import marks an address as reserved if its interface has a MAC and one of these is true.

  • The subnet is in dhcp_server_subnets.
  • The subnet has a pool in a failover group.

This is the same selection as in the build_isc_dhcp plugin. The compat export therefore writes the same host blocks. Entries for a subnet without a scope, or for a missing option, give ona.dhcp-orphan. A subnet with a scope but without a routers value gets ona.no-gateway (warn). The ONA generator skips such a subnet. The compat export skips it too, and the native export writes it.

The shared-network name that ONA derives from a VLAN (campus, VLAN number and name) is not stored. bembel computes it again from the VLAN, so the compat export keeps the name.

Blocks

A block has an ip_addr_start, an ip_addr_end, a name and notes. It is only for display. ONA does not link it to subnets. It does not need CIDR alignment. bembel needs a precise object, so the import decides per block.

Locations

A location is flat. It has no building, floor, room or rack. It is US-centric. bembel has a site tree (site, building, floor, room, row, rack) that the FNT sync fills. The import creates a site for each location. The site is a stub until the sync links it to the FNT site by name.

Data problems and finding codes

ONA keeps data integrity in PHP code. A hand edit, a failed multi-step action or a bulk SQL load leaves broken rows. The import tests all of them. Each class of problem has a finding code, a severity and a fix rule. A finding names the ONA row as ona:TABLE:ID. The fix is either a change in ONA or a rule in the map file. Why one code per class

A count per code shows the progress of the clean-up. The import knows 30 codes. The run imp-20261104-0912 has 214 findings in 22 of them. The migration chapter shows the list (migration.html#findings). The assistant explains a code to a user and finds the rows (assistant.html#advisories).

A finding is data. It has an id, a run, a code, a severity, the ONA ref, a text, a suggested fix, and a state: open, accepted (with a reason and an audit event; the permission is source:sync) or closed (a later run found the data clean, after a fix in ONA or a map file rule). Until bembel import ona --release the import page has no edit actions.
