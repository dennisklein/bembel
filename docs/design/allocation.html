Allocation and lifecycle

This chapter specifies how bembel gives out addresses and prefixes. It covers the address states, the two allocate operations, claims, idempotent retries, the locks and constraints that make concurrent calls safe, and the reaper that cleans up.

  • An address is claimed, allocated, reserved or deprecated. A free address has no row.
  • POST /v1/prefixes/{id}/addresses:allocate picks the address on the server. The client never reads a list and then writes.
  • POST /v1/prefixes/{id}/prefixes:allocate cuts an aligned child prefix from a prefix pool with the best-fit rule.
  • A claim holds an address for a short time (default 10 minutes). The caller confirms it, or the reaper releases it.
  • The Idempotency-Key header makes a retry return the first answer. The key row and the address commit in one transaction.
  • One row lock on the parent prefix serialises the calls for one subnet. PostgreSQL constraints are the safety net.
  • Bulk allocation gives n addresses in one transaction: all or none.

Address states

The address table holds only addresses that someone uses or holds. A free address has no row. Free is the absence of a row, so the database cannot disagree with itself about it.

StateMeaningWho sets itLeaves by
claimedHeld for a short time. It has expires_at and the claim owner.allocate with claim_ttlconfirm or expiry
allocatedIn use. It may have an interface and a DNS name. It drives A/AAAA and PTR records and DHCP reservations.user, service, import, agentdeprecate or delete
reservedHeld on purpose, with no host yet (for example a future gateway).userassign or release
deprecatedThe host is gone. The DNS records stay out of the export. The address cannot be given out again until deprecated_until.user, libvirt hook, syncreaper after the grace time (default 7 days), or reactivate

Why a grace time

A deleted VM or host often comes back, or a cache still points at the old address. If bembel gives the address to the next caller at once, two systems can use it. The grace time keeps the address out of reach for 7 days.

Observed addresses (from the bembel-agent, from a sync, or from IPv6 neighbour data) get the flag observed=true and the state allocated. An observed address blocks allocation of the same value. A user cannot delete it while the source still reports it.

Allocate the next free address

A client asks for an address. The server chooses it. The client never reads a free list and then writes, because that pattern has a race by design.

Content-Type: application/json

Skipped addresses

The allocator never returns these addresses:

  • The network address (IPv4 with prefix length < 31, and the subnet-router anycast address :: of an IPv6 subnet).
  • The broadcast address (IPv4 with prefix length < 31). A /31 (RFC 3021) and a /32 have no network or broadcast address.
  • The gateway of the subnet (10.20.4.1 in kestrel-compute).
  • Every address in a range with the role dhcp-pool or reserved. A request that names a range ("range": "kestrel-static") allocates only inside that range, and then a range with the role static is allowed.
  • Every address that has a row, in any state, including deprecated.

In the story data, 10.20.4.0/22 has 1 024 addresses. The DHCP pool 10.20.7.0–10.20.7.254 takes 255. The allocator can use the other 767 minus the gateway and the rows that exist.

The gap query

The first free address is always directly after a blocked item, or it is the first address of the subnet. A blocked item is an existing address, the gateway, or the end of a skipped range. So the query builds a short list of candidates and keeps the lowest one that is free. It never lists the whole subnet. It works for IPv4 and IPv6 without change, because it uses inet arithmetic.

-- $1 = subnet prefix id. The caller holds the row lock on this prefix.
WITH p AS (
  SELECT id, prefix, gateway FROM prefix WHERE id = $1
), blocked_ranges AS (
  SELECT r.first_addr, r.last_addr
  FROM range r, p
  WHERE r.prefix_id = p.id AND r.role IN ('dhcp-pool', 'reserved')
), cand AS (
  SELECT host(network(p.prefix))::inet + 1 AS c FROM p          -- first address after the network address
  UNION SELECT a.address + 1 FROM address a, p WHERE a.prefix_id = p.id
  UNION SELECT p.gateway + 1 FROM p WHERE p.gateway IS NOT NULL
  UNION SELECT br.last_addr + 1 FROM blocked_ranges br
)
SELECT cand.c
FROM cand, p
WHERE cand.c << p.prefix                                          -- inside the subnet
  AND (family(p.prefix) = 6 OR masklen(p.prefix) >= 31
       OR cand.c <> broadcast(p.prefix))                           -- not the IPv4 broadcast address
  AND cand.c IS DISTINCT FROM p.gateway
  AND NOT EXISTS (SELECT 1 FROM address a WHERE a.prefix_id = p.id AND a.address = cand.c)
  AND NOT EXISTS (SELECT 1 FROM blocked_ranges br
                  WHERE cand.c BETWEEN br.first_addr AND br.last_addr)
ORDER BY cand.c
LIMIT 1;

The strategy last uses the mirror query (candidates are address - 1 and first_addr - 1, order descending). The cost is O(n log n) for n rows in the subnet and uses the btree index on (prefix_id, address).

Never generate_series for IPv6

A /64 has 264 addresses. A query that lists them cannot finish. bembel uses only gap queries for IPv6. For random it draws one value and checks it with the unique index. The same rule applies to IPv4 subnets larger than a /20: the code does not enumerate them.

If the query returns no row, the subnet is full. The answer is 409 Conflict with the problem type https://bembel.example.org/problems/no-free-address. The body names the subnet and its utilisation.

Allocate a child prefix from a prefix pool

A container prefix marked pool hands out child prefixes. The VRF is the same as the parent. The request gives a length, not an address:

POST /v1/prefixes/{pool_id}/prefixes:allocate
Idempotency-Key: 0b8e8f1c-4c2a-4f8e-bf53-0d7a9e61c3d5

{
  "length": 24,
  "kind": "subnet",
  "name": "ceph-cluster",
  "site": "hall-2",
  "owner": "hpc-ops",
  "status": "planned"
}

Best fit and alignment

  1. bembel locks the pool row (Concurrency).
  2. It reads the child prefixes of the pool, in any status except deprecated with a past grace time.
  3. It removes the children from the pool range. What is left is the free space, written as the smallest list of aligned CIDR blocks (netipx.IPSet.Prefixes()).
  4. It keeps the blocks that are at least as large as the request (prefix length ≤ length).
  5. It takes the smallest of them. This is the best fit. If two blocks have the same size, it takes the lower address.
  6. It returns the first aligned sub-block of the requested length at the start of that block.

Every block of the list is aligned by construction, so the result is aligned: a /24 starts on a multiple of 256. The best-fit rule keeps big free blocks whole. A /20 request later still finds a /20.

The same algorithm works in IPv6. For the pool 2001:db8:4200::/48 a request for a /64 returns the lowest free /64. The pool never hands out a prefix longer than the limit on the pool: max_child_length (default 30 for IPv4, 126 for IPv6; for example a pool can be limited to /64 only).

FieldTypeRule
lengthint, requiredLarger than the pool length. At most max_child_length.

Claims

A claim is an address in state claimed. The caller wants to be sure that the address stays free while it does something slow: boot a VM, create a Neutron port, wait for a Cluster API machine. The caller confirms the claim or lets it end.

# claim for 10 minutes
POST /v1/prefixes/{id}/addresses:allocate   {"claim_ttl": "10m", ...}

# confirm: the claim becomes an allocation
POST /v1/addresses/{addr_id}:confirm        {"interface_id": "...", "dns_name": "..."}

# extend the time (at most max_claim_ttl in total)
POST /v1/addresses/{addr_id}:renew          {"claim_ttl": "10m"}

# give up
DELETE /v1/addresses/{addr_id}
SettingDefaultRule
claim_ttl in the requestnone (allocate at once)If set, 10 seconds to max_claim_ttl.
default_claim_ttl (config)10 minutesUsed when a client sends "claim_ttl": "default".
max_claim_ttl (config)1 hourLongest total time, with renewals.

Who uses claims:

  • Neutron driver (OpenStack): claims at allocate_ip, confirms at port commit.
  • Cluster API provider (Kubernetes): one claim per IPAddressClaim, confirmed when the machine exists.
  • bembel vm prepare (libvirt hook): claims an address and a MAC, and the hook confirms it by MAC when the domain starts.

A claim is in the address table, so the unique constraint covers it, the gap query skips it, and DNS and DHCP exports ignore it. They read only allocated and deprecated addresses. Metrics count open and expired claims (Observability).

Why a TTL and not a lease

A DHCP lease belongs to a client on the network. A claim belongs to a caller of the API. The caller can crash. If the claim had no time limit, a crash would leak the address for ever. With a TTL, a crash leaks the address for at most 10 minutes.

Idempotency-Key

Every :allocate call needs an Idempotency-Key header (an unguessable string, a UUID is fine). A call without it gets 400. Other POST calls accept the header and treat it the same way. bembel follows the IETF draft The Idempotency-Key HTTP Header Field.

CaseResult
New keybembel runs the call and stores the key, the request fingerprint and the response.
Same key, same fingerprint, first call finishedbembel returns the stored response: the same status code and the same body, with the header Idempotent-Replayed: true. It does not allocate again.
Same key, same fingerprint, first call still runningThe second call waits for the first transaction (the unique index on the key blocks it), and then returns the stored response.
Same key, different fingerprint422 with the problem type idempotency-key-reused. Nothing changes.
First call failed with 4xx or 5xxbembel does not store the response. The retry runs again. An error that depends on the state, such as no-free-address, can then succeed.
Key older than 24 hoursThe reaper deletes the row. The key counts as new.

The fingerprint is the SHA-256 of the method, the path and the canonical JSON body. The key is scoped to the subject: two subjects can use the same string without a clash.

CREATE TABLE idempotency_key (
  subject     text        NOT NULL,
  key         text        NOT NULL,
  fingerprint bytea       NOT NULL,
  status      int         NOT NULL,
  response    jsonb       NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (subject, key)
);
CREATE INDEX idempotency_key_created ON idempotency_key (created_at);

The key row is inserted in the same transaction as the address. If the transaction rolls back, the key row rolls back too. If it commits, both exist. So there is no state where the address exists and the key does not. A client can always retry after a timeout and gets the same address.

Controllers and deterministic names

A controller that reconciles in a loop should also send a stable name (external_ref, for example the UID of the IPAddressClaim). Then a lost key does not matter: the unique index on (source, external_ref) gives the existing address back.

Concurrency

Two callers can ask for an address in the same subnet at the same moment. bembel serialises them with a row lock on the parent prefix.

BEGIN;
SET LOCAL lock_timeout = '5s';

-- 1. Idempotency: a retry returns here, before it takes the lock.
INSERT INTO idempotency_key (subject, key, fingerprint, status, response)
VALUES ($subject, $key, $fp, 0, '{}')
ON CONFLICT (subject, key) DO NOTHING
RETURNING 1;                       -- no row: read the stored answer and stop

-- 2. Serialise all callers of this subnet.
SELECT id, prefix, gateway FROM prefix WHERE id = $1 FOR UPDATE;

-- 3. Gap query (see above), then:
INSERT INTO address (id, vrf_id, prefix_id, address, status, expires_at, owner)
VALUES (uuidv7(), $vrf, $1, $chosen, 'claimed', now() + $ttl, $owner)
RETURNING *;

UPDATE prefix_usage SET used = used + 1 WHERE prefix_id = $1;
INSERT INTO event_outbox (...) VALUES (...);          -- same transaction
UPDATE idempotency_key SET status = 201, response = $resp
 WHERE subject = $subject AND key = $key;
COMMIT;

Why a row lock

  • PostgreSQL releases it at the end of the transaction. A crashed server cannot keep it.
  • It works behind PgBouncer in transaction mode. A session advisory lock does not.
  • It is visible: pg_locks and pg_stat_activity show who waits for which prefix.
  • It locks one row. Calls for other subnets do not wait.
SituationBehaviour
Two calls, same subnetThe second waits for the first commit, then sees the new row and takes the next address.
Two calls, different subnetsNo wait.
Wait longer than lock_timeout (5 s)503 with Retry-After: 1. With the same key the retry is safe.
Prefix allocation in a poolLocks the pool row. An address allocation in a child subnet locks the child row. They do not block each other.
Direct write of a chosen address (PUT /v1/addresses/…)Takes the same row lock. If the address exists, the answer is 409.
Lock orderAlways the parent first, then nothing else. No call locks two prefixes, so deadlocks between allocations cannot occur.

The lock limits the rate for one subnet. The critical section is one index lookup and two inserts, so the expected time is a few milliseconds. That gives hundreds of allocations per second for one subnet. The number is an estimate. The load test of the first release measures it (Roadmap).

The constraint is the second guard

The lock prevents the conflict. The unique constraint and the exclusion constraint (next section) make sure that a bug in the code, a manual SQL change or an import cannot create one. If the constraint fires, bembel maps 23505 and 23P01 to 409 and, for :allocate, repeats the transaction up to 3 times.

PostgreSQL constraints

The database rejects an invalid state. The rules do not rely on the application. The excerpt shows the parts that matter for allocation. Core model has the full schema.

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE prefix (
  id         uuid PRIMARY KEY DEFAULT uuidv7(),
  vrf_id     uuid        NOT NULL REFERENCES vrf (id),
  prefix     cidr        NOT NULL,
  level      smallint    NOT NULL,     -- number of containing prefixes in the VRF (trigger)
  parent_id  uuid        REFERENCES prefix (id),
  kind       text        NOT NULL CHECK (kind IN ('container', 'subnet')),
  status     text        NOT NULL CHECK (status IN ('planned', 'active', 'reserved', 'deprecated')),
  is_pool    boolean     NOT NULL DEFAULT false,
  gateway    inet,
  CONSTRAINT prefix_is_network CHECK (prefix = network(prefix)),
  CONSTRAINT prefix_pool_is_container CHECK (NOT is_pool OR kind = 'container'),
  CONSTRAINT prefix_gateway_inside CHECK (gateway IS NULL OR gateway << prefix),
  CONSTRAINT prefix_unique_per_vrf UNIQUE (vrf_id, prefix),
  -- no two prefixes on the same level of the tree overlap in one VRF
  CONSTRAINT prefix_no_sibling_overlap
    EXCLUDE USING gist (vrf_id WITH =, level WITH =, prefix inet_ops WITH &&)
    DEFERRABLE INITIALLY IMMEDIATE
);
CREATE INDEX prefix_gist ON prefix USING gist (prefix inet_ops);

CREATE TABLE address (
  id         uuid PRIMARY KEY DEFAULT uuidv7(),
  vrf_id     uuid        NOT NULL REFERENCES vrf (id),
  prefix_id  uuid        NOT NULL REFERENCES prefix (id),
  address    inet        NOT NULL,
  status     text        NOT NULL
             CHECK (status IN ('allocated', 'reserved', 'claimed', 'deprecated')),
  expires_at timestamptz,              -- claimed
  deprecated_until timestamptz,        -- deprecated
  CONSTRAINT address_is_host CHECK
    (masklen(address) = CASE family(address) WHEN 4 THEN 32 ELSE 128 END),
  CONSTRAINT address_claim_has_expiry CHECK ((status = 'claimed') = (expires_at IS NOT NULL)),
  CONSTRAINT address_deprecated_has_grace CHECK
    ((status = 'deprecated') = (deprecated_until IS NOT NULL)),
  CONSTRAINT address_unique_per_vrf UNIQUE (vrf_id, address)
);
CREATE INDEX address_by_prefix ON address (prefix_id, address);
CREATE INDEX address_claim_expiry ON address (expires_at) WHERE status = 'claimed';

Why the exclusion uses a level

Prefixes in a tree contain each other, so a simple "no overlap" rule would reject a /16 and the /22 inside it. The column level solves this: it counts the prefixes in the same VRF that contain this one. The prefix 10.0.0.0/8 has level 0, 10.20.0.0/16 has level 1, and 10.20.4.0/22 has level 2. Two prefixes on the same level cannot overlap. A /22 that sits directly beside the /16 gets level 1, overlaps the /16, and is rejected. The caller must create the missing container or choose another range.

A trigger sets level on insert and updates the levels of the descendants when a new prefix lands between a parent and its children. The exclusion constraint is DEFERRABLE, and the trigger sets it to DEFERRED for this update only. to verify The prototype must prove this trigger and measure the cost on a table with 105 prefixes before the design is final. The ONA import creates prefixes in top-down order, so the import does not hit this case.

Why not one constraint on parent_id

A rule parent_id WITH = would not cover top-level prefixes, because NULL never equals NULL in an exclusion constraint. The level column covers every prefix in the VRF.

The reaper

The reaper is a background worker in the bembel binary. Every replica runs it. The replicas do not need to elect a leader (High availability). Each tick takes work with FOR UPDATE SKIP LOCKED, so two replicas never take the same rows.

-- every 60 seconds
WITH expired AS (
  SELECT id FROM address
  WHERE status = 'claimed' AND expires_at < now()
  ORDER BY expires_at
  LIMIT 500
  FOR UPDATE SKIP LOCKED
), gone AS (
  DELETE FROM address a USING expired e WHERE a.id = e.id
  RETURNING a.id, a.prefix_id, a.address
)
INSERT INTO event_outbox (type, subject_id, payload)
SELECT 'org.example.bembel.address.released', id,
       jsonb_build_object('address', address::text, 'reason', 'claim-expired')
FROM gone;

The history table keeps the deleted rows (History). The reaper writes an audit event with the subject service:bembel-reaper. A user can read in the audit log why an address came back.

Bulk allocation

A user or a controller often needs several addresses at once: 8 nodes of the rack A02, 16 pods of a service. One call gives count addresses, atomically:

POST /v1/prefixes/{id}/addresses:allocate
Idempotency-Key: 8a0c1e3b-...

{
  "count": 8,
  "strategy": "first",
  "contiguous": true,
  "dns_names": ["gpu-001.kestrel.example.org", "gpu-002.kestrel.example.org", "..."],
  "claim_ttl": "10m"
}
  • All count addresses or none. If fewer are free, the answer is 409 and no row changes.
  • With contiguous: true, the addresses form one block with no gap. The gap query then searches for runs of free addresses (a window function on the sorted candidates). A request that no block can satisfy gets 409 with the length of the longest free run.
  • The call takes the lock once. All addresses come from one snapshot, so the result is consistent.
  • One Idempotency-Key covers the whole call. A retry returns the same list.
  • The limit is 256 addresses for one call. A larger need uses a prefix allocation.
  • dns_names is optional. If given, it has count entries. A name clash rejects the whole call.

The batch endpoint for other kinds (POST /v1/hosts:batchCreate) follows the same rule: one transaction, per-item errors in the problem body, a cap on the size.

Utilisation

Utilisation shows how full a subnet or a pool is. The UI, the alerts and the advisory buttons use it.

  • Subnet, IPv4: used / usable. usable is the size minus the network and broadcast address. used is the number of address rows plus the addresses in ranges with the role dhcp-pool or reserved. Leases do not count: a pool counts fully, because the allocator never uses it.
  • Subnet, IPv6: the count used and the size as a power of two. A percentage in a /64 has no meaning. The API gives ratio: null for subnets larger than a /112. Alerts use the count.
  • Pool: the sum of the sizes of the child prefixes divided by the size of the pool, counted in /24 equivalents (IPv4) or /64 equivalents (IPv6).

Example, kestrel-compute 10.20.4.0/22: 1 024 addresses, 1 022 usable. The DHCP pool takes 255. There are 686 address rows (635 allocated, 38 reserved, 7 claimed, 6 deprecated). So used is 941 and the utilisation is 92.1 %. This is the value in the UI mockup and in the alert tests.

The table prefix_usage (prefix_id, used, usable) is updated in the allocate transaction, under the parent lock, so it is exact. A nightly job recomputes it from the rows and reports a difference as a finding. The metric bembel_prefix_utilisation_ratio reads this table (Observability).

Two calls at the same time

The explainer shows the story in 5 steps. a.berger and a Cluster API controller (service sa:capi-kestrel) both call addresses:allocate for the subnet 10.20.4.0/22 with strategy first. The addresses up to 10.20.4.45 are in use. The gateway is 10.20.4.1.

The same flow works for 500 callers. All of them wait in the lock queue and take one address each, in lock order. The unique constraint on (vrf_id, address) is never the first line of defence, only the last one.
