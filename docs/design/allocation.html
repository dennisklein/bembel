Allocation and lifecycle

This chapter specifies how bembel gives out addresses and prefixes. It covers the address states, the two allocate operations, claims, idempotent retries, the locks and constraints that make concurrent calls safe, and the reaper that cleans up.

  • An address is claimed, allocated, reserved or deprecated. A free address has no row.
  • POST /v1/prefixes/{id}/addresses:allocate picks the address on the server. The client never reads a list and then writes.
  • POST /v1/prefixes/{id}/prefixes:allocate cuts an aligned child prefix from a prefix pool with the best-fit rule.
  • A claim is an address in status claimed that holds the address for a short time (default 10 minutes). The caller confirms it, or the reaper releases it. Only addresses are claimed; prefixes never are.
  • The Idempotency-Key header makes a retry return the first answer. The key row and the address commit in one transaction, and the key row goes away when the address goes away.
  • One row lock on the parent prefix serialises the calls for one subnet. PostgreSQL constraints are the safety net.
  • Bulk allocation (addresses:batchAllocate) gives count addresses in one transaction: all or none.

Address states

The address table holds only addresses that someone uses or holds. A free address has no row. Free is the absence of a row, so the database cannot disagree with itself about it.

The events of an address are address.claimed (allocate with claim_ttl), address.allocated (direct allocate, confirm with previous_status: "claimed", reactivate), address.deprecated (release with a grace time), address.updated (also renew) and address.released. The last one means that the row is deleted. Its reason is released, claim-expired, grace-over or subnet-leaked.

Why a grace time

A deleted VM or host often comes back, or a cache still points at the old address. If bembel gives the address to the next caller at once, two systems can use it. The grace time keeps the address out of reach for 7 days.

Observed addresses (from the bembel-agent, from a sync, or from IPv6 neighbour data) get the flag observed=true and the state allocated. An observed address blocks allocation of the same value. A user cannot release it while the source still reports it: the answer is 409 address.observed.

Allocate the next free address

A client asks for an address. The server chooses it. The client never reads a free list and then writes, because that pattern has a race by design.

POST /v1/prefixes/{id}/addresses:allocate
Idempotency-Key: 6f1c2f1e-4f52-4a64-9d0e-0c1c8c7a5b10
Content-Type: application/json

{
  "strategy": "first",
  "fqdn": "cn-622.kestrel.example.org",
  "interface": {"host": "cn-622.kestrel.example.org", "name": "eno1", "mac": "3c:ec:ef:7a:10:22"},
  "owner": "hpc-ops"
}

This is the call that the Allocate dialog previews at the story moment: a.berger asks for the next free address for the new node cn-622. The answer is 201 Created with a Location header and the new address object. The state is claimed when claim_ttl is set (for example "claim_ttl": "PT10M", see Claims) and allocated when it is not. A request with "status": "reserved" makes a reserved address.

The body takes an interface by id (interface_id) or as an object (interface: host, name, MAC or port GUID), not both (422). With interface, bembel finds or makes the host and the interface. The field reservation: true adds a DHCP reservation and needs a MAC. A request that names address takes that address. If the address is taken, the answer is 409 address.conflict with the member holder. A request with a known external_ref returns the existing address with 200 (Adoption).

Skipped addresses

The allocator never returns these addresses:

  • The network address (IPv4 with prefix length < 31), and the subnet-router anycast address :: of an IPv6 subnet shorter than /127.
  • The broadcast address (IPv4 with prefix length < 31). A /31 (RFC 3021), a /32, a /127 (RFC 6164) and a /128 have no network or broadcast address, so every address in them can be given out.
  • The gateway of the subnet (10.20.4.1 in kestrel-compute).
  • Every address in a range with the purpose dhcp-pool, reserved, infrastructure, lb-pool or vpn-pool. A range with the purpose static is not skipped.
  • A request that names a range ("range": "kestrel-static") allocates only inside that range. The range must have the purpose static, infrastructure or reserved (the last needs range:update). Any other purpose gives 422.
  • Every address that has a row, in any state, including deprecated.

In the story data, 10.20.4.0/22 has 1 024 addresses. The DHCP pool 10.20.7.0–10.20.7.254 takes 255. The allocator can use the other 767 minus the gateway and the rows that exist.

The gap query

The first free address is always directly after a blocked item, or it is the first address of the subnet. A blocked item is an existing address, the gateway, or the end of a skipped range. When the request names a range, the first address of that range is a candidate too. So the query builds a short list of candidates and keeps the lowest one that is free. It never lists the whole subnet. It works for IPv4 and IPv6 without change, because it uses inet arithmetic. Every candidate is a host value (/32 or /128), so the query compares it with host(broadcast(cidr))::inet: an inet comparison includes the mask, and broadcast(cidr) keeps the mask of the subnet.

-- $1 = subnet prefix id, $2 = range id named in the request or NULL. The caller holds the row lock on this prefix.
WITH p AS (
  SELECT id, cidr, gateway,
         (family(cidr) = 4 AND masklen(cidr) >= 31)
      OR (family(cidr) = 6 AND masklen(cidr) >= 127) AS p2p        -- /31, /32, /127, /128: no network or broadcast address
  FROM prefix WHERE id = $1
), want AS (                                                      -- the named range, if any
  SELECT r.first_addr, r.last_addr FROM range r WHERE r.id = $2
), blocked_ranges AS (
  SELECT r.first_addr, r.last_addr
  FROM range r, p
  WHERE r.prefix_id = p.id
    AND r.purpose IN ('dhcp-pool', 'reserved', 'infrastructure', 'lb-pool', 'vpn-pool')
    AND r.id IS DISTINCT FROM $2
), cand AS (
  SELECT CASE WHEN p.p2p THEN host(network(p.cidr))::inet
              ELSE host(network(p.cidr))::inet + 1 END AS c FROM p
  UNION SELECT w.first_addr FROM want w
  UNION SELECT a.address + 1 FROM address a, p WHERE a.prefix_id = p.id
  UNION SELECT p.gateway + 1 FROM p WHERE p.gateway IS NOT NULL
  UNION SELECT br.last_addr + 1 FROM blocked_ranges br
)
SELECT cand.c
FROM cand, p
WHERE cand.c <<= p.cidr
  AND (p.p2p OR family(p.cidr) = 6 OR cand.c <> host(broadcast(p.cidr))::inet)
  AND cand.c IS DISTINCT FROM p.gateway
  AND NOT EXISTS (SELECT 1 FROM address a WHERE a.prefix_id = p.id AND a.address = cand.c)
  AND NOT EXISTS (SELECT 1 FROM blocked_ranges br WHERE cand.c BETWEEN br.first_addr AND br.last_addr)
  AND ($2 IS NULL OR EXISTS (SELECT 1 FROM want w WHERE cand.c BETWEEN w.first_addr AND w.last_addr))
ORDER BY cand.c
LIMIT 1;

The strategy last uses the mirror query. It starts at host(broadcast(cidr))::inet - 1 for IPv4 shorter than /31, and at host(broadcast(cidr))::inet for a point-to-point prefix (p2p). Its candidates are address - 1 and first_addr - 1, in descending order. The cost is O(n log n) for n rows in the subnet and uses the btree index on (prefix_id, address).

The allocator tests cover these edge cases: a /22 that is full except the broadcast address gives 409; a /31 gives both addresses; a /32 gives its one address; a gateway with a mask other than /32 or /128 is rejected by prefix_gateway_is_host.

Never generate_series for IPv6

A /64 has 264 addresses. A query that lists them cannot finish. bembel uses only gap queries for IPv6. For random it draws one value and checks it with the unique index. The same rule applies to IPv4 subnets larger than a /20: the code does not enumerate them.

If the query returns no row, the subnet is full. The answer is 409 Conflict with the problem type urn:bembel:problem:prefix.exhausted (errors). The body names the subnet and has the members largest_free and utilisation.

Allocate a child prefix from a prefix pool

A container prefix with is_pool = true hands out child prefixes. The VRF is the same as the parent. The request gives a length, not an address:

POST /v1/prefixes/{pool_id}/prefixes:allocate
Idempotency-Key: 0b8e8f1c-4c2a-4f8e-bf53-0d7a9e61c3d5

{
  "length": 24,
  "prefix_kind": "subnet",
  "name": "ceph-cluster",
  "site": "hall-2",
  "owner": "hpc-ops",
  "status": "planned"
}

Best fit and alignment

  1. bembel locks the pool row (Concurrency).
  2. It reads the child prefixes of the pool, in any status except deprecated with a past grace time.
  3. It removes the children from the pool range. What is left is the free space, written as the smallest list of aligned CIDR blocks (netipx.IPSet.Prefixes()).
  4. It keeps the blocks that are at least as large as the request (prefix length ≤ length).
  5. It takes the smallest of them. This is the best fit. If two blocks have the same size, it takes the lower address.
  6. It returns the first aligned sub-block of the requested length at the start of that block.

Every block of the list is aligned by construction, so the result is aligned: a /24 starts on a multiple of 256. The best-fit rule keeps big free blocks whole. A /20 request later still finds a /20.

The same algorithm works in IPv6. For the pool 2001:db8:4200::/48 a request for a /64 returns the lowest free /64. The pool never hands out a prefix longer than the limit on the pool: max_child_length (default 30 for IPv4, 126 for IPv6; for example a pool can be limited to /64 only).

FieldTypeRule
lengthint, requiredLarger than the pool length. At most max_child_length.

prefix_kindsubnet or containerDefault subnet. The field kind is only the object kind (prefix).

vlan_id or ib_partition_id, site, owner, tags, external_refoptionalSet on the new prefix in the same transaction. A prefix has a VLAN or an IB partition, never both (422).

A block of addresses inside a subnet, for example the pool of a load balancer, is a range, not a child prefix. POST /v1/prefixes/{id}/ranges:allocate with {size, purpose, name, hint?, external_ref?, tags?} returns the lowest free aligned block of size addresses (a power of two) outside every address row, the gateway and every range, or exactly hint if that block is free. Otherwise the answer is 409 prefix.exhausted. The call needs an Idempotency-Key and the permission prefix:allocate, and emits range.created.

Claims

A claim is an address row in status claimed with expires_at. There is no claim table and no claim resource in the API. Only addresses are claimed; prefixes never are. The caller wants to be sure that the address stays free while it does something slow: boot a VM, or create a Neutron port. The caller confirms the claim, gives it up, or lets it end.

# claim for 10 minutes: 201, status claimed
POST /v1/prefixes/{id}/addresses:allocate   {"claim_ttl": "PT10M", ...}

# confirm: the claim becomes an allocation (200, status allocated)
POST /v1/addresses/{id}:confirm             {"interface_id": "...", "fqdn": "..."}

# extend the time (at most max_claim_ttl in total)
POST /v1/addresses/{id}:renew               {"claim_ttl": "PT10M"}

# give up: a claimed address is deleted at once
POST /v1/addresses/{id}:release

The confirm body is {fqdn?, interface_id? | interface?, external_ref?, reservation?}, and the call needs an Idempotency-Key. A confirm of an address that is already allocated gives 200 and changes nothing. A confirm or renew after expiry gives 409 claim.expired with the member expired_at: bembel finds the expired claim in the history table. An unknown id gives 404. A renew that takes the total life over max_claim_ttl gives 422 validation.failed. The claims of a subnet are listed with GET /v1/addresses?status=claimed, bembel address ls --status claimed or the UI page /addresses?status=claimed.

The permission kind claim is tested on the subnet of the address (permissions).

Who uses claims, and who does not:

  • Neutron driver (OpenStack): claims at allocate, and the OpenStack sync confirms it on the next poll after the port commit.
  • bembel vm prepare (libvirt hook): claims an address and a MAC with publish: true (TTL default 24 h, the maximum), and the hook confirms it by MAC when the domain starts.
  • Cluster API provider (Kubernetes): makes no claim. It allocates directly, one address per IPAddressClaim, found again by external_ref (Adoption).

A claim is in the address table, so the unique constraint covers it and the gap query skips it. The DNS and DHCP exports read allocated addresses, reserved addresses with an FQDN, and claimed addresses with publish: true. Deprecated addresses make no record unless dns.publish_deprecated is set (derived records). Metrics count open, held and expired claims (Observability).

Why a TTL and not a lease

A DHCP lease belongs to a client on the network. A claim belongs to a caller of the API. The caller can crash. If the claim had no time limit, a crash would leak the address for ever. With a TTL, a crash leaks the address only until the TTL ends (default 10 minutes).

Release

POST /v1/addresses/{id}:release with {"grace": "P7D"} ends the use of an address. An allocated or reserved address becomes deprecated for the grace time, then the reaper frees it. Its DNS records and DHCP reservation leave the export when it becomes deprecated. A claimed address is deleted at once.

  • A request without grace uses allocation.default_release_grace (7 days).
  • "grace": "PT0S" frees the address at once. The CLI asks for a confirmation for --now.
  • The release of an observed address that its source still reports gives 409 address.observed.
  • An allocate with the same external_ref during the grace time reactivates the address (Adoption).

Idempotency-Key

These calls need an Idempotency-Key header (an unguessable string of 8 to 255 characters, a UUID is fine): addresses:allocate, addresses:batchAllocate, prefixes:allocate, ranges:allocate and addresses/{id}:confirm. A call without it gets 400 request.invalid, and the detail names the header. Every other POST call, :release and :renew included, accepts the header and treats it the same way. bembel follows the IETF draft The Idempotency-Key HTTP Header Field. The same rules are in REST API.

CaseResult
New keybembel runs the call and stores the key, the request fingerprint, the response and the ids of the objects that the call created.
Same key, same fingerprint, first call finishedbembel returns the stored response: the same status code and the same body, with the header Idempotent-Replayed: true. It does not allocate again.
Same key, same fingerprint, first call still runningThe second call waits on the key row. If the first call commits, the second returns its stored response. If the first call rolls back, the second runs as new. A wait longer than lock_timeout (5 s) gives 409 idempotency.in-progress with Retry-After: 1.
Same key, different fingerprint422 with the problem type idempotency.mismatch. Nothing changes.
First call failed with 4xx or 5xxbembel does not store the response. The retry runs again. An error that depends on the state, such as prefix.exhausted, can then succeed.
The object the first call created has since been released, expired or deletedThe key row went with it. The call runs again as new.
Key older than 24 hoursThe reaper deletes the row. The key counts as new.

The fingerprint is the SHA-256 of the method, the path and the canonical JSON body. The key is scoped to the subject: two subjects can use the same string without a clash.

CREATE TABLE idempotency_key (
  subject      text        NOT NULL,
  key          text        NOT NULL,
  fingerprint  bytea       NOT NULL,
  status       int         NOT NULL,
  response     jsonb       NOT NULL,
  resource_ids uuid[]      NOT NULL DEFAULT '{}',   -- ids this call created (all of them for a batch)
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (subject, key)
);
CREATE INDEX idempotency_key_created   ON idempotency_key (created_at);
CREATE INDEX idempotency_key_resources ON idempotency_key USING gin (resource_ids);

The key row is inserted in the same transaction as the address. If the transaction rolls back, the key row rolls back too. If it commits, both exist. So there is no state where the address exists and the key does not. A client can retry after a timeout and gets the same address, as long as that address is still claimed or allocated.

A stored response is valid only while the objects it created are live. Every transaction that releases, expires or deletes such an object also deletes the key rows that point at it, with DELETE FROM idempotency_key WHERE resource_ids && $ids. This runs in :release (to deprecated or deleted), in the two deletes of the reaper (expired claim and deprecated grace), and in prefix delete and range delete. A later retry with that key then runs as a new call and cannot replay an address that another caller holds now. Calls that only change objects (:release, :confirm, :renew, PATCH) store an empty resource_ids.

Controllers and deterministic names

A controller that reconciles in a loop should also send a stable name in external_ref, for example k8s:kestrel-mgmt:ipaddressclaim/capi-kestrel/kestrel-k8s-cp-0-eth0 (namespace and name; the UID changes on clusterctl move). Then a lost or expired key does not matter: the unique index address_source_ref gives the existing address back.

Adoption by external_ref

The server sets source (and managed_by for an integration subject) from the source mapping of the subject. The client may send external_ref on create. A later change of it gives 422. It is unique per source. Inside the allocate transaction, before the gap query, bembel looks for an address with the same (source, external_ref):

Concurrency

Two callers can ask for an address in the same subnet at the same moment. bembel serialises them with a row lock on the parent prefix.

BEGIN;
SET LOCAL lock_timeout = '5s';

-- 1. Idempotency: a retry returns here, before it takes the lock.
INSERT INTO idempotency_key (subject, key, fingerprint, status, response)
VALUES ($subject, $key, $fp, 0, '{}')
ON CONFLICT (subject, key) DO NOTHING
RETURNING 1;                       -- no row: the key exists (an in-flight first call was waited for);
                                   -- read the stored answer and stop

-- 2. Serialise all callers of this subnet.
SELECT id, cidr, gateway FROM prefix WHERE id = $1 FOR UPDATE;

-- 3. Adoption: an existing (source, external_ref) answers here with 200 (see above).

-- 4. Gap query (see above), then:
INSERT INTO address (id, vrf_id, prefix_id, address, status, expires_at, owner, source, external_ref)
VALUES (uuidv7(), $vrf, $1, $chosen, $status, $expires_at, $owner, $source, $external_ref)
RETURNING *;                       -- 'claimed' with now() + claim_ttl, or 'allocated' with NULL

UPDATE prefix_usage SET used = used + 1 WHERE prefix_id = $1;
INSERT INTO event_outbox (...) VALUES (...);          -- same transaction; bembelseq is set after commit
UPDATE idempotency_key SET status = 201, response = $resp, resource_ids = ARRAY[$new_id]
 WHERE subject = $subject AND key = $key;
COMMIT;

Why a row lock

  • PostgreSQL releases it at the end of the transaction. A crashed server cannot keep it.
  • It works behind PgBouncer in transaction mode. A session advisory lock does not.
  • It is visible: pg_locks and pg_stat_activity show who waits for which prefix.
  • It locks one row. Calls for other subnets do not wait.
SituationBehaviour
Two calls, same subnetThe second waits for the first commit, then sees the new row and takes the next address.
Two calls, different subnetsNo wait.
Wait for the prefix lock longer than lock_timeout (5 s)503 with Retry-After: 1. With the same key the retry is safe.
Prefix allocation in a poolLocks the pool row. An address allocation in a child subnet locks the child row. They do not block each other.
Allocate of a chosen address (addresses:allocate with address)Takes the same row lock. If the address exists, the answer is 409 address.conflict.
Lock orderAlways the parent first, then nothing else. No call locks two prefixes, so deadlocks between allocations cannot occur.

The lock limits the rate for one subnet. The critical section is one index lookup and two inserts, so the expected time is a few milliseconds. That gives hundreds of allocations per second for one subnet. The number is an estimate. A load test measures it (Operations).

The constraint is the second guard

The lock prevents the conflict. The unique constraint and the exclusion constraint (next section) make sure that a bug in the code, a manual SQL change or an import cannot create one. If the constraint fires, bembel repeats the transaction up to 3 times (for :allocate and for prefix creates), and then maps 23505 and 23P01 to 409.

PostgreSQL constraints

The database rejects an invalid state. The rules do not rely on the application. This excerpt repeats the allocation-relevant parts of the schema in Core model, with the same columns.

  CONSTRAINT address_unique_per_vrf UNIQUE (vrf_id, address)
);
CREATE INDEX address_by_prefix ON address (prefix_id, address);
CREATE INDEX address_claim_expiry ON address (expires_at) WHERE status = 'claimed';
CREATE UNIQUE INDEX address_source_ref ON address (source, external_ref) WHERE external_ref IS NOT NULL;

An object that the ONA import merged from several ONA rows keeps the extra refs in object_ref (kind text, object_id uuid, source text, external_ref text, UNIQUE (source, external_ref)). A lookup by ref checks both tables, so it still finds exactly one object.

Why the exclusion uses a level

Prefixes in a tree contain each other, so a simple "no overlap" rule would reject a /16 and the /22 inside it. The column level solves this: it counts the prefixes in the same VRF that contain this one. The prefix 10.0.0.0/8 has level 0, 10.20.0.0/16 has level 1, and 10.20.4.0/22 has level 2.

Two CIDR blocks are either nested or disjoint. While the trigger keeps level correct, two overlapping prefixes always have different levels, so the exclusion never fires in normal use. It catches a wrong level: two concurrent transactions that insert nested prefixes can both compute the same level from snapshots that do not see each other. The exclusion rejects the second with 23P01. bembel repeats the transaction up to 3 times, and the retry computes the right level.

A trigger sets level and parent_id on insert and updates the levels of the descendants when a new prefix lands between a parent and its children. The exclusion constraint is DEFERRABLE, and the trigger sets it to DEFERRED for this update only. to verify The prototype must prove this trigger and measure the cost on a table with 105 prefixes before the design is final. The ONA import creates prefixes in top-down order, so the import does not hit this case.

The same BEFORE trigger (on INSERT, and on UPDATE of cidr, vrf_id or prefix_kind) keeps the tree rule that a subnet has no child prefix. It raises 23514 in two cases:

  • prefix_not_in_subnet: the smallest prefix in the VRF that contains the new prefix is a subnet.
  • prefix_subnet_childless: the new prefix is a subnet, and prefixes in the VRF already exist inside it.

Why not one constraint on parent_id

A rule parent_id WITH = would not cover top-level prefixes, because NULL never equals NULL in an exclusion constraint. The level column covers every prefix in the VRF.

The reaper

The reaper is a background worker in the bembel binary. Every replica runs it. The replicas do not need to elect a leader (High availability). Each tick takes work with FOR UPDATE SKIP LOCKED, so two replicas never take the same rows.

A claim of a source that confirms claims by sync (the column source.confirms_claims; today the kind openstack) needs more than the time. bembel reaps it only after a successful sync run that started after expires_at has not confirmed it. While the sync is late or down, the expired claim is held, so the reaper never frees the address of a live Neutron port. The sync stays the only confirm path for these claims. The claim_ttl of such a source should be at least 3 times its sync interval; this is advice, not a check.

-- every 60 seconds
WITH expired AS (
  SELECT a.id FROM address a
  LEFT JOIN source s ON s.key = a.source AND s.confirms_claims
  WHERE a.status = 'claimed' AND a.expires_at < now()
    AND (s.key IS NULL OR s.last_success_started_at > a.expires_at)
  ORDER BY a.expires_at
  LIMIT 500
  FOR UPDATE OF a SKIP LOCKED
), gone AS (
  DELETE FROM address a USING expired e WHERE a.id = e.id
  RETURNING a.id, a.prefix_id, a.address
), keys AS (
  DELETE FROM idempotency_key k USING gone g WHERE g.id = ANY (k.resource_ids)
)

SELECT 'org.example.bembel.address.released', id,
       jsonb_build_object('address', host(address), 'reason', 'claim-expired')
FROM gone;

Bulk allocation

A user or a controller often needs several addresses at once: 8 new nodes of one rack, 16 pods of a service. One call gives count addresses, atomically:

POST /v1/prefixes/{id}/addresses:batchAllocate
Idempotency-Key: 8a0c1e3b-...

{
  "count": 8,
  "strategy": "first",
  "contiguous": true,
  "fqdns": ["cn-623.kestrel.example.org", "cn-624.kestrel.example.org", "..."],
  "claim_ttl": "PT10M"
}

The answer is 201 with {"items": [...]}, a list of address objects. The body has the fields of a single allocate without address, hint and fqdn, plus count (1 to 256, required), contiguous (default false) and fqdns.

  • All count addresses or none. If fewer are free, the answer is 409 prefix.exhausted and no row changes.
  • With contiguous: true, the addresses form one block with no gap. The gap query then searches for runs of free addresses (a window function on the sorted candidates). A request that no block can satisfy gets 409 prefix.exhausted with the member longest_free_run.
  • The call takes the lock once. All addresses come from one snapshot, so the result is consistent.
  • One Idempotency-Key covers the whole call. Its key row holds the ids of all the addresses. A retry returns the same list while all of them are live.
  • The limit is 256 addresses for one call. A larger need uses a prefix allocation.
  • fqdns is optional. If given, it has count entries. A name clash rejects the whole call.

The batch endpoint for other kinds (POST /v1/hosts:batchCreate) follows the same rule: one transaction, per-item errors in the problem body, a cap on the size.

Plan and apply

A user often brings a list: 40 nodes of a new rack in a spreadsheet, or 120 records of a new service. bembel reads such a list as a plan first and writes it only after a confirm.

  • Every batch call accepts "validate_only": true. The server runs all checks and the permission test in a transaction that it rolls back. The answer is the plan: for each row the action (create, update, delete, none), the changed fields and the findings. The plan has a hash.
  • bembel apply -f rack-a04.csv (or a YAML file) reads the rows, asks for the plan, prints it as a table and asks for a confirm. Then it sends the same calls with plan_hash. If the data changed after the plan, the hash differs and the answer is 409 plan.stale.
  • A CSV file has one kind for each file, and a header row with the API field names (fqdn,prefix,mac,interface,owner,tags). A row finds its object by the natural key (FQDN for a host, VRF and address for an address, zone, name and type for a record), so a second apply of the same file changes nothing.
  • A plan with more than access.change_request.bulk_threshold objects (default 50) becomes a change request. The request holds the plan, and the approver sees the same table (access.html#changes).
  • The Import dialog of the web UI and the bulk edit of the lists use the same calls.

Hosts and networks change place. bembel has one call for each kind of move. Each call keeps the names, so the derived records and the reservations follow.

Utilisation

Utilisation shows how full a subnet or a pool is. The UI, the alerts and the advisory buttons use it.

  • Subnet, IPv4: used / usable. usable is the size minus the network and broadcast address. used is the number of address rows plus the addresses in ranges with the purpose dhcp-pool, reserved, infrastructure, lb-pool or vpn-pool, each address counted once. Leases do not count: a pool counts fully, because the allocator never uses it.
  • Subnet, IPv6: the count used and the size as a power of two. A percentage in a /64 has no meaning. The API gives percent: null for subnets larger than a /112. Alerts use the count.
  • Pool: the sum of the sizes of the child prefixes divided by the size of the pool, counted in /24 equivalents (IPv4) or /64 equivalents (IPv6).

Example, kestrel-compute 10.20.4.0/22: 1 024 addresses, 1 022 usable. The DHCP pool takes 255. There are 686 address rows (635 allocated, 38 reserved, 7 claimed, 6 deprecated). So used is 941 (of which only 635 are in status allocated) and the utilisation is 92.1 %. This is the value in the UI mockup and in the alert tests.

The table prefix_usage (prefix_id, used, usable) is updated in the allocate transaction, under the parent lock, so it is exact. A nightly job recomputes it from the rows and reports a difference as a finding. The metric bembel_prefix_utilisation_ratio reads this table (Observability).

The nightly usage recount writes one row for each prefix and day into prefix_usage_daily (prefix_id, day, used, usable). It keeps the rows for 3 years. The prefix page draws the trend from it, and the report utilisation uses it (reports).

Observations

bembel knows what it allocated. An observation tells it what the network really uses. All sources write through one call:

POST /v1/observations:batch

{
  "source": "sweep:agent-ns1",
  "items": [
    {"vrf": "global", "address": "10.20.4.44", "mac": "3c:ec:ef:12:0a:44", "seen_at": "2026-11-04T16:02:11Z", "method": "arp"},
    {"vrf": "global", "address": "10.20.4.230", "seen_at": "2026-11-04T16:02:12Z", "method": "icmp"}
  ]
}
  • The methods are lease, dhcp-ack, arp, nd, icmp, nmap, libvirt, vpn and sync. The DHCP lease ingestion has its own call, because it also keeps the lease state, and it writes the same observations with lease and dhcp-ack (dhcp.html#leases).
  • A known address gets last_seen_at, last_seen_mac, last_seen_source and, if the MAC differs from the interface, the finding address.mac-mismatch.
  • An unknown IPv6 address in a subnet becomes an observed address. An unknown IPv4 address gives the finding address.unknown-seen: someone uses an address that bembel did not give out.
  • bembel observe import --format nmap-xml scan.xml reads an nmap XML file and sends it with the method nmap. Thus an existing scan job keeps its value.
  • The bembel-agent can do a reachability sweep of the subnets in its scope: ICMP echo, and ARP or ND on its own links. The sweep is off by default. It has a rate limit (agent.sweep.rate, default 50 packets/s) and a list of subnets that it never touches. Turn it on only with the approval of the network security team.
  • The permission is observation:create, tested on the subnet of the address. A read of the raw observations needs observation:read.

The report stale-addresses uses all methods. Thus a static server that answers ICMP is not stale, although it never asks for a lease.

Two calls at the same time

The explainer shows the story in 5 steps. a.berger and d.klein (subject kc:d.klein, from the CLI) both call addresses:allocate for the subnet 10.20.4.0/22 with strategy first and no claim_ttl. At the story moment the first free addresses are 10.20.4.213 and 10.20.4.214. The gateway is 10.20.4.1.

The same flow works for 500 callers. All of them wait in the lock queue and take one address each, in lock order. The unique constraint on (vrf_id, address) is never the first line of defence, only the last one.
