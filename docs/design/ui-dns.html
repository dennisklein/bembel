UI: DNS and DHCP

This chapter specifies the web UI pages for names, leases and delivery: Zones, one Zone, the record dialog, a DHCP scope, Exports, the parallel-run diff, and Routing and groups. The shell and the common parts are in ui.html. Each page below has a screenshot of the mockup, its purpose, its parts with the reason for each part, its states, and its URL, API calls and CLI commands.

  • The screenshots show one moment of the story: 4 November 2026, 18:02. Bundle b-7c41e0 is on all servers, and night 12 of 14 of the parallel run with ONA is over.
  • A record shows where it comes from. A derived record has a lock and a link to its address. A manual record has a checkbox and an edit action. The user never edits an A, AAAA or PTR record in a zone.
  • Every dialog and every page shows the CLI command of its action, and an assistant button where a known tool plan exists. The assistant only reads. It proposes drafts.
  • The Exports page is the place that says "the servers have what bembel knows". A target that does not pull is a warning, not an error.
  • The diff page makes the parallel run decidable: three lines, one known, two unexplained, each with a reason and a next step.

Common parts

All pages use the shell of ui.html: top bar, sidebar, main area. Zones is in the group "DNS and DHCP", with DHCP scopes and Exports. Routing and groups is in the group "Addressing". The page head of each page has the title, one line of facts, a CLI toggle, at most one assistant button and at most one filled button for the real next step.

Four rules hold on all pages of this chapter.

  • Origin before edit. A derived record is read only. The lock has a tooltip: "Derived from an address. Change the address to change this record." The row links to the address (409 record.derived is the API answer to a write).
  • One list for all states. A pill shows only a state that needs a look (stale, failed, new, unexplained). The normal state is a dot and a word.
  • Preview before write. The record dialog shows the zone file line. The export page offers Preview. A user sees the text that a server will read.
  • Names as values. An FQDN, an IP, a MAC and a prefix use the value classes of the shared components: mono, no break inside, muted domain part.

Zones

Purpose: the page lists all zones that the user may see, and says which one needs a look. It is the start of every DNS task.

Layout

  • Head. "41 zones in 3 views", the split forward and reverse, the record count, the access of the user as a scope chip. Buttons: CLI toggle, "Check all zones" (assistant, quiet), "New zone…" (filled).
  • Banner. One warning when a zone has findings from the ONA import. It says what is wrong and who decides. It links to the import page.
  • Toolbar. A filter box, chips for kind, view, team and "Needs a look", and a Tree or Flat switch. Each chip has a count.
  • Table. Two groups: "Forward zones" and "Reverse zones". Child zones are indented under their parent. Columns: zone, views, records, derived and manual, serial, DNS servers, team, last export, status.
  • DNS servers and views. A second card with ns1, ns2 and ns3: role, views, zone count, serial of kestrel.example.org, last pull.

Zone

Purpose: the page shows and changes the facts and the records of one zone in one view. It tells a user where each record comes from and what a change does.

Layout

  • Head. The breadcrumb Zones / example.org / kestrel.example.org, the name, a chip with the view, a pill "exported", one line of facts. A view switch (internal 1 846, external 3), the CLI toggle, "Check zone" (assistant) and "New record…" (filled).
  • Tabs. Records, Delegations, Servers, History. Each tab has a count.
  • Zone facts. Three columns: serial, primary, contact; refresh, retry, expire, negative TTL, default TTL; the NS set, parent, source. "Edit…" opens the SOA dialog.
  • Records. Filter, type chips with counts, origin switch (All, Derived, Manual), the bulk bar, the table, the footer with paging.
  • Side column. "Checks" with the result of named-checkzone and the rules of bembel, and the result card of the assistant.

The records table

ColumnContent
FirstA checkbox for a manual row. A lock for a derived row, and for the NS set.
NameRelative to the zone. @ is the apex. A new tag marks a record younger than the last export (cn-011).
TypeA small chip: A and AAAA in the DNS colour, CNAME in blue, SRV, MX and TXT in violet.
TTLSeconds. An empty TTL in the data shows the zone default.
DataBy type. SRV shows priority, weight and port in bold and the target as an FQDN. TXT shows the quoted text.

LastA ⋯ menu. A derived row offers "Copy as zone file line" and "History". A manual row adds "Edit…" and "Delete…".

Why the lock

ONA let a user edit an A record in the DNS table and then did not match the address. In bembel the address is the one source. The lock is a visible refusal, with the way out in the tooltip and in the link of the origin column.

Inline edit and validation

The ⋯ menu of a manual row, or a double click, turns the row into inputs: name, type, TTL, data. The row gets a grey background and a red left edge when it has an error. The error stands under the data field. It has a code, a plain sentence and a link to the cause.

The example in the mockup: a user renames the CNAME slurm to ctl01. The name has a derived A record from 10.20.4.5. The API answers 409 with the problem code cname.conflict. The row shows: "ctl01 already holds an A record, derived from 10.20.4.5. A name with a CNAME cannot hold other records." Save stays disabled until the user changes the name.

Bulk actions

A selection of manual rows opens a bar over the table: "2 manual records selected", with Set TTL…, Copy to view… and Delete…. The bar does not list derived rows. A bulk change of more than the configured limit becomes a change request (access.html). The dialog says so before the user confirms.

Checks and the assistant

  • Checks card. Five lines with a dot: named-checkzone ok, no CNAME beside other data, PTR coverage, targets outside the zone, and the unsaved row. A warning has a second line with the detail.
  • Check zone. The advisory check-zone reads the records and the last export diff. The answer is one sentence of verdict and a numbered list. It cites the known difference kd-1 and the new record cn-011. A fold "Tools used" lists the calls. A button opens the diff.

States

  • External view. The switch shows the 3 records of view external. A record that exists only in one view has a chip with that view.
  • Managed zone. A zone with source=openstack:os-prod has locks on all rows and a banner "managed by". Humans cannot edit it.
  • Held change. A delete that needs a change request shows the row as "pending" until an approver acts.
  • Conflict. A save with an old If-Match shows "Another user changed this record" and offers a reload of the row.
URL
/zones/{zone}[?view=internal&tab=records&type=&origin=manual&q=], tabs tab=delegations|servers|history
API

CLI
bembel record ls kestrel.example.org --view internal --manual, bembel record add …, bembel zone check kestrel.example.org

Record dialog

Purpose: the dialog creates or changes a manual record. It shows the result in the form of the zone file before the user saves.

Parts and why

  • Name with suffix. The input takes the relative name. The zone name stands after it as a fixed suffix .kestrel.example.org.. A user cannot write the wrong zone. @ means the apex.
  • Type. A, AAAA and PTR are not in the list. The hint says they come from addresses. The list has CNAME, MX, NS, CAA, SRV and TXT.
  • TTL. A number of seconds. An empty field takes the zone default, shown in the hint.
  • Data fields by type. The group below changes with the type. A short table shows each form.
  • Views. One checkbox per view of the zone, with the record count of the view. The default is the view of the zone page.
  • Warning. A banner explains the CNAME rule for this name: "A name that holds an SRV cannot hold a CNAME." It names the number of records at the name.
  • Preview. A dark block shows the lines of the zone file at this name, with the new line in green, and the serial change. Four checks stand under it.
  • Command. The same change as a bembel record add command, with a copy button.
  • Footer. The role of the user in the scope, the audit note, and the undo ("delete the record"). Cancel is on the left, "Create record" is filled.
TypeFieldsCheck
CNAMEtarget nameThe name holds no other record. The name is not the apex. The target is not a CNAME that loops.
MXpreference, mail hostThe host has an address record and is not a CNAME.
NSname serverOnly for a delegation. The zone NS set has its own place.
SRVpriority, weight, port, targetThe target has an A or AAAA record in the view. The mockup shows 10.20.4.7.
TXTtextbembel splits the text at 255 bytes and escapes a semicolon and a quote.
CAAflag, tag, valueThe tag is issue, issuewild or iodef.

Why a preview of the zone file

The DNS editors of the organisation know the zone file format. A line in that format needs no explanation. It also shows what the next export will contain, so the user finds a wrong dot at the end of a name before the server does.

States

  • Error. An invalid field has a red border and a sentence under it. "Create record" stays enabled. The server answer shows on the first field it names.
  • Edit. The title is "Edit record in …". The name and type are fixed. The footer shows "Revision 7".
  • Held. A change that needs approval has the button "Ask for approval…" and a field for the reason.
  • No permission. The page behind the dialog does not offer the dialog. The button is disabled, with the reason in its title.
URL
A dialog on /zones/{zone}. A link with ?new=SRV&name=_slurmctld._tcp opens it filled.
API
POST /v1/zones/{id}/records (Idempotency-Key), PATCH /v1/records/{id} (If-Match), POST /v1/zones/{id}/records:validate for the preview and the checks.
CLI
bembel record add kestrel.example.org --view internal --name _slurmctld._tcp --type SRV --data "30 0 6817 ctl03.kestrel.example.org."

DHCP scope

Purpose: the page shows the DHCP settings of one subnet: the pool, the reservations, the options and the state of the leases. It answers "which clients get which address and which options, and from which server".

Layout

  • Head. The scope name, the prefix, a pill "enabled". The line: VRF, VLAN 204, gateway, team, fabric. Buttons: CLI toggle, "Find stale reservations" (assistant), "New reservation…" (filled).
  • Main column. Pools and address map, Reservations, Reservations by client identifier, Options, Leases.
  • Side column. Scope facts, Failover pair, the assistant result.

Why the chain, not only the value

ONA showed the option at one level. A user could not see why a host got MTU 1500 when the scope says 9000. The chain shows the answer, and the note names the overrides ("overridden for 2 hosts").

Find stale reservations

The advisory stale-reservations reads the reservations, the leases and the asset mirror. In the story it finds 4 of 641 reservations with no lease for 90 days. For cn-009 the asset mirror says "removed since 2026-08-02". The card lists the findings and offers "Open draft". The draft deletes nothing until the user applies it (assistant.html).

States

  • Scope off. The pill says "disabled". The pool and reservations stay visible. The export omits the scope.
  • Failover degraded. A node with state "communications interrupted" has a red dot and the banner "dhcp2 does not answer". The pool row shows the share of the secondary as "unavailable".
  • No lease data. If the ingestion is older than 15 minutes, the Leases card says "Lease data is 42 min old" with a warning dot.
  • Pool nearly full. The meter turns yellow at 70 % and red at 90 %.

Exports

Purpose: the page shows, for each delivery target, which bundle it has, whether the checks passed and when the agent pulled it. It also builds a bundle now and previews files. It is the page for the question "do the servers have my change?".

Layout

  • Head. "8 delivery targets · 7 current, 1 stale", the last bundle, the parallel-run state. Buttons: CLI toggle, "Why does the export differ?" (assistant), "Preview…", "Build now" (filled).
  • Banner. A warning for the stale target, with "Pull log" and "Silence 24 h…".
  • Target cards. Two columns. One card per target: ns1, ns2, ns3, dhcp1, dhcp2, sm-kestrel, fw-edge, frr-core.
  • Bundle history. A table: bundle, trigger, targets, built, duration, zones changed, lines, files, checks, diff link.

Actions

  • Build now. It builds all targets whose content changed. The result shows as a toast and a new row in the history. It never pushes: the agents pull.
  • Preview. It renders the files of one target in a dialog, with a file list on the left and the text on the right. It writes nothing.
  • Pull log. The list of the last pulls of a target, with time, agent, code and ETag.
  • Silence. It mutes the stale warning for a time. It needs a reason and writes an audit event.

States

  • Build failed. The history row has a red pill "failed" and a link "log". The targets keep their last good bundle. The head says "1 build failed".
  • Nothing changed. A scheduled build with no change creates a row "no change". It makes no new bundle.
  • Running. The build button shows a spinner and "Building…". The cards stay.

Export diff

Purpose: during the parallel run the page compares the ONA export with the bembel bundle of one target. A user decides each differing line: explained, or to fix. The run ends when the diff is empty or fully explained on the last 3 nights (migration.html).

Parts and why

  • Summary. Three numbers: 3 differing lines in 2 of 41 files, 1 known difference, 2 unexplained. A bar splits the lines by class. A bar chart shows the unexplained lines for each night; the current night is marked. The cutover rule stands under it. The user sees the trend, not only a count.
  • File tree. Files of the bundle with "identical" or "N lines". The filter "Differ" is on. Identical files fold into one line "31 more, all identical". The note says that ONA writes no views, so ONA is compared with view internal.
  • Normalised before the diff. A card lists what the diff ignores: the SOA serial and the header date, and the order of record lines (dns.html#compat). A user knows what the "identical" claim covers.
  • Diff. One card per file. A dark block with two line-number columns, the sign, and the text. A removed line has a red tint, an added line a green tint, a hunk header a blue band. A badge ends the line: "known kd-1" links to the list below; "unexplained" is yellow.
  • Explain diff. The result card of the advisory explain-diff. It explains each class in one sentence, and it checks the claim with a canonical zone dump ("L2 check"). It cannot accept a line. The button "Accept 2 lines as known difference…" opens a dialog that the user confirms.
  • Known differences. A table of rules: id, what differs, why it is fine, who accepted it and when, and the lines that match tonight. A rule expires at the cutover.

Why accept by rule and not by line

A line number changes every night. A rule matches by zone, type and a pattern, so the same difference is not a new question the next night. A new kind of difference never matches an old rule by accident.

States

  • Empty diff. The summary says "0 differing lines" with a green mark. The page counts the nights with an empty or explained diff.
  • Accept dialog. It asks for a note of 8 characters or more, shows the pattern of the rule, and the CLI command. The audit event names the user.
  • No ONA data. If the ONA export of the night is missing, the page says so and shows no diff.
URL
/exports/ns1/diff[?night=12&file=]
API
GET /v1/exports/{id}/diff?against=ona&night=12, POST /v1/exports/{id}/known-differences. Both are a proposal for the OpenAPI document.
CLI
bembel export diff ns1 --against ona:/srv/ona/zone_data --normalize, bembel export diff accept ns1 --line db.kestrel.example.org:34 --note "…" --until cutover
Assistant
"Explain diff": advisory explain-diff, tools export.diff, address.get, audit.query.

Routing and groups

Purpose: the page holds the values that network automation and firewalls read: ASNs, route targets, static routes and address groups. bembel is the source of the values. It does not push device configuration (routing.html). This section describes the tab Address groups.

Parts and why

  • Tabs. ASNs 3, Route targets 12, Static routes 27, Address groups 7. The mockup shows the last one.
  • Groups table. Name and description, filter as chips (host.role login, vrf global, team hpc-ops), member count, feeds (nftables, EDL, firewalld, JSON), consumers with the last pull. The selected row has a tint. A group with no consumer says so.
  • Filter card. The definition of login-nodes as YAML in a dark block, the revision, the editor, and a table of the 4 matching hosts with the reason. "6 members" counts hosts and prefixes.
  • Feed card. The plain text list that a firewall fetches over HTTPS: a comment line and one entry per line. The URL has a copy button. Two consumers show the last pull, the code and the ETag.
  • Prefix list card. A preview of bembel export prefix-list for FRR with a switch for bird, junos and eos. It shows the prefixes with announce=true in VRF global and the target frr-core.

Why a filter and not a list

A list of addresses is old after the next allocation. A filter follows the data: a new login node with role login joins the group and all feeds change at the next build. The firewall policy stays in the firewall tool and refers to the group by name.

  • Consumer late. A consumer that did not pull for 3 intervals gets a yellow dot, as a target on the Exports page.
  • Edit. "Edit…" opens the filter as YAML with a live count of members and a diff of the feed. Saving writes a new revision.
