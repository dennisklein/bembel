Migration from OpenNetAdmin

This chapter describes how the organisation moves from ONA 19.0.x to bembel without a big bang. ONA stays the writer until the cutover. bembel imports its data again and again, builds the same files as ONA, and a nightly diff proves that the files are equal. Then DNS moves first and DHCP follows. The mapping rules are in map-ona.html.

  • ONA stays the only writer until the cutover. bembel only reads ONA, as often as needed.
  • bembel import ona is idempotent. Every object has the external ref ona:TABLE:ID, so a new run updates and never duplicates.
  • Each data problem is a finding with a code. The fix is a change in ONA or a rule in the map file. Then the next run closes the finding.
  • The parallel run builds the BIND and dhcpd files in ONA and in bembel from the same dump, normalises both and compares them every night. The exit criterion is 14 nights in a row without an unexplained difference.
  • The cutover is per service: freeze, last import and DNS in window A, DHCP in window B. The bembel-agent on each server switches its source.
  • The SOA serial of a zone never goes below the unix-time serial that ONA wrote.
  • Rollback means: switch the agent URL back to the ONA files. ONA stays read-only for 30 days.

The story in the examples

The organisation runs ONA 19.0.x on MariaDB with about 41 000 hosts, 1 900 subnets and 62 000 DNS records. The DNS servers are ns1.example.org (primary) with ns2 and ns3. The DHCP servers are dhcp1.example.org and dhcp2.example.org, a failover pair. The import run imp-20261104-0912 finds 214 findings. Today is night 12 of 14 of the parallel run. The user d.klein runs the migration.

Plan

The plan follows five rules.

  1. One writer. At each time only one system accepts changes. It is ONA until the freeze on 2026-11-09, then bembel. Only bembel-only objects that make no server output (planned prefixes, change requests, bindings, partitions) can be edited in bembel during the parallel run.
  2. Repeat, do not rehearse once. The import runs often: by hand in the first weeks, every night and every 10 minutes in the day during the parallel run. An error in the rules shows on the next day.
  3. Prove with files. The servers do not care about the model. They read files. If the files are equal for 14 nights, the model is right for the servers.
  4. Small steps. DNS and DHCP move in two windows. Inside a window one server moves first.
  5. Go back fast. Until the end of the read-only period, one switch returns the servers to the ONA files.

The import in phase 1 runs from a laptop or a jump host. In phase 2 it runs as a systemd timer on the host of ona-shadow. The timer runs bembel import ona --dump … at 01:31 on the nightly dump, and bembel import ona --dsn … every 10 minutes from 07:02 to 19:52, at the minutes 02, 12, …, 52. Each run has the id imp-YYYYMMDD-HHMM, for example imp-20261104-0912. Only the 01:31 run feeds the nightly diff. The bembel API is in Kubernetes with three replicas (operations.html#ha). The import is a client of the API. bembel records the writes of the timer as the built-in subject system:ona-import, with the origin sync. This subject has fixed rights and no bindings, and it is the only writer of the source ona-import (access.html#source-guard).

Extract

The import reads the ONA database directly with SQL. It does not use dcm.pl for the data. ONA has no list module. Each *_display call returns one object, so a full export would need 100 000 calls. The text output hides raw ids and orphans. The PHP stack may also be broken on PHP 8. dcm.pl only serves for sample checks.

Access

Give bembel a user that can only read. Allow only the address of the import host.

CREATE USER 'bembel_ro'@'10.30.5.20' IDENTIFIED BY '…';
GRANT SELECT ON ona.* TO 'bembel_ro'@'10.30.5.20';

If a direct connection is not possible, take a consistent dump on the ONA host and restore it elsewhere.

mysqldump --single-transaction --skip-lock-tables \
  --default-character-set=binary --hex-blob \
  ona | zstd > /srv/ona-dumps/ona-20261104-0130.sql.zst

bembel import ona --dump FILE restores such a file into a throw-away MariaDB instance that it starts with a temporary data directory (it needs mariadbd in the path). It stops and deletes the instance at the end.

Pre-checks

The first command of a new migration is the check. It reads no data rows beyond counts.

$ bembel import ona --dsn 'mysql://bembel_ro@ona-db.example.org/ona' --check
schema      ona 19.0.3, upgrade_index 15            ok
tables      45 found, 3 unknown (plugin tables)      warn
columns     dns.dns_view_id present                  ok
            dhcp_pools.ip_addr_* INT(10)             ok (IPv4 only)
            subnets.network_role_id absent           ok
            domains.mtime absent (legacy)            ok
charset     tables utf8: 42, latin1: 3               warn  (ona.encoding is likely)
ip columns  DECIMAL(39,0): subnets, interfaces, blocks
sequences   2 tables with seq below MAX(id)          info  (ona.sequence-drift)
contexts    1 database in database_settings.inc.php  ok
guest       disable_guest = 0                        warn

The check does these steps.

  1. Read sys_config.version and upgrade_index.
  2. Compare the columns with the list from install/ona-table_schema.xml of ONA v19.0.3. Each column there is required or optional (legacy). A missing required column stops the check. A missing legacy column is ok. The length checks use the column widths that information_schema.COLUMNS gives for the source database.
  3. Find the table charset. A latin1 table means mixed encodings.
  4. Find tables that the import does not know. They are listed and ignored.
  5. Count the databases ("contexts"). Each database needs its own run.

Zero dates break most database drivers. The reader therefore selects every date as text. It never sets a strict SQL mode. It reads every number column as a string and converts it with a big-integer library.

Sample check against ONA

After the first full run, compare 20 objects by hand with ONA. Use the ONA CLI, not the SQL of the import.

dcm.pl -r host_display host=cn-004.kestrel.example.org verbose=Y format=json
bembel host show cn-004.kestrel.example.org -o json

Both outputs must show the same interfaces, addresses and records. The sample also checks the reader itself.

Import

The CLI reads the ONA data, applies the rules of map-ona.html and sends the result to the API in batches. The server stores an import_run and applies each batch idempotently. A run has the id imp-YYYYMMDD-HHMM. In phase 2 the timer also runs bembel import ona --dsn … every 10 minutes from 07:02 to 19:52, at the minutes 02, 12, …, 52.

Command

bembel import ona --check
bembel import ona --release

Map file

The map file holds what ONA cannot know and the answers to findings. It lives in git, next to the known-differences file. Every change goes through a review.

# map.yaml for the import of ONA at example.org
version: 1
source: ona-import

vrf:                         # ONA has one address space
  - {cidr: 172.16.0.0/16, vrf: oob}
  - {cidr: 10.100.0.0/16, vrf: hpc-fabric}
  - {cidr: 10.110.0.0/16, vrf: hpc-fabric}
  - {cidr: 10.30.0.0/16,  vrf: os-provider}
  - {default: global}

fabric:
  - {cidr: 10.100.0.0/16, fabric: kestrel-ib}
  - {cidr: 10.110.0.0/16, fabric: osprey-roce}

teams:                       # owner by prefix or by domain
  - {cidr: 10.20.0.0/16, team: hpc-ops}
  - {domain: openstack.example.org, team: openstack}

prefixes:                    # containers that ONA never had, or fields that ONA lacks
  - {cidr: 10.20.0.0/16, site: Hall 2}   # ONA block "Hall 2 HPC": adds the site
  - {cidr: 10.110.0.0/16, vrf: hpc-fabric, prefix_kind: container, name: osprey RoCE, site: Hall 2}

hosts:
  host_kind:
    - {match: {model: "KVM guest"}, host_kind: vm, platform: libvirt}
    - {match: {fqdn: '^hv-0[1-6]\.example\.org$'}, host_kind: hypervisor}

views: {DEFAULT: internal}

failover_names: {1: dhcp-a}  # ONA group id to the bembel name

users:   {dklein: d.klein, mhuber: m.huber}
groups:  {Admin: "kc:netops"}
read_all: true

resolve:                     # answers to findings
  - {finding: ona.ipv6-ambiguous, ref: "ona:interfaces:30211", family: v6}
  - {finding: ona.dup-mac, refs: ["ona:interfaces:5120", "ona:interfaces:48802"], keep: first}
encoding:
  interfaces.description: latin1

A prefixes: entry follows these rules (map-ona.html#parent).

  1. An entry whose CIDR and VRF equal a prefix that the import makes from an ONA subnet or block does not make a second prefix. It fills only the fields that ONA lacks (site, team, fabric, the name when it is empty). The object keeps its ref ona:subnets:ID or ona:blocks:ID, and the filled fields go into its row hash.
  2. An entry with no ONA match makes a container with the external ref map:prefixes:CIDR (for example map:prefixes:10.110.0.0/16), the source ona-import and managed_by = ona-import. A re-import finds it by that ref. If you remove the entry, the next run marks the container deprecated.
  3. An entry that overlaps a subnet but does not contain it makes nothing. The import raises ona.map-prefix-overlap (error).

Idempotent re-import

The server finds every object by (source, external_ref). The reference is ona:TABLE:ID, for example ona:hosts:8812. A merged object has a list of refs. The CLI sends with each object a row hash, the hash of the transformed ONA rows that made it. The server decides per object.

CaseActionAudit event
Ref not knownCreate the object.created, subject system:ona-import, origin sync
Ref known, hash equalNothing. The run counts it as unchanged.none
Ref known, hash differsUpdate the fields that the import owns.updated
Ref known, row missing in this runMark the object deprecated. Delete it if it is missing in the next run too.deprecated, deleted
Object edited in bembel by a userNot possible. managed_by = ona-import blocks edits until --release.deny event

A mass-delete guard stops a run that would delete more than 5 % of the objects of a kind. This happens when someone points the import at an empty or wrong database. The run fails with a clear message.

Fields that the import does not own survive a re-import. Tags and attributes that a user adds in bembel (when the map file allows it) stay. The map file key owned_fields lists the exceptions.

Workflow

  1. List the open findings of the last run: bembel import findings list --run imp-20261104-0912 --severity error.
  2. Open one finding. The text names the ONA rows and the suggested fix.
  3. Choose a fix. Either change the row in ONA, or add a rule to the map file, or accept the finding with a reason.
  4. Run the import again. The server closes the findings that are clean now and opens the new ones.
  5. Repeat until no finding of severity error is open without a decision.
$ bembel import findings show f-7c41
f-7c41  ona.dup-mac  warn  open  imp-20261104-0912

accepted by d.klein (audit evt-9a02)

Why fix in ONA first

ONA stays the writer until the cutover. A fix in the map file hides a problem in the import only. A fix in ONA removes it for the users and for the ONA exports too. The map file takes the cases that ONA cannot hold, such as the VRF or a family decision.

Parallel run

The parallel run compares the files that ONA builds with the files that bembel builds. It runs every night in phase 2. It is the main proof for the cutover (dns.html#compat, dhcp.html#compat).

Set-up

  • ona-shadow. A copy of the ONA code and plugins on a scratch host, with a scratch MariaDB. The nightly job restores the dump there. The live ONA is not touched.
  • ONA files. The ONA plugins run in ona-shadow with a changed configuration, so they write to a scratch path and do not reload a service.
  • bembel files. The server builds the files from the imported model in compat mode, for the same five servers.
# /etc/onabase on the ona-shadow host contains /opt/ona-shadow
# /opt/ona-shadow/etc/build_bind.conf  (default file; build_bind exits if it is missing)
DCM_PATH="/opt/ona-shadow/bin/dcm.pl"

# /opt/ona-shadow/etc/build_bind-ns1.conf  (one file per server: ns1, ns2, ns3)
ONA_PATH="/srv/ona-parallel/ns1.example.org"   # zone_data/ below it
SRV_FQDN="ns1.example.org"
DCM_PATH="/opt/ona-shadow/bin/dcm.pl"
CHECKCOMMAND="/bin/true"                        # no check on this host
SYSTEMINIT="/bin/true"                          # never reload

# nightly script
for s in ns1 ns2 ns3; do
  /opt/ona-shadow/bin/build_bind -c /opt/ona-shadow/etc/build_bind-$s.conf -b
done
for s in dhcp1 dhcp2; do
  /opt/ona-shadow/bin/build_dhcpd -s $s.example.org -b -t   # -t: no restart
done

Upstream build_bind v1.6 declares -s without an argument (getopts "c:sbtd"), and the sourced conf overrides SRV_FQDN, so -s cannot select the server. One conf per server, passed with -c, does.

The ONA output is the plugin output. It is named.conf.ona, one file zone_data/named-FQDN for each zone and dhcpd.conf.ona for each DHCP server. The bembel command writes the same names:

$ bembel export bind  --server ns1.example.org  --mode compat-ona --out /srv/bembel-parallel/ns1.example.org
$ bembel export dhcpd --server dhcp1.example.org --mode compat-ona --out /srv/bembel-parallel/dhcp1.example.org

Normalisation

ONA and bembel write dates and serials that change on every build. Both trees pass the same normaliser before the diff.

  1. Replace the build date in the first lines with <DATE>.
  2. Replace the serial in the SOA record with <SERIAL>.
  3. Sort the record lines of a zone. ONA sorts by type only, and the order inside a type is open.
  4. Sort the host blocks of dhcpd by IP address.
  5. Keep the line TOTAL RECORDS (count=N). It is a check by itself.
  6. In strict mode keep the column widths. In loose mode (--loose) fold runs of white space.

Diff levels

LevelComparesFinds
L1Normalised text, byte by byte.Any change. Expected result: no difference.
L2Zones as DNS data: named-compilezone -f text -F text -s full -o - ORIGIN FILE | sort on both trees, then diff of the RRsets. The style full writes the absolute owner name on each line.Format-only differences (order, white space, name case) versus real differences.
L3dhcpd as a model: the tuple sets that the diff tool's dhcpd.conf parser reads from both files. The parser is the Go package dhcpdconf inside bembel export diff. It emits normalised (subnet, pool, option, failover, host) tuples. dhcpd -t -cf FILE and dhcpd -6 -t -cf FILE stay a syntax gate before the comparison.Differences in meaning even when the text differs.

Known differences

Some differences are on purpose, for example the repair of an ONA fault. A known difference is a rule in a file under version control. A line that matches a rule is explained. All other lines are unexplained.

# known-differences.yaml
version: 1
differences:
  - id: KD-001
    title: ONA writes a forward stanza without semicolon
    files: ["*/named.conf.ona"]
    ona:     'file "/.*/named-.*";}'
    bembel: 'file "/.*/named-.*";};?'
    reason: ONA fault. bembel keeps the stanza valid in compat mode.
    owner: m.huber
    added: 2026-10-22
  - id: KD-002
    title: TXT text longer than 255 bytes in UTF-8
    files: ["*/zone_data/named-*"]
    kind: line-changed
    match: {type: TXT, ona_utf8_bytes_gt: 255}   # byte length, evaluated by the diff tool, not a regex
    reason: BIND refuses a string over 255 bytes. bembel splits it into strings of at most 255 bytes, also in compat mode.
    owner: m.huber
    added: 2026-10-20
  - id: KD-003
    title: DHCP host with two options
    files: ["*/dhcpd.conf.ona"]
    kind: line-added-in-bembel
    bembel: '^\s+option (domain-name-servers|ntp-servers) '
    reason: ONA repeats or drops the second option row of a host.
    owner: d.klein
    added: 2026-10-21
    expires: 2026-12-10
  - id: KD-004
    title: Record with a real future ebegin (up to 2038-01-10)
    files: ["*/zone_data/named-*"]
    kind: line-added-in-bembel
    reason: Both systems skip it until the date. The ONA dump is taken a few hours before the build.
    owner: m.huber
    added: 2026-10-22
    expires: 2026-11-09

Each rule has an owner and may have an expiry date. A rule that expires turns its lines into unexplained lines again. The report names the rules that matched nothing for 7 nights, so users can delete them.

Two cases need no rule. A record that ONA disabled (an ebegin after 2038-01-10, map-ona.html#dns) is imported as disabled, so it is absent in both trees. A record in a domain without a server row is folded as disabled for the same reason. A SRV, CNAME, MX or NS target without a final dot comes only from bad data. L2 reports it as unexplained, and the fix belongs in the import, not in this list.

Exit criterion

  • 14 nights in a row with no unexplained line, on all five servers. One unexplained line resets the counter to 0.
  • A line that only a rule added later explains still counted as unexplained on its night.
  • The 14 nights include at least one real change of each kind: add a host, change an IP, delete a host, add a subnet with a pool, change a failover setting, change an option.
  • Two L4 runs pass: one in week 1, one in week 2.
  • The known-differences file is reviewed by m.huber and d.klein.
  • Open findings of severity error: none without a decision.

Today is night 12. Nights 1 to 12 had no unexplained line, so the counter is 12. Before night 1, on the trial night 2026-10-21 to 10-22, a zone differed in 4 lines that nobody had explained. The rule KD-001 and a fix in the compat mode closed the gap before the counter started. Two nights remain.

Report

The nightly job posts the report with POST /v1/parallel-runs. The Overview page shows the counter, the last 14 nights and the open lines. The page links to the files. The same report goes to hostmaster@example.org.

The advisory button Why does the export diff uses the export diff tool. It shows the lines, the matching rule if any, and a suggested cause. It proposes a draft for the known-differences file and does not write it.

Cutover

The cutover moves the writer role and the file source from ONA to bembel. A change request with the approver m.huber covers it (access.html#changes). The agents are already installed in shadow mode. A shadow agent pulls bundles from bembel, checks them, and keeps them, but does not activate them.

Before the windows

  1. Check the exit criterion. The parallel run ends on night 14, 2026-11-06.

SOA serial rule

ONA writes the unix time of the build as the serial. A serial of today is about 1.79 billion. For example, ONA wrote 1793757600 on 2026-11-04 at 02:00 UTC. A counter that starts at 1 would be lower. Secondary servers would then refuse all updates. The native serial scheme is the one of dns.html#serial. The rule at the cutover is:

  1. The import stores the highest ONA serial of each zone as the floor of the zone.
  2. The first native serial is max(YYYYMMDD01, floor + 1).
  3. After that the serial follows dns.html#serial: date based, bumped only on change.
  4. The serial never goes down. The export refuses a lower serial and raises an alert.

The first date serial, for example 2026110901, is about 2.3×108 above the ONA serial. The gap is below 231, so the secondaries accept it as higher. A native serial (~2.03 billion) stays above ONA's Unix-time serial until about 2034. A rollback therefore needs the agent to re-stamp the ONA zones (dns.html#delivery). bembel export bind --check-serial-floor reports per zone the next native serial, the ONA floor, the served serial and the re-stamp value for a rollback. Run it before each window and before a rollback.

Why a rollback re-stamps the serials

A date serial like 2026110901 is larger than today's unix-time serial (about 1.79 billion), so the switch is accepted. The risk is the rollback: ONA's next serial would be lower in RFC 1982 terms, and the secondaries would refuse it. bembel-agent therefore re-stamps every ONA zone on a rollback.

Rollback

A rollback returns the servers to the files of ONA. It does not return the data. ONA is read-only and cannot take new data back.

When to roll back

  • A zone or a DHCP scope gives wrong answers, and no fix is possible in 30 minutes.
  • A DHCP failover pair does not return to normal.
  • The bembel API or database is down and the servers cannot get a bundle for a change that cannot wait.

Procedure

  1. Stop the agent timer on the server: systemctl stop bembel-agent.timer.
  2. Set the source URL back to the ONA files: bembel-agent source set ona-final. The ONA files are the release ona-final, and the ONA web host publishes the newest build under https://ona.example.org/bundles/SERVER/.
  3. Run bembel-agent rollback --to ona-final. The agent checks the files, gives each ONA zone the serial max(ONA serial, served serial + 1), swaps the symlink and reloads. While the source of the agent is ona, it re-stamps every later ONA build in the same way. For DHCP, restart the secondary first, then the primary.
  4. The agent re-stamps the ONA serials (dns.html#delivery). Check that ns1 to ns3 answer the same serial for each zone. If a secondary differs, run rndc retransfer ZONE on it. A secondary that the team does not control needs a manual retransfer by its operator.
  5. Make ONA writable again only if the rollback lasts more than a day: restore the permissions of the web server and the database user.
  6. List what users changed in bembel since the cutover: bembel audit ls --since 2026-11-09T06:00Z --origin ui. Enter these changes by hand in ONA.

No automatic back-sync exists. The ONA schema cannot hold VRFs, views, fabrics or the prefix tree. A generic back-sync would lose data without notice.
