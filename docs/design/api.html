REST API

The REST API is the product. The OpenAPI 3.1 document is reviewed first. The generators make the Go server interfaces, the Go client of the CLI and the TypeScript client of the UI from it. This chapter shows the resource tree, the rules that all endpoints share, full request examples and the CLI.

  • Resource oriented, in the style of the Google AIP: plural collections, standard methods, custom methods with a colon (:allocate).
  • JSON with snake_case fields. Ids are UUIDv7. Addresses and prefixes are strings.
  • Errors are RFC 9457 application/problem+json with stable problem codes.
  • Cursor pagination, strong ETags with If-Match, and an Idempotency-Key on every call that allocates or confirms.
  • Each change makes a CloudEvent through a transactional outbox: SSE for live clients, signed webhooks for the rest.
  • /v1 only gets additive changes. oasdiff in CI blocks a breaking change.

Principles

  1. Spec first. A change starts as a change of api/openapi.yaml. The review looks at the contract. Code follows.
  2. One contract, many clients. The UI, the CLI, the Neutron driver, the CAPI provider, the external-dns webhook and the assistant tools use only this API. No client has a private path.
  3. Server chooses. For allocation the client never reads a free address and then writes it. The client asks for "the next free address". The database arbitrates, so races cannot give one address twice.
  4. Safe to retry. Every write is safe to retry: with Idempotency-Key, with a client chosen name, or with If-Match.
  5. Tell the reason. Each error has a stable code, a readable sentence and, where it helps, the next step.
  6. Permissions in the data. Each object carries allowed_actions. Lists show only what the caller may read (evaluation).

Why not JSON:API or GraphQL

JSON:API adds an envelope, relationship objects and includes. Its code generation in Go and TypeScript is weak. GraphQL makes access checks and caching harder. Plain REST with OpenAPI has the best tool support. Network admins also know it from NetBox.

The tools are: ogen (OpenAPI 3.1 server and client for Go), openapi-typescript with openapi-fetch (UI), and oasdiff (breaking changes). See API first for the build. The coverage of OpenAPI 3.1 features in ogen is not verified for this document. A spike with the sketch is the first task (OpenAPI).

Conventions

Base URL
https://bembel.example.org/v1. The OpenAPI document is at /openapi.yaml.
Format
Content-Type: application/json. Patch bodies are application/merge-patch+json (RFC 7396). No JSON Patch.
Names
Collections are plural and in kebab-case (dhcp-scopes). Fields are in snake_case. Enum values are lower case.
Ids
UUIDv7 (time ordered). Most filters also accept the natural key: ?vrf=global, ?cidr=10.20.4.0/22.
Address data
IPs and CIDRs are strings. IPv6 is in the short form of RFC 5952. A MAC is lower case with colons. Counts that can exceed 64 bits (IPv6) are decimal strings.
Time
RFC 3339 in UTC. Durations are ISO 8601 (PT10M, P7D).
Auth
Authorization: Bearer. See login. A browser session uses the cookie and X-Bembel-Csrf.
Request id
The server returns X-Request-Id (and traceparent). The same id is in logs, audit events and error bodies.
Partial answers
?fields=id,cidr,status limits the fields. ?expand=addresses inlines one level (interfaces of a host).

Examples

The examples use the story data. $BEMBEL_TOKEN holds a token (login). The ids are short for reading.

Allocate the next free address

a.berger asks for the next free address in 10.20.4.0/22 for the new node cn-622 and gives the DNS name and the MAC. This is the call that the Allocate dialog previews. bembel finds or makes the host and the interface, and makes the address, the A and PTR records and (with reservation) the DHCP reservation in one transaction.

The call is safe to repeat (idempotency). The strategy is first (the default), last, random or hint (with hint). range allocates only inside one named range. To take one named address, send "address": "10.20.4.214". If it is taken, the answer is 409 address.conflict with holder. A call with an external_ref that already exists in the source returns the existing address with 200. The call needs address:allocate.

To get several addresses in one call, send POST /v1/prefixes/{id}/addresses:batchAllocate with count (1 to 256), contiguous (default false) and fqdns (one name for each address). The answer is 201 with {"items": [...]}. If the subnet has too few free addresses, the answer is 409 prefix.exhausted; with contiguous it also has longest_free_run.

Claim, confirm and release

A claim holds an address for a limited time. It fits a flow where another system must finish first, such as bembel vm prepare or the Neutron driver. A claim is not a separate resource: it is an address in status claimed with expires_at. The allocate call makes it when the body has claim_ttl (from PT10S up to allocation.max_claim_ttl, 24 hours). With "publish": true the claimed address gets its DNS records and DHCP reservation in the next export (about 30 s); without it, it gets none until the confirm. GET /v1/addresses?status=claimed lists the claims. A claim and a renew need claim:create, a confirm claim:confirm, and the release of a claim claim:release.

# 1. claim for 24 hours in kestrel-services, published for the install
curl -sS -X POST \
  https://bembel.example.org/v1/prefixes/0197c0de-0003-7a00-8000-000000202401/addresses:allocate \
  -H "Authorization: Bearer $BEMBEL_TOKEN" \
  -H "Idempotency-Key: 3d52f0aa-96b1-4a0c-8f0e-77d2c1d0a9e4" \
  -H "Content-Type: application/json" \
  -d '{"claim_ttl": "PT24H", "publish": true,
       "fqdn": "vm-build-07.kestrel.example.org",
       "interface": {"host": "vm-build-07.kestrel.example.org", "name": "eth0",
                     "mac": "52:54:00:5e:3a:b1"}}'
{
  "id": "0197c3c4-0a10-7b00-9e11-1a2b3c4d5e6f",
  "kind": "address",
  "address": "10.20.20.37",
  "status": "claimed",
  "expires_at": "2026-11-05T09:20:00Z",
  "publish": true,
  "fqdn": "vm-build-07.kestrel.example.org",
  "revision": 1
}
# 2. confirm after the domain is defined
curl -sS -X POST https://bembel.example.org/v1/addresses/0197c3c4-0a10-7b00-9e11-1a2b3c4d5e6f:confirm \
  -H "Authorization: Bearer $BEMBEL_TOKEN" \
  -H "Idempotency-Key: 9a1c77e0-0f3e-4b0b-8f64-53a1c1e7d002" \
  -H "Content-Type: application/json" -d '{}'
# 200 OK: the address 10.20.20.37 has status "allocated" and revision 2.
# A second confirm of an allocated address gives 200 and changes nothing.
# After expires_at the reaper deletes an unconfirmed claim. A late confirm gives 409 claim.expired (with expired_at).
# :renew with {"claim_ttl": "PT10M"} extends a claim. A total life over max_claim_ttl gives 422 validation.failed.

# 3. release after the VM is gone; keep the address 7 days as "deprecated"
curl -sS -X POST https://bembel.example.org/v1/addresses/0197c3c4-0a10-7b00-9e11-1a2b3c4d5e6f:release \
  -H "Authorization: Bearer $BEMBEL_TOKEN" \
  -H "Idempotency-Key: c1e9a1d4-52a2-4b7b-9c9a-0d9e2f6a4b11" \
  -H "If-Match: \"2\"" \
  -H "Content-Type: application/json" -d '{"grace": "P7D"}'
# 200 OK: status "deprecated" until deprecated_until. Its DNS records and the reservation leave the export now.
# Without grace, bembel uses allocation.default_release_grace (7 days). "PT0S" frees the address at once.
# The release of a claimed address deletes it at once.

Pagination

A list is a page: {"items": [...], "next_page_token": "..."}. The token is an opaque cursor. It holds the last sort key and the id (keyset), and a hash of the filter. There is no offset, so a page is cheap at any depth and stable when rows change.

curl -sS "https://bembel.example.org/v1/prefixes?within=10.0.0.0/8&page_size=100" -H "Authorization: Bearer $BEMBEL_TOKEN"
# ...
curl -sS "https://bembel.example.org/v1/prefixes?within=10.0.0.0/8&page_size=100&page_token=eyJrIjoiMTAuMjAuNC4wLzIyIiwiaSI6IjAxOTdj..." -H "Authorization: Bearer $BEMBEL_TOKEN"
  • page_size: default 100, maximum 1 000.
  • The token is valid for 24 hours. With another filter or order it gives 400 request.invalid.
  • The last page has "next_page_token": null.
  • There is no total by default, because a count is slow on big sets. ?count=estimate adds total_estimate from the planner. ?count=exact adds total.
  • The access predicate is part of the query, so the pages contain no hole that hidden rows would make.

Concurrency

ETag and If-Match

Each object has a strong ETag. It is the revision. A write that changes or deletes an object needs If-Match. This stops two users from overwriting each other.

CaseAnswer
If-Match equals the current ETagThe change runs. New ETag in the answer.
If-Match differs412 precondition.failed with current_etag. The client reads and merges.
No If-Match on PATCH, PUT, DELETE428 precondition.required
If-Match: *Allowed for DELETE of an object that must exist
If-None-Match: * on createCreate only if the name is new (412 otherwise)
GET with If-None-Match304 when the ETag is equal. The DNS and DHCP agents use this on the bundle of their server (GET /v1/dns-servers/{name}/bundle).
curl -sS -X PATCH https://bembel.example.org/v1/prefixes/0197c0de-0001-7a00-8000-0000000420e4 \
  -H "Authorization: Bearer $BEMBEL_TOKEN" \
  -H "If-Match: \"12\"" \
  -H "Content-Type: application/merge-patch+json" \
  -d '{"description": "kestrel compute nodes, VLAN 204", "tags": {"role": "compute", "gen": null}}'
# In a merge patch, null removes a key.

Idempotency-Key

These calls need the header Idempotency-Key (8–255 characters; a UUID is best): addresses:allocate, addresses:batchAllocate, prefixes:allocate, ranges:allocate and addresses/{id}:confirm. Without the key the answer is 400 request.invalid, and the detail names the header. Every other POST call may send it, also :release and :renew.

  1. bembel computes the SHA-256 of the method, the path and the canonical JSON body. It looks up the key for the caller.
  2. New key: it runs the call and stores the key, the hash, the answer and the ids of the objects that the call created in the same transaction as the change.
  3. Known key, same hash, first call finished: it returns the stored answer with Idempotent-Replayed: true. Nothing runs again.
  4. Known key, other hash: 422 idempotency.mismatch.
  5. Known key, first call still running: bembel waits on the key row. If the first call commits, the retry gets its stored answer. If it rolls back, the retry runs as new. After the lock timeout (5 s) the answer is 409 idempotency.in-progress with Retry-After: 1.

Rules: the key is scoped to the subject. The record lives 24 hours. A 4xx or 5xx answer is not stored, so a retry runs again. A stored answer is valid only while the objects that it created are live: a release, a claim expiry or a delete of such an object also deletes the key rows that point at it, so a later retry runs as a new call and never gets an address that bembel has given back. The allocation chapter shows the table. A controller should also send a stable external_ref (unique per source, with no time limit), so that a lost key does not duplicate work: an allocate with an external_ref that exists returns that address with 200.

Events

Each change writes an outbox row in the same transaction. The row has no order number yet, because transactions commit in a different order than they start. After the commit, a stamper on one replica numbers the committed rows in one short transaction (row lock on a counter, FOR UPDATE SKIP LOCKED). So bembelseq is a gap-free, monotonic order number, assigned after commit. Each sink (the SSE stream, the webhooks) has its own cursor and reads only stamped rows in bembelseq order. A resume with Last-Event-ID or GET /v1/events?after_seq= loses nothing.

The envelope is CloudEvents 1.0 in JSON. The type is org.example.bembel.<kind>.<verb>. The prefix is the reversed domain of the site (events.type_prefix).

SSE stream

GET /v1/events/stream?types=org.example.bembel.address.* keeps the connection open. Each frame has the order number as id. A client that reconnects sends Last-Event-ID and gets the events it missed. When a pod shuts down, it sends retry: 2000 and closes each stream at once, so the client reconnects to another pod with Last-Event-ID. The server sends a comment line every 15 seconds. The stream applies the same read predicate as a list: a client sees only events of objects it may read.

id: 482913
event: bembel
data: {"specversion":"1.0","id":"evt_0197c3a2-5c01-7e00-8b11-4d5e6f708192","type":"org.example.bembel.address.allocated", ... }

A reconnect with an id older than the retention (default 30 days) gets 410 Gone. The client then does a full list.

Webhooks

A webhook is a registered URL that receives events of chosen types. The scheme follows the Standard Webhooks specification.

curl -sS -X POST https://bembel.example.org/v1/webhooks \
  -H "Authorization: Bearer $BEMBEL_TOKEN" -H "Content-Type: application/json" \
  -d '{"url": "https://hooks.example.org/bembel",
       "types": ["org.example.bembel.address.*", "org.example.bembel.export.failed"]}'
# 201: {"id": "...", "secret": "whsec_MfKQ9r8GKYqrTwjUPD8ILPZIo2LaLaSw", ...}  (shown once)
POST /bembel HTTP/1.1
Content-Type: application/cloudevents+json
webhook-id: evt_0197c3a2-5c01-7e00-8b11-4d5e6f708192
webhook-timestamp: 1793783561
webhook-signature: v1,K5oZfzN95Z9UkAYgAt1V0QnCyH3uZ1b2KE8tJc0lYV4=
  • Signature. HMAC-SHA256 over webhook-id "." webhook-timestamp "." body with the secret. The receiver rejects a timestamp older than 5 minutes. The secret can rotate, and both secrets are valid for 24 hours.
  • Success. Any 2xx within 10 seconds.
  • Retries. After a failure, bembel retries 8 times with growing delay: 5 s, 30 s, 2 min, 10 min, 30 min, 2 h, 6 h, 24 h. Then the delivery is failed. After 50 failed deliveries in a row, the endpoint is disabled and an event webhook.disabled goes to the owner.
  • At least once. A receiver uses webhook-id to drop duplicates. Order is by bembelseq; a retry may arrive late.
  • Delivery log. GET /v1/webhooks/{id}/deliveries lists attempts with status code, duration and the first 1 KB of the answer. POST /v1/webhooks/{id}/deliveries/{did}:redeliver sends an event again.
  • Safety. The URL must be https. bembel blocks private ranges unless events.webhook.allow_private lists them.

Versioning

  • The path has the major version: /v1. Inside /v1 bembel only adds: new endpoints, new optional fields, new enum values, new problem codes. A client must ignore unknown fields and handle unknown enum values.
  • A breaking change needs /v2. Both versions run side by side for at least 12 months.
  • oasdiff runs in CI against the OpenAPI document of main. It fails on a removed field, a new required field, a narrowed type or a removed status code. A deliberate break needs the label api-break and a review.
  • A deprecated endpoint or field has deprecated: true in the document and these headers in each answer: Deprecation: @1793750400 (RFC 9745), Sunset: Tue, 04 Nov 2027 00:00:00 GMT (RFC 8594) and Link: <https://dennisklein.github.io/bembel/design/api.html#versioning>; rel="deprecation". The metric bembel_deprecated_calls_total{route} counts the calls of each route. The access log names the subjects that still call it.
  • Server and client versions: GET /v1/me and each answer carry X-Bembel-Version. The CLI warns when the server is older than the client by more than one minor.

Risks to check in the first spike

ogen covers most of OpenAPI 3.1, but not every feature (not verified for this sketch). Check these: path templates with a colon after a parameter (/addresses/{id}:release), type arrays with null, allOf with generic pages, and text/event-stream. If a router limit appears, the fallback is a fixed path like /addresses/{id}/release with the same meaning, decided once for all custom methods.
