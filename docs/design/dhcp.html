DHCP and ISC dhcpd export

bembel holds the DHCP data. ISC dhcpd 4.4.3 on dhcp1.example.org and dhcp2.example.org gives the addresses. This chapter describes the scope, pool, reservation and option model, the failover pair, the IPoIB client identifier, and the dhcpd.conf export. It also describes how bembel-agent installs the file without a service outage and how it sends lease data back.

  • A DHCP scope is the DHCP part of one subnet. A pool is a range with the purpose dhcp-pool. A reservation is an address with an interface MAC or an IPoIB client identifier.
  • An option has four levels: global, server, scope and host. The most specific level wins. A table and a diagram show the rules.
  • A failover pair, for example dhcp-a, writes an ISC failover peer block on both servers and puts the pools in it.
  • DHCPv6 uses a separate file, dhcpd6.conf, for dhcpd -6. ISC dhcpd has no failover for DHCPv6.
  • ISC dhcpd has no reload. bembel-agent restarts one peer at a time, and bembel grants the restart ticket.
  • The agent reads dhcpd.leases for the pool addresses and the dhcpd log for the reservations, and sends last-seen data to bembel. bembel uses it to find stale addresses and wrong client identifiers.
  • ISC DHCP has reached end of life. The model is neutral, so a Kea 3.0 LTS JSON export is a second renderer later.

Scope of the export

The ISC dhcpd export is a v1 requirement of the requester. It also feeds the ONA parallel run. The export does not configure DDNS. Local settings such as authoritative, ddns-update-style and log-facility stay in a header file on the server, as in ONA.

Scopes

A DHCP scope belongs to one subnet. The scope switches DHCP on or off for the subnet, names the DHCP servers, holds the options and refers to the failover pair. The scope names its subnet by prefix_id. It shows the cidr and the vrf of that prefix, read only. An IPv4 subnet and an IPv6 subnet are two prefixes and have two scopes (see fabrics.html#dual-stack).

The API path is /v1/dhcp-scopes/{id}. A user needs dhcp-scope:create, dhcp-scope:update or dhcp-scope:delete in the scope of the subnet. The role dhcp-editor has them.

Rules for a scope:

  • The scope has a router (the subnet gateway) or routers: none. ONA drops a subnet without a router option and writes a warning comment. bembel reports a finding and refuses the export of a scope that has neither. A subnet for IPoIB often has no router, so the explicit none with reachability: attached is the normal case there (reachability).
  • The subnet is in a shared network. All subnets on the same VLAN, or in the same IB partition, go in the same shared-network block. Without a VLAN, the subnet stands alone.
  • All servers of a failover pair have the same scopes. The export writes the same scope to both.
  • One server, and both peers of a pair, serve no overlapping subnets from different VRFs. ISC dhcpd 4.4 has one flat address space and no VSS (RFC 6607). It selects a subnet only by the relay address (giaddr) or the link selection, so it cannot tell two VRFs apart. bembel checks this at write time: a scope create or change, or a change of its servers or failover_pair, that gives one server an overlapping subnet from another VRF gets 409 dhcp-scope.vrf-overlap. The error names both scopes and both VRFs. Overlapping VRFs need separate dhcpd instances or pairs.

Reachability

A client sends DHCPDISCOVER as a broadcast. The broadcast must get to a server. A scope has two ways:

  • relay: the gateway of the subnet forwards the request (ip helper) to the servers of the scope. This is the normal case for Ethernet subnets, for example kestrel-compute on VLAN 204.
  • attached: a DHCP server has an interface in the subnet and gets the broadcast directly. This is the normal case for an IPoIB subnet with routers: none, because no router forwards the request.

The DHCP server object has the field attached_interfaces: a list of {interface, prefix, partition, address}. In the story both servers have the pkey child interface ib0.8001 in kestrel-ipoib:

  • The agent's service config lists the interface: INTERFACESv4="eno1 ib0.8001" in /etc/default/isc-dhcp-server.
  • The OpenSM partition kestrel-ipoib (0x0001) lists the port GUIDs of dhcp1 and dhcp2 (0c42a10300710067, 0c42a10300710068) as full members (fabrics.html#opensm). Without full membership, a limited member cannot reach the server.
  • A scope with routers: none needs at least one attached server in its subnet or partition. Otherwise the export check gives the error finding dhcp-scope-unreachable, and the scope is not exported.

Pools

A DHCP pool is a range of a subnet with the purpose dhcp-pool. The range is part of the addressing model (model.html#addressing). The DHCP scope adds the pool settings: lease times, failover and the bootp rule.

In the story, the subnet kestrel-compute (10.20.4.0/22) has the range 10.20.7.0 to 10.20.7.254 (255 addresses) with the purpose dhcp-pool. The rest of the /22 is static.

Reservations

A reservation gives one address to one client always. bembel makes it from an address that is bound to an interface with a MAC. The address field dhcp has the values reserve (default for an interface with a MAC), none and dynamic. The interface and the address are the data of the host, so a reservation needs no separate object.

  • The export writes a reservation for an address in status allocated, for a reserved address with an FQDN, and for a claimed address only when the claim has publish: true (bembel vm prepare sets it). A deprecated address makes no reservation. Its reservation leaves the export when it becomes deprecated (allocation.html#release).
  • The key of the match is the MAC for Ethernet fabrics, and the client identifier for IPoIB (ipoib).
  • The host stanza name is HOST-INTERFACE, for example cn-004-eno1. ONA names it by the IP address. A host name stays valid after an address change, so native mode uses the host name.
  • The stanza has fixed-address (the address, or the FQDN if the setting dhcp.fixed_address_fqdn is true), the match and the option host-name with the primary FQDN label.
  • An interface with two addresses of one family makes two stanzas only if the client can ask for two. ISC dhcpd gives one address per MAC and subnet. bembel reports a finding when an interface has two reserved addresses in one subnet.
  • A reservation in a shared network is valid on all subnets of the network. bembel writes the host stanza at the top level and uses the address to select the subnet. ISC dhcpd needs the address in a subnet of the network the client sits on.

Options

A DHCP option is a code and a value. The option has four levels. A value at a lower level hides the same option from a higher level.

LevelApplies toWhere bembel writes itExample
GlobalAll servers and all scopesTop of every dhcpd.confdomain-name-servers 10.20.2.53, 10.20.2.54
ServerAll scopes of one serverTop of that server file, after the global optionstime-servers on dhcp1 only
ScopeOne subnetIn the subnet blockrouters 10.20.4.1, interface-mtu 4092
HostOne reservationIn the host stanzahost-name cn-004, next-server for a PXE node

The merge rules are simple.

  • The key of an option is its code (name for the standard options). The same key at a lower level replaces the whole value of the higher level. There is no partial merge of a list.
  • ISC dhcpd has no way to remove an inherited option. v1 has no "unset". The page of the scope shows the options that the scope inherits, and where they come from. To drop a global option for one scope, a user moves it from global to the other scopes.
  • bembel does the merge in the export for the check. It writes each option at its own level. This keeps the file short and lets dhcpd do the inheritance.
  • A value has a type from the option definition. bembel checks the value against the type when a user saves it.

Option definitions

The standard options of dhcpd (routers, domain-name-servers, domain-name, domain-search, ntp-servers, interface-mtu, tftp-server-name, bootfile-name) are known. A site can define an own option by code. The definition has a name, a code, a type and the family. The export writes the definition before it uses the option, as ISC dhcpd requires. Native mode writes a definition only for a real site-defined option, normally a code from 224 to 254 (RFC 3942). Codes from 101 to 223 include standard options such as 119 domain-search and 121 classless-static-routes, which dhcpd knows. The ONA import maps an ONA option with a known code to the standard option (map-ona.html#dhcp-options).

The statements next-server and filename are not options but statements in dhcpd. bembel models them as the pseudo options next-server and filename, and the export writes them as statements. PXE boot on a node uses them at the host level.

Failover

A failover pair is two DHCP servers that share the pools of a scope. ISC dhcpd supports failover for DHCPv4 with a TCP link between the two servers. One server is primary and one is secondary. In the story, the pair dhcp-a has dhcp1.example.org as primary and dhcp2.example.org as secondary.

The pair object has the fields of the ISC failover peer declaration. The defaults come from the ISC example and from the ONA table dhcp_failover_groups.

  • The pools of a scope that names a pair get the failover peer line. The reservations go to both servers.
  • Split or MCLT can differ only in the primary file. The secondary file has neither.
  • The two servers must have the same dhcpd.conf content for scopes, except the peer block and the server options. The export writes one model for both and renders it twice. The check "failover symmetric" compares them.

DHCPv6

ISC dhcpd runs DHCPv6 as a second process: dhcpd -6 -cf /etc/dhcp/dhcpd6.conf. bembel writes a separate file dhcpd6.conf and a separate lease file. The rules differ from IPv4:

  • The scope of an IPv6 subnet becomes a subnet6 block with range6 for each pool.
  • A reservation uses the DUID of the client (host-identifier option dhcp6.client-id). An interface needs a stored DUID. Without a DUID, bembel writes no stanza and shows a finding.
  • ISC dhcpd has no failover for DHCPv6. For a dual-stack subnet, a user has two ways: split the v6 range by hand over two independent servers, or use SLAAC for addresses and DHCPv6 only for options (stateless). bembel warns when a v6 scope names a failover pair.
  • Prefix delegation (prefix6) is later work.
  • SLAAC and EUI-64 addresses are not allocated. bembel only observes them (fabrics.html#dual-stack).
subnet6 2001:db8:4200:204::/64 {
    option dhcp6.name-servers 2001:db8:4200:204::53, 2001:db8:4200:204::54;
    option dhcp6.domain-search "kestrel.example.org";
    range6 2001:db8:4200:204::1000 2001:db8:4200:204::1fff;
}

IPoIB reservations

An IPoIB interface has a 20-byte hardware address. The first 4 bytes hold flags and the queue pair number (QPN). The QPN can change when the interface restarts. The other 16 bytes are the GID: a subnet prefix of 8 bytes and the port GUID of 8 bytes. A MAC match is therefore not stable. ISC dhcpd matches an IPoIB client by the DHCP client identifier (option 61).

bembel stores the port GUID on the IB interface (fabrics.html#guids). It derives the client identifier from the GUID:

client identifier = FABRIC_PREFIX (12 bytes) + port GUID (8 bytes)
default prefix    = ff:00:00:00:00:00:02:00:00:02:c9:00
port GUID cn-004  = 0c42a1030071a2b4
identifier        = ff:00:00:00:00:00:02:00:00:02:c9:00:0c:42:a1:03:00:71:a2:b4

The prefix is a setting of the fabric (ib.client_id_prefix). The default is the value that many NVIDIA OFED setups send. The value depends on the client software and on the subnet prefix. This chapter does not claim that the default is right for each site. A user can replace the full identifier on an interface (dhcp_client_id). The IPoIB subnet has no pool, so dhcpd writes no lease for a wrong identifier. The log ingestion helps to find a wrong prefix: bembel reads the unmatched DHCPDISCOVER lines from ib0.8001 and compares their last 8 bytes with the known GUIDs. A match with a different prefix gives the finding ipoib-client-id-mismatch with the identifier that the client sent. That dhcpd 4.3 and later log the client identifier when the hardware length is 0 is not verified in this record. A site can also add a small quarantine pool to the IPoIB scope (short lease, no routers), whose leases show the identifier that the client sent.

Why not match the GUID alone

A host stanza in ISC dhcpd matches an exact value. A substring test works in a class, but a class cannot assign a fixed address. An exact identifier in the host stanza is the only way to a fixed IPoIB address in ISC dhcpd. The setting for the prefix keeps the exactness without hand work.

The dhcpd.conf export

The command is bembel export dhcpd --server dhcp1.example.org. The output has two files per server: dhcpd.conf.bembel for IPv4 and dhcpd6.conf.bembel for IPv6. The server file /etc/dhcp/dhcpd.conf includes it. The header file with the local settings stays in the server file.

# /etc/dhcp/dhcpd.conf  (written by hand, once)
authoritative;
ddns-update-style none;
log-facility local7;
include "/etc/dhcp/bembel-omapi.key";   # key "bembel-omapi" { algorithm hmac-md5; secret "…"; };
omapi-port 7911;
omapi-key bembel-omapi;
include "/var/lib/bembel-agent/dhcpd/current/dhcpd.conf.bembel";
  • The agent reads the live failover state over OMAPI (delivery). It uses the key only for reads. dhcpd cannot bind OMAPI to localhost only, so the agent installs an nftables rule that accepts tcp/7911 only from 127.0.0.1 and ::1.
  • The agent writes the bundle to /var/lib/bembel-agent/dhcpd/releases/<bundle>/ and swaps the symlink current. dhcpd only reads /var/lib/bembel-agent/dhcpd/current/dhcpd.conf.bembel. The leases stay in /var/lib/dhcp/dhcpd.leases, and dhcpd never needs write access to /var/lib/bembel-agent.
  • The bembel path is outside the distribution defaults. With AppArmor, the agent package adds /var/lib/bembel-agent/dhcpd/** r, to /etc/apparmor.d/local/usr.sbin.dhcpd. With SELinux, the tree gets the context dhcp_etc_t. The agent pre-flight check fails as a deployment error when dhcpd cannot read the tree.

Notes on the file:

  • The order is fixed: definitions, global and server options, failover, shared networks, hosts. ISC dhcpd needs a definition before its use.
  • The host cn-004-ib0 does not use hardware ethernet. It matches by option dhcp-client-identifier. The statement is valid in a host declaration only as an exact value.
  • The IPoIB subnet has no pool in the story. The nodes have reservations. A site can add a pool in the same way.
  • The file for dhcp2 differs in the failover block (secondary;, no mclt, no split, the two addresses swapped) and in the server options. All other blocks are identical.
  • The sort order of subnets is by address. The host stanzas are by host name. The same data gives the same bytes.
  • The comment of each subnet names its VLAN or partition and its VRF. One server serves subnets from two VRFs here (global and hpc-fabric). This is allowed because the subnets do not overlap (scopes).

Delivery

The delivery of the dhcpd export follows the same pull model as the BIND export (dns.html#delivery): GET /v1/dhcp-servers/dhcp1.example.org/bundle with If-None-Match, a signed manifest, a release directory and an atomic symlink swap. The agent never pulls /v1/exports/{id}/artifact; that path is for human download and preview.

The bundle has bundle.tar, manifest.json with "kind": "dhcpd" and "server": "dhcp1.example.org", and manifest.json.sig (Ed25519 over manifest.json). The agent trusts only the signed manifest. It runs the same checks as the DNS agent (dns.html#manifest), in this order: the signature with the key named by key_id; kind and server equal to its own identity; a snapshot not lower than that of the current release; the sha256 of the tar and of each file. A rejected bundle leaves the current release in place and is reported as deploy.bundle-rejected. The signature protects the transport and the ingress path. It does not protect against a compromised bembel pod that holds the key.

Two things differ from DNS.

  1. ISC dhcpd has no reload. A new config needs a restart (systemctl restart isc-dhcp-server on Debian). OMAPI can add a host at run time, but the file and the run time then differ. v1 does not use OMAPI for config. The agent uses OMAPI only to read the failover state.
  2. A restart of both peers at once stops DHCP. The failover pair protects the service only if one server runs.

The restart ticket solves this. The agent that has a new valid config asks bembel for a ticket: POST /v1/dhcp-failover-pairs/dhcp-a/restart-tickets with the body {"server": "dhcp2.example.org"}. The answer is 201 with {id, server, expires_at}. DELETE /v1/dhcp-failover-pairs/dhcp-a/restart-tickets/{id} returns the ticket.

The agent reads the live failover state over OMAPI (export). It reads the failover-state object dhcp-a and needs local-state and partner-state both normal. It also needs systemctl is-active isc-dhcp-server, so a dead process cannot report normal. The agent sends this state in its periodic report and after each restart.

  • bembel grants one ticket at a time for each pair. A second request gets 409 dhcp-failover.ticket-held.
  • bembel grants a ticket only if the agent of the other peer reported, less than 2 minutes ago, both states normal and the process active. Otherwise the request gets 409 dhcp-failover.peer-not-normal.
  • The secondary gets its ticket first when both are waiting. Then the primary goes second.
  • A ticket expires after 10 minutes. A crashed agent does not block the pair.
  • A server without a pair needs no ticket. The agent restarts it at once, in a time window that the admin sets (restart_window: "02:00-04:00"), if the window is set.

After the swap and the restart, the agent reads the failover state over OMAPI again. It waits up to 5 minutes for both states normal. Then it reports the result and returns the ticket. If the state does not become normal, the agent keeps the ticket, reports the error and does not start the peer. It cannot hold the ticket past its expiry of 10 minutes. The user reads the state on the server page. The agent can swap back to the previous release (bembel-agent rollback).

When one peer is down or stays in communications-interrupted, the other peer can never get a normal ticket. A user with dhcp-server:update can then send the request with "override": true. bembel holds the call (202) under the default rule dhcp.restart-override (access.html#changes). The approval screen shows the state of the partner, the MCLT and the impact: a short DHCP outage on the only serving peer, and whether to put the partner in partner-down first. On approval bembel issues the ticket, with expires_at 10 minutes after the approval. The audit log records the override.

The agent keeps the last 5 releases. A change that touches only the other server (for example a server option of dhcp2) does not change the bundle of dhcp1, so dhcp1 does not restart.

Why the server asks bembel

The two agents do not know each other. A central ticket needs no extra link between the servers and no leader election. The state of both peers is in one place, and an operator can see why a restart waits.

Lease ingestion

A lease is a dynamic address that dhcpd gave. dhcpd writes every change as a new block at the end of the file /var/lib/dhcp/dhcpd.leases. The file holds only pool addresses. A host with fixed-address never appears in it, so the agent has two inputs:

  • The lease file. The agent reads it, keeps the last block per address, and sends the data with source: lease and kind: lease.
  • The dhcpd log (journalctl -u isc-dhcp-server or syslog). A line DHCPACK on 10.20.4.44 to 3c:ec:ef:12:0a:44 via … gives last-seen data for a reservation (source: log, kind: ack). A DHCPDISCOVER or DHCPREQUEST line that ends in no free leases or unknown client gives an unmatched client (kind: unmatched).
lease 10.20.7.31 {
  starts 3 2026/11/04 13:02:11;
  ends 3 2026/11/04 21:02:11;
  binding state active;
  hardware ethernet 3c:ec:ef:12:0b:9a;
  uid "\001<\354\357\022\013\232";
  client-hostname "cn-031";
}

  • The agent sends changes only, in batches. It keeps its position in the file and in the log. A restart of the agent re-reads the file and sends a full state.
  • bembel finds the address through the scopes of the reporting server: (server, ip) → scope → prefix → VRF → address, never by the IP alone. The same IP can exist in two VRFs. One server serves no overlapping subnets from different VRFs, so this result is unique.
  • bembel stores last_seen_at, last_seen_mac, last_seen_client_id and last_seen_source on the address. The data is an observation, not a claim. A lease does not create an address in the allocated state.
  • bembel limits the writes: one update per address in 15 minutes. A renewal does not make a change event.
  • Each lease and each DHCPACK is also an observation with the method lease or dhcp-ack. Other sources (ARP, ICMP sweep, nmap, VPN sessions) add to the same data (observations).
  • With a failover pair, bembel merges the reports of both servers. The later ends wins.

Kea later

ISC DHCP has reached end of life. Kea is the successor. Kea 3.0 is the first long-term support release (July 2025). The DHCP model of bembel is neutral on purpose: scope, pool, option, reservation and failover pair do not depend on ISC syntax. A Kea renderer is a second output and an extra DHCP server kind. The facts below come from public sources and from the research notes. Several are not verified in this sandbox.

ItemDesign
Config exportbembel export kea writes kea-dhcp4.conf and kea-dhcp6.conf as JSON. The check is kea-dhcp4 -t FILE. The agent applies it with the control command config-reload. There is no restart.
ReservationsFew reservations: inline in the JSON. Many reservations: write them into the Kea host database (PostgreSQL), or send them with the host_cmds hook. The database approach is better with more than about 10 000 reservations. It ties bembel to the Kea schema version.
High availabilityThe libdhcp_ha.so hook replaces the ISC failover peer. The failover pair maps to a high-availability relationship (hot standby or load balancing). The two protocols are not compatible. A cutover must not mix ISC peers and Kea HA.
Config backendThe Kea config backend (cb_cmds) is a commercial hook. bembel does not use it.
LeasesThe agent or bembel reads the Kea lease database (PostgreSQL lease4 and lease6), or calls the lease4-get-page command. The result goes through the same ingestion API.
IPoIBA reservation by client-id. The same stored identifier is the source.
MigrationThe ISC tool keama converts dhcpd.conf to Kea JSON. bembel runs it on the ONA file and on its own dhcpd export. It compares the sets of subnets, pools, options and reservations with the Kea output of bembel. It is a second opinion and not an input.
