Roadmap

This chapter orders the work. v1 replaces OpenNetAdmin and gives the base for all later integrations. v1.1 and v2 add the integrations for Kubernetes, OpenStack, DNS and policy. Each release has a scope and exit criteria. The last sections list the open questions and the sources.

  • v1: core model, REST API, web UI, OIDC access, BIND, dhcpd and OpenSM exports, ONA import and parallel run, FNT asset mirror, libvirt agent, help, read-only assistant, HA deployment on Kubernetes, metrics and logs.
  • v1.1: Cluster API provider, Terraform provider, load-balancer pool sync, read-only OpenStack sync, Kea export, catalog zones, address group feeds.
  • v2: Neutron IPAM driver, external-dns webhook, RFC 2136 and PowerDNS delivery, deny rules with Cedar, NetBox exchange.
  • The order follows the risk. The cutover from ONA comes first, because ONA is the thing that must go. Integrations that write into other systems come last.
  • The roadmap gives phases and exit criteria, not calendar dates. A phase ends when its exit criteria hold.

Timeline

Entry criteria of the M4 cutover

The cutover from ONA starts only when these criteria hold. They come from the v1 exit criteria, but they must hold before the cutover, not only at the release.

  1. HA works. First check the placement: one bembel pod and one PostgreSQL instance per zone. Then the kill tests of one pod, one zone and the PostgreSQL primary pass (Operations).
  2. Restore works. One point-in-time restore drill into a new cluster passes (Operations).
  3. Alerts are tested. The alerts BembelReplicasLow, BembelExportStale, BembelExportNotPulled and BembelOutboxLag have passing promtool tests (Operations).

The CloudNativePG image contains pgvector from M3, so the first production cluster needs no image change later.

Why the cutover is in the middle

The parallel run needs the exports (M3) and the import (M4), and nothing else. It starts as early as possible and lasts for weeks. So the later milestones (FNT, agent, assistant, routing) develop while the real data already flows through bembel. Problems in the model show up when the change is still cheap. The cutover itself also needs HA, backup and alerts, so these come in M3 with the exports, not at the end.

v2

v2 adds the parts where bembel becomes a dependency of another system, so a bug has a larger effect, and the policy extension.

ItemScopeExit criteria

external-dns webhook providerA webhook provider so that external-dns writes manual records for Services and Ingresses into owned zones.Records of one cluster appear and disappear with the Service. Ownership by managed_by stops a clash with humans.

Deny rules with CedarOptional deny policies on top of the allow-only bindings. Policy test tool.The evaluation of lists still uses the SQL filter. A policy change can be tried in a dry run on the audit log.

Not planned: a CNI IPAM plugin. The latency and availability needs at pod start do not fit a central service (Kubernetes). Also not planned: write back to FNT Command, a DHCP server or DNS server inside bembel, and a firewall or router config manager.
