Exports and delivery

bembel builds a signed bundle for each server. bembel-agent on the server pulls it, checks it and installs it. This chapter specifies the delivery for the BIND, dhcpd and OpenSM exports, with BIND as the worked example.

Delivery

A server pulls its bundle. The pull works through firewalls, and the server keeps its last good state when bembel is down.

Bundle and trust

PartContent
bundle.tarThe files for the server (files in a BIND bundle).
manifest.jsonThe kind, the server, the snapshot, the key_id, and the sha256 of bundle.tar and of every file (BIND manifest).
manifest.json.sigA detached signature, Ed25519 over manifest.json.

The manifest holds the hashes, so the signature covers all parts. The agent trusts only the signed manifest. The key pair belongs to the installation.

SideSetting
bembel serverexports.signing: {key_id: bembel-2026-1, key_file: /run/secrets/export-signing-key}
Agenttrust.keys: [{id: bembel-2026-1, public_key_file: /etc/bembel/keys/bembel-2026-1.pub}]

Trusted keys

The agent config lists the trusted public keys: up to two during a key rotation (operations.html#security).

The signature protects the transport and the ingress path. It does not protect against a compromised bembel pod that holds the signing key.

Agents and kinds

The BIND, dhcpd and OpenSM agents use the same pipeline. They differ in the identity, the pull path and the action after the swap.

KindPull path or targetIdentity in the manifestAfter the swap
bindGET /v1/dns-servers/ns1.example.org/bundlekind bind, server ns1.example.orgrndc reconfig and rndc reload (BIND on the server)
dhcpdGET /v1/dhcp-servers/dhcp1.example.org/bundlekind dhcpd, server dhcp1.example.orgA restart, after a restart ticket (dhcp.html#delivery)
opensmThe subnet manager object of the fabric, /v1/fabrics/kestrel-ib/subnet-managerskind opensm, server the name of its subnet managerA hang-up signal to OpenSM, which reads the file again (fabrics.html#opensm)

The agent never pulls /v1/exports/{id}/artifact. That path is for human download and preview.

Agent steps

The agent works in these steps. The example values are those of ns1.

  1. Pull. Every 60 seconds (with jitter) the agent calls GET /v1/dns-servers/ns1.example.org/bundle. The request has the header If-None-Match and the bearer token of the agent. bembel answers 304 when the ETag is the same (api.html#concurrency).
  2. Verify. On 200 the agent saves the three parts and makes the checks of the verify table, in this order.
  3. Unpack and check. The agent unpacks the bundle to /var/lib/bembel-agent/bind/releases/b-9e2d41/ and runs the checks of the kind on a check copy (BIND).
  4. Install and swap. If the checks pass, the agent installs the changed files. Then it replaces the symlink current with a new symlink through rename(2). Both steps are atomic.
  5. Reload. The agent makes the service read the new files (the last column of the kinds table).
  6. Report. The agent sends the status to POST /v1/dns-servers/ns1.example.org/deployments: the bundle id, the time and the result.
  7. Prune. The agent keeps the last 5 releases and the release ona-final, and removes older ones.

Checks of the agent

The agent makes these checks in this order. They are the same for the BIND, dhcpd and OpenSM kinds. A refused bundle changes nothing: the current release stays. The agent reports deploy.bundle-rejected and counts it in bembel_agent_bundle_rejected_total{reason}.

OrderCheckReason label
1The signature of manifest.json is valid with the trusted key that key_id names.signature
2kind and server are equal to the identity in the agent config (bind, ns1.example.org). A bundle for another server is refused.identity
3snapshot is not lower than the snapshot of the current release. An older bundle is refused.rollback
4The sha256 of bundle.tar and of each file is equal to the manifest.hash

A pin is a newer bundle (rollback and pin), so check 3 has no exception. Only the local command bembel-agent rollback overrides it.

BIND on the server

For the BIND kind, the agent does these things in steps 3 to 6.

StepAction
3 Check copyThe agent writes a check copy to releases/b-9e2d41/.check/. In the copy, the prefix /var/lib/bembel-agent/bind/current/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/.
3 Check copyThe prefix /var/lib/bind/bembel/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/zones/. The agent verifies that each rewritten file differs only in these prefixes.
3 Confignamed-checkconf -z runs on a copy of /etc/bind/named.conf. The bembel include of the copy points at releases/b-9e2d41/.check/named.conf.bembel.
3 Zonesnamed-checkzone runs with the flags of step 2 of the export checks on releases/b-9e2d41/zones/<view>/<zone>.zone for each changed zone.
3 ResultThe checks read the new release, not the release behind current. The sandbox on the bembel side does the same with its unpack directory.
4 Zone filesFor each changed zone, the agent writes a temporary file in /var/lib/bind/bembel/<view>/, calls fsync and renames it with rename(2). This is atomic.
5 ReloadThe agent compares the manifest with the one of the last release. If config_changed is true, it runs rndc reconfig. For each zone with changed: true it runs rndc reload ZONE in VIEW.
6 ReportThe status holds the result per zone and the serial that named answers.

Paths on the server

PathOwner and use
/var/lib/bembel-agent/bind/releases/<bundle>/The agent. One directory per release, the staging area. The agent keeps the last 5 and ona-final.
/var/lib/bembel-agent/bind/currentThe agent. A symlink to releases/<bundle>. named reads only named.conf.bembel, acls.conf and views/*.conf through it.
/var/lib/bind/bembel/<view>/<zone>.zoneThe zone files. Directory root:bind, mode 2775. The agent user is in the group bind. Every generated file statement uses this stable path, the DNSSEC stanza too.
/var/lib/bind/bembel/<view>/<zone>.zone.jnl, .signed, .signed.jnlnamed. The journal of ixfr-from-differences and the files of inline signing stay over bundles. The agent removes them only when the zone leaves the bundle.
/etc/bind/bembel-tsig.confThe administrator. The TSIG keys of the views.
  • named never needs write access to /var/lib/bembel-agent.
  • On Debian and Ubuntu the AppArmor profile of named allows /var/lib/bind/** already. The agent adds the line /var/lib/bembel-agent/bind/** r, to /etc/apparmor.d/local/usr.sbin.named.
  • With SELinux the config tree has the type named_conf_t and the zone directory named_cache_t.
  • A pre-flight check at agent start makes sure that the user bind can write /var/lib/bind/bembel/ and read the config tree. A failure is a deployment error.

Rollback and pin

If a step from 3 to 5 fails, the agent keeps the old symlink (or swaps back to the previous release) and reports the error. This swap back during a failed apply, before any reload, needs no new serial, because no server saw the new serial.

Why other rollbacks move the serial up

An older release holds lower serials. If ns1 loaded them, ns2 and ns3 would keep the newer, bad data with no time limit. The zone does not expire, because ns1 still answers their SOA queries. So all other rollbacks bring the content back and move the serial up.

CaseCommandWhat happens
PinPUT /v1/dns-servers/ns1.example.org/pin with {"bundle": "b-5e08c3", "reason": "…"}. Needs export:build.bembel builds a new bundle (new id, new snapshot, new ETag) with the zone bodies of the named bundle. See the pin rules below.
Lift the pinDELETE /v1/dns-servers/ns1.example.org/pinThe answer is 204. The next export uses a serial above the stamped one.
Local emergency rollbackbembel-agent rollback --to b-5e08c3Works without bembel, from the local releases. The agent installs the zone content of that release and rewrites the SOA serial of each changed zone to the served serial plus one. It runs named-checkzone, swaps and reloads.
Report of a local rollbackPOST /v1/dns-servers/ns1.example.org/deploymentsThe agent reports the new serials. bembel raises its stored serial.
Rollback to ONAbembel-agent rollback --to ona-finalEach ONA zone gets the serial max(ONA serial, served serial + 1). While the source of the agent is ona, it re-stamps every later ONA build in the same way. No RFC 1982 reset is needed.

The pin rules:

  • Each zone whose body differs gets the serial max(highest serial that bembel published for this zone and view, highest served serial) + 1.
  • The bundle goes through the normal checks (export checks), step 4 too.
  • While the pin is set, data changes do not change the bundle of this server.
  • A pin holds a server on known good content while a fix is made.

Deployment report and drift view

The deployment status gives a drift view. The server page in the UI shows these values for each server:

  • the bundle id;
  • the age of the last pull;
  • the serial per zone that the server answers, against the serial that bembel expects.

The metric bembel_export_last_pull_timestamp_seconds has the alert rule BembelExportNotPulled (operations.html#alerts).

Why pull and not push

A pull needs no inbound firewall rule on the DNS servers. The agent can run on a server that bembel cannot reach. A broken bembel leaves the servers with the last good bundle. The ONA script wrote files in place and checked them afterwards, so a bad zone was already live on disk. The agent checks first and swaps after.
