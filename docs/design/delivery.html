Exports and delivery

bembel builds a signed bundle for each server. bembel-agent on the server pulls it, checks it and installs it. This chapter specifies the delivery for the BIND, dhcpd and OpenSM exports.

Delivery

A DNS server pulls its bundle. The pull works through firewalls, and the server keeps its last good state when bembel is down. A bundle has three parts: bundle.tar, manifest.json and a detached signature manifest.json.sig (Ed25519 over manifest.json). The manifest holds the sha256 of bundle.tar and of every file, so the signature covers all parts. The key pair belongs to the installation. The server config names the signing key (exports.signing: {key_id: bembel-2026-1, key_file: /run/secrets/export-signing-key}). The agent config lists the trusted public keys (trust.keys: [{id: bembel-2026-1, public_key_file: /etc/bembel/keys/bembel-2026-1.pub}]), up to two during a key rotation (operations.html#security).

The agent works in these steps.

  1. Every 60 seconds (with jitter) the agent calls GET /v1/dns-servers/ns1.example.org/bundle with the header If-None-Match and its bearer token. bembel answers 304 when the ETag is the same.
  2. On 200 the agent saves the three parts and makes these checks, in this order:
    1. The signature of manifest.json is valid with the trusted key that key_id names.
    2. kind and server are equal to the identity in the agent config (bind, ns1.example.org). A bundle for another server is refused.
    3. snapshot is not lower than the snapshot of the current release. An older bundle is refused. A pin is a newer bundle (see below), so this rule has no exception. Only the local command bembel-agent rollback overrides it.
    4. The sha256 of bundle.tar and of each file is equal to the manifest.
    A refused bundle changes nothing: the current release stays. The agent reports deploy.bundle-rejected and counts it in bembel_agent_bundle_rejected_total{reason} (signature, identity, rollback, hash).
  3. The agent unpacks the bundle to /var/lib/bembel-agent/bind/releases/b-9e2d41/. It writes a check copy to releases/b-9e2d41/.check/. In the check copy, the path prefix /var/lib/bembel-agent/bind/current/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/, and /var/lib/bind/bembel/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/zones/. The agent verifies that each rewritten file differs only in these prefixes. Then it runs named-checkconf -z on a copy of /etc/bind/named.conf whose bembel include points at releases/b-9e2d41/.check/named.conf.bembel, and named-checkzone with the flags of step 2 of the checks on releases/b-9e2d41/zones/<view>/<zone>.zone for each changed zone. So the checks read the new release, not the release behind current. The sandbox on the bembel side does the same with its unpack directory.
  4. If the checks pass, the agent installs each changed zone file into /var/lib/bind/bembel/<view>/: it writes a temporary file in the same directory, calls fsync and renames it with rename(2). Then it replaces the symlink current with a new symlink through rename(2). Both steps are atomic.
  5. The agent compares the manifest with the one of the last release. If config_changed is true, it runs rndc reconfig. For each zone with changed: true it runs rndc reload ZONE in VIEW.
  6. The agent sends the status to POST /v1/dns-servers/ns1.example.org/deployments: the bundle id, the time, the result per zone and the serial that named answers.
  7. The agent keeps the last 5 releases and the release ona-final, and removes older ones.

The signature protects the transport and the ingress path. It does not protect against a compromised bembel pod that holds the signing key. The same checks apply to the dhcpd and OpenSM bundles (dhcp.html#delivery, fabrics.html#opensm).

Paths on the server

PathOwner and use
/var/lib/bembel-agent/bind/releases/<bundle>/The agent. One directory per release, the staging area. The agent keeps the last 5 and ona-final.
/var/lib/bembel-agent/bind/currentThe agent. A symlink to releases/<bundle>. named reads only named.conf.bembel, acls.conf and views/*.conf through it.
/var/lib/bind/bembel/<view>/<zone>.zoneThe zone files. Directory root:bind, mode 2775. The agent user is in the group bind. Every generated file statement uses this stable path, the DNSSEC stanza too.
/var/lib/bind/bembel/<view>/<zone>.zone.jnl, .signed, .signed.jnlnamed. The journal of ixfr-from-differences and the files of inline signing stay over bundles. The agent removes them only when the zone leaves the bundle.
/etc/bind/bembel-tsig.confThe administrator. The TSIG keys of the views.

named never needs write access to /var/lib/bembel-agent. On Debian and Ubuntu the AppArmor profile of named allows /var/lib/bind/** already. The agent adds the line /var/lib/bembel-agent/bind/** r, to /etc/apparmor.d/local/usr.sbin.named. With SELinux the config tree has the type named_conf_t and the zone directory named_cache_t. A pre-flight check at agent start makes sure that the user bind can write /var/lib/bind/bembel/ and read the config tree. A failure is a deployment error.

Rollback and pin

If a step from 3 to 5 fails, the agent keeps the old symlink (or swaps back to the previous release) and reports the error. This swap back during a failed apply, before any reload, needs no new serial, because no server saw the new serial.

All other rollbacks bring the content back and move the serial up. An older release holds lower serials. If ns1 loaded them, ns2 and ns3 would keep the newer, bad data with no time limit: the zone does not expire, because ns1 still answers their SOA queries.

  • Pin. PUT /v1/dns-servers/ns1.example.org/pin with {"bundle": "b-5e08c3", "reason": "…"} needs export:build. bembel builds a new bundle (new id, new snapshot, new ETag) with the zone bodies of the named bundle. Each zone whose body differs gets the serial max(highest serial that bembel published for this zone and view, highest served serial) + 1. The bundle goes through the normal checks, step 4 too. While the pin is set, data changes do not change the bundle of this server. DELETE /v1/dns-servers/ns1.example.org/pin lifts it (204). The next export uses a serial above the stamped one. This is the way to hold a server on known good content while a fix is made.
  • Local emergency rollback. bembel-agent rollback --to b-5e08c3 works without bembel, from the local releases. The agent installs the zone content of that release and rewrites the SOA serial of each changed zone to the served serial plus one. It runs named-checkzone, swaps and reloads. Then it reports the new serials in POST /v1/dns-servers/ns1.example.org/deployments, and bembel raises its stored serial.
  • Rollback to ONA. bembel-agent rollback --to ona-final gives each ONA zone the serial max(ONA serial, served serial + 1). While the source of the agent is ona, it re-stamps every later ONA build in the same way. No RFC 1982 reset is needed.

The deployment status gives a drift view. The server page in the UI shows the bundle id of each server, the age of the last pull, and the serial per zone that the server answers against the serial that bembel expects. The metric bembel_export_last_pull_timestamp_seconds has the alert rule BembelExportNotPulled (operations.html#alerts).

Why pull and not push

A pull needs no inbound firewall rule on the DNS servers. The agent can run on a server that bembel cannot reach. A broken bembel leaves the servers with the last good bundle. The ONA script wrote files in place and checked them afterwards, so a bad zone was already live on disk. The agent checks first and swaps after.
