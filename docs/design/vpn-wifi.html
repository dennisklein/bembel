VPN and Wi-Fi

This chapter specifies how bembel serves remote access and wireless access. In both cases a server outside bembel gives the client addresses: the eduVPN node or the DHCP server of the Wi-Fi. bembel owns the space, the pools, the names of the infrastructure, and the record of who had which address.

  • A VPN profile is one eduVPN profile or one WireGuard server. Its subnets have a range of the purpose vpn-pool. Allocation never takes an address from such a range.
  • GET /v1/vpn-profiles/{id}/config?format=eduvpn gives the range keys of the profile (wRangeFour, oRangeSix and the rest). The config management of the VPN nodes writes them into config.php. bembel does not write files on the node.
  • The script connection hook of eduVPN sends each connect and disconnect to the bembel-agent on the node. The agent writes VPN sessions to bembel. The hook always exits 0: a bembel outage never blocks a VPN connection.
  • The agent compares the sessions with the admin API of eduVPN every 5 minutes. A lost event becomes a corrected session, not a hole in the record.
  • A VPN session answers "who had 10.40.0.17 at 14:02". It is personal data: it needs vpn-session:read, bembel keeps it 90 days, and each read is in the audit log.
  • A plain WireGuard server uses normal allocation. Each peer has an address and an interface with its public key. bembel never holds a private key.
  • Wi-Fi needs no new kind. Each SSID has one VLAN, one subnet and a DHCP scope for the clients. The access points are hosts of the kind appliance. A sync mirrors the access points and the active clients from ExtremeCloud IQ, read only.

eduVPN

eduVPN is the VPN server of many universities and research sites. One portal (vpn-user-portal) has profiles. Each profile runs on one or more nodes, with WireGuard, OpenVPN or both.

eduVPN gives each client an address from the range of its profile, node and protocol, and takes it back at the disconnect. bembel does not allocate these addresses. It gives eduVPN the ranges and records what eduVPN did.

VPN profiles

The story has one eduVPN portal on two nodes, vpn-01.example.org and vpn-02.example.org. The container 10.40.0.0/16 (twin 2001:db8:4200:400::/56) in VRF global holds all VPN subnets. Each subnet is one range of eduVPN and has one range of the purpose vpn-pool that covers it.

  • A VPN profile has a kind (eduvpn or wireguard) and a profile_id (the eduVPN profileId). It also has a display name, the host name of the service, the DNS settings and an owner team.
  • The pools of a profile are a list of (node host, protocol, subnet).
  • The eduVPN rule is that the ranges of all profiles and nodes are unique and do not overlap. bembel tests the same rule in the database: a pool is a subnet, and subnets do not overlap.
  • The route list can name prefixes or an address group. bembel resolves the group at each export, so a new HPC subnet goes to the hpc profile without an edit of the profile.
  • The DNS servers come from the resolvers of the site (10.20.2.53 and 10.20.2.54). A change of a resolver changes the profile export.
  • The ACL permission is a value for eduVPN (aclPermissionList). eduVPN tests it against the attributes of the IdP. bembel does not evaluate it.

The keys are the keys of the eduVPN ProfileList. An Ansible template writes them into /etc/vpn-user-portal/config.php and runs vpn-maint-apply-changes, which applies the change to the VPN daemons. bembel does not write the file, because the file also holds keys and settings that bembel does not own.

A pool change needs a drain

eduVPN keeps the address of a connected client. A smaller or moved pool can leave a client outside the new range. bembel refuses a change of a pool with active sessions outside the new CIDR (409 vpn.pool-in-use), unless the call has "drain": true. A drain is a change request: the approver sees the count of sessions that end.

The connection hook

eduVPN runs a script at each connect and disconnect when connectScriptPath is set. The script gets the event in environment variables: VPN_EVENT (C or D), VPN_PROTO, VPN_IP_FOUR, VPN_IP_SIX, VPN_CONNECTION_ID, the profile, and the user id. A non-zero exit code makes eduVPN refuse the connection. The bembel package installs the script /usr/lib/bembel-agent/eduvpn-hook.

  1. The script writes the variables as one JSON line to /run/bembel-agent/vpn.sock, with a timeout of 1 second.
  2. The script exits 0 in all cases, also when the socket does not answer. bembel records access. It never decides access.
  3. The agent writes the event to a queue on disk (/var/lib/bembel-agent/vpn-queue), so a restart loses nothing.
  4. The agent sends the queue in batches with POST /v1/vpn-sessions:batch, at most every 5 seconds. A connect starts a session. A disconnect ends the session with the same connection id.
  5. bembel also writes an observation with the method vpn for each connect. An address in a vpn-pool range gives no finding address.unknown-seen.
# /etc/vpn-user-portal/config.php (part)
'connectScriptPath' => '/usr/lib/bembel-agent/eduvpn-hook',

# /etc/bembel-agent/agent.yaml (part)
eduvpn:
  node: vpn-01.example.org
  admin_api: https://vpn.example.org/vpn-user-portal/admin/api/v1/
  admin_token_file: /etc/bembel-agent/eduvpn-admin.token
  reconcile_interval: 5m

Reconcile

A hook event can get lost: the agent was down, or the node restarted during a disconnect. Every 5 minutes the agent reads connection_list of the eduVPN admin API with show_all (eduVPN 3.10 or later). It compares the list with the open sessions of its node in bembel.

CaseResult
A connection is in the list, but bembel has no open sessionThe agent starts a session with started_at from the list and the flag late: true
bembel has an open session, but the connection is not in the listThe agent ends the session with ended_at set to the time of the read and end_reason: reconcile
A connection has an address outside all pools of the profile and nodeThe finding vpn.address-outside-pool: the config.php of the node differs from bembel
The admin API does not answer for 30 minutesThe alert BembelVpnReconcileFailing

The admin token of eduVPN lets the agent read connections and also delete them. The agent never deletes a connection. The token file is readable only by the agent user.

VPN sessions

A VPN session is one row for each connection: profile, node, protocol, user id, connection id, IPv4 address, IPv6 address, start, end, end reason. With originatingIp on (OpenVPN only), it also has the public address of the client.

$ bembel vpn session ls --address 10.40.0.17 --at 2026-11-04T14:02:00Z
PROFILE  NODE    PROTO      USER                 IPV4         IPV6                    START             END
staff    vpn-01  wireguard  m.huber@example.org  10.40.0.17   2001:db8:4200:400::11   2026-11-04 13:41  2026-11-04 15:07
1 session (read recorded in the audit log)
  • The question has an exact answer. eduVPN gives an address to one client at a time, and a session has a start and an end. An overlap of two sessions with the same address is a finding vpn.session-overlap.
  • vpn-session:read is not in *:read and not in viewer. The story gives it to the group kc:netsec with global scope. network-admin also holds it.
  • Each read of a session is an audit event with the filter of the query. The audit log thus shows who looked up whom.
  • The reaper deletes a session 90 days after its end (vpn.session_retention). This value must agree with the data protection rules of the site. bembel keeps no session longer, also not in the history tables.
  • The address page of a client address shows only the count of sessions to a user without vpn-session:read.

Plain WireGuard

Some links use WireGuard without eduVPN: an admin access server or a link to a remote site. Here no server gives addresses. Each peer has a fixed address, so bembel allocates it like any other address.

  • A VPN profile of the kind wireguard names the server host (wg-01.example.org), its interface wg0 and one subnet (10.40.32.0/24, twin 2001:db8:4200:420::/64). The subnet has no vpn-pool range.
  • A peer is a host with a WireGuard interface. The interface has no MAC. It has wg_public_key and the allocated addresses. bembel does not hold the private key or a preshared key.
  • GET /v1/vpn-profiles/ops-wg/config?format=wg-quick gives the [Peer] sections for the server: PublicKey and AllowedIPs of each peer. The config management adds the [Interface] section with the private key from its secret store.
  • The derived records name each peer, for example oob-gw-hall3.wg.example.org. So a tunnel address in a log has a name.
# GET /v1/vpn-profiles/ops-wg/config?format=wg-quick  (revision 4)
[Peer]
# oob-gw-hall3.wg.example.org
PublicKey = 0k3mXr7vQ2b9cY1sJfH5aWn8tLpR4dEuGzKiVoNqB2M=
AllowedIPs = 10.40.32.11/32, 2001:db8:4200:420::11/128, 172.16.40.0/22

The route of a site behind a peer (here 172.16.40.0/22) comes from a static route of the peer in bembel (routing).

Wi-Fi

A Wi-Fi network needs no new object kind. Everything in the table below is an object of the model already.

ValueObject in bembelRule
SSIDTag ssid=eduroam on the VLANThe SSID name only. Its settings stay in the Wi-Fi management.
Client networkVLAN, subnet pair, DHCP scopeA pool of the purpose dhcp-pool covers most of the subnet, and the lease time is short. A Wi-Fi subnet is large and its use changes during the day. The utilisation alert uses the peak of the day.
Access pointHost of the kind appliance, tag role=wifi-apOne interface with the MAC, one address in wlan-mgmt with a DHCP reservation, the name ap-h2-01.example.org
PlaceAsset link to an FNT room or floorAn access point is often not a rack device. The link to the room is enough.
RADIUS clientsAddress group wlan-ap (tag role=wifi-ap)The feed /v1/feeds/wlan-ap?format=text gives the client list of the RADIUS server.
Guest isolationAddress group wlan-guestThe firewall feed blocks the guest subnet from the internal prefixes.

The lease ingestion of the DHCP servers gives the active Wi-Fi clients. The pool utilisation and its alert work as for any other scope (DHCP leases).

ExtremeCloud IQ mirror

The access points of the site are managed in ExtremeCloud IQ (XIQ). XIQ is the cloud product that was earlier named HiveManager NG. The old local HiveManager Classic is no longer sold, and its developer API is closed. bembel uses only the public XIQ REST API at api.extremecloudiq.com with an API token.

  • The sync worker system:sync-xiq reads the device list every 15 minutes. Each access point becomes or updates a host with source=xiq: host name, serial number, model, MAC and management address. The address must be in a subnet of bembel. If not, the result is the finding xiq.address-outside.
  • The match key is the MAC. An access point that bembel already has with a reservation keeps its address. The sync only fills the fields of XIQ.
  • The sync reads GET /clients/active and writes observations with the method sync: client MAC, address, SSID and access point. Thus the last-seen data of a Wi-Fi client has the access point, which the DHCP lease does not give.
  • The location tree of XIQ (site, building, floor) maps by name to the FNT mirror. A name without a match is the finding xiq.location-unmatched. Users then set the asset link by hand.
  • The mirror is read only. bembel never writes to XIQ. The API paths other than /clients/active need a test against the XIQ tenant of the site (open questions).

Example

  1. d.klein makes the container 10.40.0.0/16 and allocates the subnets of the profile staff from it: bembel prefix allocate 10.40.0.0/16 --length 22 --name vpn-staff-wg-01, and so on. Each subnet gets a range of the purpose vpn-pool.
  2. d.klein makes the VPN profile staff with the four pools and the DNS settings. The profile export has revision 1.
  3. The Ansible run of the VPN nodes reads /v1/vpn-profiles/staff/config?format=eduvpn for each node and writes config.php.
  4. m.huber connects with the eduVPN app over WireGuard. eduVPN gives 10.40.0.17 and runs the hook. The agent of vpn-01 sends the connect. bembel starts the session.
  5. At 14:02 a firewall log shows an attack from 10.40.0.17. A user of kc:netsec runs bembel vpn session ls --address 10.40.0.17 --at 2026-11-04T14:02:00Z and gets the user id. The audit log records the read.
  6. m.huber disconnects at 15:07. The hook sends the disconnect, and bembel ends the session. After 90 days the reaper deletes it.
