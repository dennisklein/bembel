DNS and BIND export

bembel owns the data of the zones. BIND answers the queries. This chapter describes the zone and view model, the records that bembel derives from addresses, the reverse zones that it computes from subnets, and the BIND export that carries all of it to ns1.example.org, ns2.example.org and ns3.example.org.

  • A zone belongs to one or more views. A record belongs to all views of its zone, or to a list of them.
  • An address with a name makes the A or AAAA record and the PTR record. Nobody edits these derived records. They change only when the address changes.
  • Reverse zones come from the subnets. This includes the ip6.arpa nibble zones and the RFC 2317 child zones, with the parent CNAME records that ONA never wrote.
  • The BIND export is deterministic. It writes named.conf.bembel, one zone file per view and zone, and a manifest. A zone serial changes only when the zone content changes.
  • A bundle is published only after named-checkconf -z and named-checkzone pass in a sandbox. bembel-agent pulls the bundle, verifies the signed manifest, installs the changed zone files, swaps a symlink and runs rndc reload for the changed zones.
  • Two modes: native mode for the clean output, compat mode for byte parity with ONA build_bind during the parallel run.

What is in v1

v1 delivers BIND zone files and named.conf fragments by pull. Catalog zones, RFC 2136 updates, a PowerDNS driver and DNSSEC signing support come later (later). The requester requires the BIND export in v1. The Kea chapter is DHCP and ISC dhcpd export.

Zones

A zone is a part of the DNS name space with one set of SOA and NS data. bembel knows two kinds of zone. A forward zone, for example kestrel.example.org, holds names. A reverse zone, for example 20.10.in-addr.arpa, holds PTR records. A user creates the forward zones. bembel computes the reverse zones from the subnets (reverse).

A zone has these fields. The API path is /v1/zones/{id}.

A zone is a normal object. It has an owner, tags, a revision and an audit trail. A user needs zone:update in the scope of the zone to change it, and zone:create or zone:delete to create or delete it. Manual records need record:create, record:update or record:delete in the scope of their zone. The scope type zone covers the zone and all zones below it by name, so a role can end at kestrel.example.org.

A zone has a parent by name. The parent holds the delegation. If kestrel.example.org and example.org are zones on the same servers, bembel writes no NS delegation for the child into the parent. If the child lives on other servers, the user gives the child a delegation list. bembel then writes NS records and glue for the child into the parent.

Views

A DNS view gives different answers to different clients. The name internal serves the campus and the cluster. The name external serves the rest of the world. ONA has a dns_views table, but build_bind ignores it. In bembel the view is a real part of the output.

FieldMeaning
nameThe view name. Unique. It appears in named.conf and in file paths.
ordinalThe order in named.conf. BIND uses the first view whose match-clients matches. bembel stores the order and refuses duplicates.
match_clientsA list of prefixes, address groups or TSIG key names. bembel writes it as an acl. An address group makes the ACL follow the data.
match_destinationsOptional. For servers with one address per view.
recursionyes or no. Default no. The story's internal view sets yes for its address ACL, so DHCP and VM clients can use ns1 and ns2 as resolvers (10.20.2.53, 10.20.2.54). The external view keeps no.
transfer_keyThe name of the TSIG key that selects this view for zone transfers and NOTIFY. Default xfer- and the view name, for example xfer-internal. The bundle names the key. The secret is in a file on each server.

A zone has one copy in each of its views. Two copies of example.org are two files: one for internal and one for external. A record has the field view. The value null means "all views of the zone". A list, for example ["internal"], limits the record to these views. This is how the name ib-leaf-a01.example.org stays inside the campus.

BIND has strict rules for views. bembel checks them when it builds the export.

  • When one view exists, every zone must be inside a view.
  • A zone name can appear once in a view.
  • A zone that must be the same in two views can use in-view. bembel uses it only when the user sets share_view on the zone. Then both views serve one file.
  • Each view has its own transfer key (field transfer_key). On every server the key is the first element of the view's match-clients, and the other views exclude it with !key. Zone stanzas use the view's key in allow-transfer, also-notify and primaries. Then a secondary gets each copy of a zone from the right view, although its address matches the internal ACL.
  • An rndc command for a zone needs the view name: rndc reload kestrel.example.org in internal.

A test proves the split for the secondaries. It transfers the copy of example.org of each view from ns2 with the key of the view (dig @10.20.2.54 example.org AXFR -y hmac-sha256:xfer-external:…) and compares it with zones/<view>/example.org.zone of the bundle. The name ib-leaf-a01 must be absent from the copy of external. The test runs in the export tests and in the cutover checks (migration.html#cutover).

Why one view means no view block

Most sites have one view at the start. If only one view exists, bembel writes the zones directly in named.conf.bembel without a view block. The paths still contain the view name. A later second view then changes the config, but not the paths of the existing files.

Records

A record has a name, a type, a TTL, the data and a view list. It lives in one zone. bembel picks the zone with the longest matching suffix among the zones of the view. Two kinds of record exist.

TypeKindRule
A, AAAAderivedMade from an address that has an FQDN. A user cannot edit it. An A or AAAA record for a target outside all subnets is a manual record with the tag external-address.
PTRderivedMade from an address. One PTR per address. See derived.
CNAMEmanualAn alias. The name must not hold other data.
MXmanualPreference 0–65535 and a target name. The target must not be a CNAME.
SRVmanualPriority, weight, port and a target name. The owner starts with _service._proto.
TXTmanualOne or more strings. bembel splits a string longer than 255 bytes into chunks.
NSmanualOnly at the apex, or at a delegation point of a child zone.
CAA, SSHFP, TLSAmanualData is checked for syntax. TLSA and SRV owners may start with underscores.

The validation rules apply to every write through the API. The export checks them again, because import and sync write records too.

  • CNAME exclusivity. A name that has a CNAME has no other record of any type. The check covers derived records, so allocating an address for a name that is a CNAME fails with 409 cname.conflict.
  • No CNAME at the apex. The apex holds SOA and NS.
  • Targets. The target of MX, NS and SRV is a name with an A or AAAA record, never a CNAME. A missing target is a warning when it is outside bembel, and an error when it is inside a zone of bembel.
  • Name syntax. A label has 1–63 bytes. A name has at most 253 bytes. The letters are a–z, digits and the hyphen. A label does not start or end with a hyphen. bembel stores names in lower case. The underscore is valid in the owner of SRV, TXT and TLSA records only. The wildcard * is valid only as the first label.
  • TTL. Allowed values are 60 to 604800 seconds. The TTL of a record comes from, in this order: the record, the address or host field dns_ttl, the default_ttl of the zone.
  • Duplicates. The same name, type and data twice in one view is an error. A record set (same name and type) shares one TTL. A write that sets a different TTL for one member changes the whole set.

Derived records

An address that has an FQDN makes records. The user does not write them. A host can have many addresses and each can have a name, so the rules say which record is the PTR.

InputOutput
Address 10.20.4.44, FQDN cn-004.kestrel.example.orgA record cn-004 in zone kestrel.example.org, data 10.20.4.44
Address 2001:db8:4200:204::44, same FQDNAAAA record cn-004, same zone. The A and the AAAA record form no conflict.
Both addresses, host primary FQDN cn-004.kestrel.example.orgTwo PTR records. Each address has one PTR to the primary FQDN.
Address 10.100.4.44 on ib0, FQDN cn-004-ib0.kestrel.example.orgA record in the zone. The PTR goes to the name of the address itself, because the primary FQDN belongs to the Ethernet address.

The rules are short.

  1. A forward record exists for each address in status allocated or reserved that has an FQDN. An address can have more than one FQDN. Each name makes its own A or AAAA record.
  2. The PTR target of an address is the field ptr_name. It defaults to the host primary FQDN when the address is the primary address of the host, and to the first FQDN of the address otherwise. The value none switches the PTR off.
  3. The host primary FQDN is one name per host (ONA primary_dns_id). The user sets it on the host. One of the host addresses gets the flag primary.
  4. A shared address (VIP, anycast) makes one A record for each name and one PTR with the field ptr_name.
  5. An address in status claimed makes no record, unless the claim was made with publish: true (bembel vm prepare sets it). When the claim expires, the reaper deletes the address and the next export drops the records.
  6. An address in status deprecated makes no record. The setting dns.publish_deprecated changes this. The default is false.

The records are not stored twice. bembel calculates them from the addresses when it reads zone content, through a database view. The API lists them as read-only records with derived: true and a link to the address. A write to a derived record returns 409 record.derived and names the address.

What changes when an address moves

A change of the address data changes the derived records in the same transaction. The serial of each zone that changes goes up at the next export.

A manual CNAME that points to a renamed host does not change. bembel shows it in the finding list as cname-dangling, because the target name no longer exists. The user fixes it or the rename wizard offers to rewrite the CNAME.

Reverse zones

bembel computes the reverse zones from the prefix tree. The user can state one rule: a prefix can carry reverse_zone: true and then it is the top of one reverse zone. If no prefix above a subnet has this flag, the defaults apply.

FamilySubnetZone
IPv4Prefix length 8, 16 or 24One zone: 10.in-addr.arpa, 20.10.in-addr.arpa or 4.20.10.in-addr.arpa
IPv4Between the boundaries, for example 10.20.4.0/22One zone per /24 it covers (4.20.10.in-addr.arpa to 7.20.10.in-addr.arpa), unless a container above has reverse_zone: true
IPv4Longer than /24, for example 198.51.100.64/27PTR records go in the /24 zone. With reverse_mode: classless the subnet gets an RFC 2317 child zone (classless).
IPv6Prefix length is a multiple of 4One zone with prefix_length / 4 nibbles
IPv6Other length, for example /62Zones of the next longer multiple of 4 that cover it. A /62 gives four /64 zones.

The story has a container 10.20.0.0/16 with reverse_zone: true. Its zone is 20.10.in-addr.arpa. All subnets below it put their PTR records in this one zone. The IPv6 subnet 2001:db8:4200:204::/64 has a zone with 16 nibbles.

Each reverse zone follows the same rules as a forward zone: SOA, NS, servers, views and an owner. The zone name is the key. If the user creates a reverse zone by hand with the same name, it replaces the computed one and keeps the settings. The difference is that bembel adds and removes a computed zone when subnets come and go. bembel never removes a zone that holds a manual record. It reports a finding instead.

Two subnets, one PTR name

The PTR owner of an address is unique per view. When two addresses in two VRFs have the same IP (for example 10.100.4.44 in hpc-fabric and in another VRF), only one VRF can publish PTR records for the zone. The zone has a field vrf. The reverse computation uses the addresses of that VRF only. The default is global.

Classless delegation (RFC 2317)

A /27 holds 32 addresses. A normal reverse zone cannot be delegated for a part of a /24. RFC 2317 solves this with CNAME records. The parent /24 zone holds one CNAME for each address. The CNAME points into a child zone, and the child zone is delegated to the owner of the /27.

ONA writes the child zone, with the owner names such as 5-27.0.168.192.in-addr.arpa.. ONA does not write the CNAME records and the NS delegation in the parent zone. The user must add them by hand in the parent. bembel makes them from the data.

The rules for a classless subnet:

  • The subnet is longer than /24 and has reverse_mode: classless. A /25 to /31 subnet is valid.
  • The child zone is named FIRST-LEN.C.B.A.in-addr.arpa. For 198.51.100.64/27 this is 64-27.100.51.198.in-addr.arpa. The setting reverse.label_style: slash changes the hyphen to a slash. The file name always uses the hyphen.
  • The parent zone is the /24 zone that covers the subnet. bembel writes an NS record at the label 64-27 for each server of the child zone.
  • The parent zone holds a CNAME for each address of the subnet, from .64 to .95. The CNAME targets the same number in the child zone.
  • The PTR records of the addresses are in the child zone. The child zone has the usual SOA and NS data.
  • If the child zone has the same servers as the parent, the export writes both zones to the same server. If the child is delegated to other servers, bembel writes the NS and the CNAME records only, and the child zone is marked external.

The check "CNAME exclusivity" covers the parent: the label 65 in the parent zone cannot hold a PTR when it holds the CNAME. A conflict is an error for the zone build.

The BIND export

The BIND export turns the DNS data into files for one DNS server. The command is bembel export bind. The server runs it as a job, and a user can run it from the CLI for a dry run.

# dry run: write the files of ns1 to a directory
bembel export bind --server ns1.example.org --out ./out/ns1

# the same through the API: a bundle for one server
curl -H "Authorization: Bearer $BEMBEL_TOKEN" \
     -o bundle.tar https://bembel.example.org/v1/dns-servers/ns1.example.org/bundle

The export has these properties.

  • Consistent. The export reads one database snapshot. A change that happens during the build goes into the next build.
  • Deterministic. The same data gives the same bytes. The render code sorts names in canonical DNS order, then by type and by data. The line endings are LF. The column widths are fixed. No map order reaches the output.
  • Per server. The model for ns1 holds the zones that ns1 serves, with the role of ns1 for each zone. A secondary gets a type secondary stanza and no zone file.
  • Secret free. A bundle holds no key material. The TSIG keys xfer-internal and xfer-external are in the file /etc/bind/bembel-tsig.conf on each server. The config only names the keys and includes the file.

Files in a bundle

A bundle for ns1.example.org has this tree. The names are the same for every server. A bundle id is b- and the first 6 hex digits of the SHA-256 digest of the bundle.

b-9e2d41/
├── manifest.json             # a copy of the signed manifest; manifest.json.sig is a separate part
├── named.conf.bembel        # include this file from named.conf
├── acls.conf                 # one acl per view and per address group
├── views/
│   ├── internal.conf         # zone stanzas of the view
│   └── external.conf
└── zones/
    ├── internal/
    │   ├── example.org.zone
    │   ├── kestrel.example.org.zone

    │   └── 4.0.2.0.0.0.2.4.8.b.d.0.1.0.0.2.ip6.arpa.zone
    └── external/

The bundle tree is the staging area. named never reads a zone file inside it. The agent installs each changed zone file into a stable directory that named owns: /var/lib/bind/bembel/<view>/<zone>.zone, for example /var/lib/bind/bembel/internal/kestrel.example.org.zone. named reads only the config parts (named.conf.bembel, acls.conf, views/*.conf) through the symlink current. See Paths on the server.

The file named.conf.bembel holds the views and the includes. The administrator of ns1 adds one line to the own named.conf:

include "/var/lib/bembel-agent/bind/current/named.conf.bembel";
// bembel bundle b-9e2d41 for ns1.example.org
// generator bembel 0.1.0, mode native. Do not edit.
include "/etc/bind/bembel-tsig.conf";      // keys xfer-internal and xfer-external, local file
include "/var/lib/bembel-agent/bind/current/acls.conf";

    match-clients { !key "xfer-external"; key "xfer-internal"; "bembel-internal"; };
    recursion yes;
    allow-recursion { "bembel-internal"; };
    allow-query-cache { "bembel-internal"; };

    match-clients { !key "xfer-internal"; key "xfer-external"; any; };

// views/internal.conf

The file /etc/bind/bembel-tsig.conf holds key "xfer-internal" { algorithm hmac-sha256; secret "…"; }; and the same for xfer-external. The view external uses xfer-external in its zone stanzas.

On ns2 and ns3 the same export gives the same match-clients in both views, and stanzas of type secondary with primaries { 10.20.2.53 key "xfer-<view>"; };, for example primaries { 10.20.2.53 key "xfer-internal"; }; in the view internal. The SOA queries, the transfers and the NOTIFY messages are signed with the key of the view, so each lands in the right view on both sides. A secondary has its zone file in a local directory that BIND owns. ns2 needs no bundle pull for zone content. It still pulls the bundle, because the bundle holds its config. In a hidden-primary setup, only the primary has the zone files.

The native format has these rules.

  • The header holds no date and no build number. A timestamp would change the file on each build.
  • The file prints a TTL on a record line only when it differs from the zone $TTL.
  • The owner names are relative to $ORIGIN. The data names are absolute with a final dot.
  • The sections "derived from addresses" and "manual records" have comment headers. An extra_records block follows at the end under its own header.
  • A note on a record becomes a trailing comment. bembel removes line breaks from it.

The manifest

The manifest names the kind and the server of the bundle, the snapshot, the signing key, the sha256 of bundle.tar and of every file, and the zone serials. bembel signs the manifest. The agent trusts only the signed manifest. It uses the manifest to check the bundle and to decide which zones to reload.

Serial rule

A zone serial is a 32-bit number. A secondary transfers a zone only when the serial of the primary is higher (RFC 1982 arithmetic). bembel sets the serial with these rules.

  1. Bump only on a change. The export renders the zone body without the SOA serial. It compares the sha256 of the body with the hash of the last published body. If the hashes are equal, the serial stays. The bytes stay equal, the ETag stays, and no one reloads.
  2. Date based. The new serial is YYYYMMDDnn with the UTC date and a two-digit counter. The first change of the day gives nn = 01.
  3. Never below the current serial. If YYYYMMDD01 is not higher than the current serial, the new serial is the current serial plus one. This happens after 99 changes in one day, or after a clock error. The serial then runs ahead of the date. This is valid.
  4. One writer. Only the export job sets serials. The servers never stamp them. All servers that serve a zone get the same serial.

The serial of a zone depends on the content in each view. The zone example.org in internal and in external has two serials. They can differ.

These rules apply in native mode. In compat-ona mode the serial is the Unix time of the build, as ONA writes it (compat mode). For example, the build b-7c41e0 of 2026-11-04 17:57:41 UTC gives the serial 1793815061.

Cutover from the ONA serial

ONA writes the Unix time as the serial. On 2026-11-04 this is about 1 793 700 000. The date-based form of the same day, 2026110401, is a larger number (2 026 110 401). The difference is about 232 million. This is less than 231, so a secondary treats the new serial as higher. No manual step is needed on the secondary.

  • At import, bembel reads the highest serial it sees in the ONA zone files and stores it as the floor of the zone. The floor is the highest of the ONA-file serial and the serial that the servers answer.
  • The first native serial is max(YYYYMMDD01, floor + 1). After that the serial follows the rules above: date based, bumped only on a change, never below the current serial.
  • The cutover check stops the export with an error when the new serial is not higher than the last serial the secondaries have. The agent reports the serial that the server answers for the SOA.
  • A native serial (about 2.03 billion) stays above the Unix-time serial of ONA until about 2034. A rollback to ONA therefore cannot rely on the ONA serial. The agent re-stamps the ONA zones (rollback).

Do not change to a smaller scheme

A serial that goes down makes secondaries ignore the primary. A counter that starts at 1 is lower than the Unix time by a factor of a billion. bembel never produces such a serial. The migration chapter gives the steps of the switch from the ONA serial and of a rollback (migration.html#serial). The administrator keeps the date-based scheme for the lifetime of the zone.

Checks

A bundle is published only after its checks pass. The checks run in the export job on the bembel side, in a sandbox. BIND binaries of the version of the servers (BIND 9.18 or 9.20, set per server) are in the image of the job. The agent runs the same checks again on the server before it swaps the symlink.

Delivery

A DNS server pulls its bundle. The pull works through firewalls, and the server keeps its last good state when bembel is down. A bundle has three parts: bundle.tar, manifest.json and a detached signature manifest.json.sig (Ed25519 over manifest.json). The manifest holds the sha256 of bundle.tar and of every file, so the signature covers all parts. The key pair belongs to the installation. The server config names the signing key (exports.signing: {key_id: bembel-2026-1, key_file: /run/secrets/export-signing-key}). The agent config lists the trusted public keys (trust.keys: [{id: bembel-2026-1, public_key_file: /etc/bembel/keys/bembel-2026-1.pub}]), up to two during a key rotation (operations.html#security).

The agent works in these steps.

  1. Every 60 seconds (with jitter) the agent calls GET /v1/dns-servers/ns1.example.org/bundle with the header If-None-Match and its bearer token. bembel answers 304 when the ETag is the same.
  2. On 200 the agent saves the three parts and makes these checks, in this order:
    1. The signature of manifest.json is valid with the trusted key that key_id names.
    2. kind and server are equal to the identity in the agent config (bind, ns1.example.org). A bundle for another server is refused.
    3. snapshot is not lower than the snapshot of the current release. An older bundle is refused. A pin is a newer bundle (see below), so this rule has no exception. Only the local command bembel-agent rollback overrides it.
    4. The sha256 of bundle.tar and of each file is equal to the manifest.
    A refused bundle changes nothing: the current release stays. The agent reports deploy.bundle-rejected and counts it in bembel_agent_bundle_rejected_total{reason} (signature, identity, rollback, hash).
  3. The agent unpacks the bundle to /var/lib/bembel-agent/bind/releases/b-9e2d41/. It writes a check copy to releases/b-9e2d41/.check/. In the check copy, the path prefix /var/lib/bembel-agent/bind/current/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/, and /var/lib/bind/bembel/ becomes /var/lib/bembel-agent/bind/releases/b-9e2d41/zones/. The agent verifies that each rewritten file differs only in these prefixes. Then it runs named-checkconf -z on a copy of /etc/bind/named.conf whose bembel include points at releases/b-9e2d41/.check/named.conf.bembel, and named-checkzone with the flags of step 2 of the checks on releases/b-9e2d41/zones/<view>/<zone>.zone for each changed zone. So the checks read the new release, not the release behind current. The sandbox on the bembel side does the same with its unpack directory.
  4. If the checks pass, the agent installs each changed zone file into /var/lib/bind/bembel/<view>/: it writes a temporary file in the same directory, calls fsync and renames it with rename(2). Then it replaces the symlink current with a new symlink through rename(2). Both steps are atomic.
  5. The agent compares the manifest with the one of the last release. If config_changed is true, it runs rndc reconfig. For each zone with changed: true it runs rndc reload ZONE in VIEW.
  6. The agent sends the status to POST /v1/dns-servers/ns1.example.org/deployments: the bundle id, the time, the result per zone and the serial that named answers.
  7. The agent keeps the last 5 releases and the release ona-final, and removes older ones.

The signature protects the transport and the ingress path. It does not protect against a compromised bembel pod that holds the signing key. The same checks apply to the dhcpd and OpenSM bundles (dhcp.html#delivery, fabrics.html#opensm).

Rollback and pin

If a step from 3 to 5 fails, the agent keeps the old symlink (or swaps back to the previous release) and reports the error. This swap back during a failed apply, before any reload, needs no new serial, because no server saw the new serial.

All other rollbacks bring the content back and move the serial up. An older release holds lower serials. If ns1 loaded them, ns2 and ns3 would keep the newer, bad data with no time limit: the zone does not expire, because ns1 still answers their SOA queries.

  • Pin. PUT /v1/dns-servers/ns1.example.org/pin with {"bundle": "b-5e08c3", "reason": "…"} needs export:build. bembel builds a new bundle (new id, new snapshot, new ETag) with the zone bodies of the named bundle. Each zone whose body differs gets the serial max(highest serial that bembel published for this zone and view, highest served serial) + 1. The bundle goes through the normal checks, step 4 too. While the pin is set, data changes do not change the bundle of this server. DELETE /v1/dns-servers/ns1.example.org/pin lifts it (204). The next export uses a serial above the stamped one. This is the way to hold a server on known good content while a fix is made.
  • Local emergency rollback. bembel-agent rollback --to b-5e08c3 works without bembel, from the local releases. The agent installs the zone content of that release and rewrites the SOA serial of each changed zone to the served serial plus one. It runs named-checkzone, swaps and reloads. Then it reports the new serials in POST /v1/dns-servers/ns1.example.org/deployments, and bembel raises its stored serial.
  • Rollback to ONA. bembel-agent rollback --to ona-final gives each ONA zone the serial max(ONA serial, served serial + 1). While the source of the agent is ona, it re-stamps every later ONA build in the same way. No RFC 1982 reset is needed.

The deployment status gives a drift view. The server page in the UI shows the bundle id of each server, the age of the last pull, and the serial per zone that the server answers against the serial that bembel expects. The metric bembel_export_last_pull_timestamp_seconds has the alert rule BembelExportNotPulled (operations.html#alerts).

Why pull and not push

A pull needs no inbound firewall rule on the DNS servers. The agent can run on a server that bembel cannot reach. A broken bembel leaves the servers with the last good bundle. The ONA script wrote files in place and checked them afterwards, so a bad zone was already live on disk. The agent checks first and swaps after.

Compat mode

The compat mode writes the same bytes as ONA build_bind (v1.6, build_bind_conf and build_bind_domain v1.51). The parallel run compares the two outputs every night. When the diff is empty or explained, the cutover can start (migration.html#parallel). The export setting mode is compat-ona or native, per DNS server. Until the cutover, ns1 to ns3 are in compat-ona, and their agents run in shadow mode: they pull and check each bundle but do not activate it (migration.html#agent). ONA still writes the live files.

The nightly diff normalises three things on both sides: the date in line 1, the SOA serial, and the order of the record lines. It keeps TOTAL RECORDS (count=N) as an assertion. The list of known differences is a file in the repository (migration.html#known). It names each difference with a reason. A diff that is not in the list fails the run. The level 2 diff compares the zones as records: named-compilezone -f text -F text -s full -o - ORIGIN FILE | sort runs on both trees, and the diff compares the sorted RRsets. The style -s full writes an absolute owner name on every line. This finds a difference that survives the byte normalisation.

When compat mode ends

At cutover, the administrator sets the mode of each server to native one server at a time. The file paths change, and the agent handles the move. The first native bundle contains a one-time include for the new paths. ONA stays able to build for the rollback window. A rollback to ONA re-stamps the ONA serials (rollback).

    type primary;
    file "/var/lib/bind/bembel/internal/kestrel.example.org.zone";

    inline-signing yes;

Every later step is a new delivery kind of the DNS server object. The data, the views, the derived records and the checks stay the same. The roadmap lists the order (roadmap.html#v1-1).
