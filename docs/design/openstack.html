OpenStack

This chapter specifies how bembel works with an OpenStack cloud. Phase 1 reads the cloud and shows what it uses. Phase 2 replaces the address allocation of Neutron with a driver that calls the bembel API. The example cloud is os-prod.

  • Phase 1 is read-only. A sync worker polls Neutron and Ironic with a Keystone application credential. Objects get source=openstack:os-prod and a managed-by mark, so a user cannot edit them.
  • The sync finds conflicts: an OpenStack subnet that overlaps a prefix that bembel manages becomes a finding.
  • Phase 2 is the Python package networking-bembel. It registers the entry point neutron.ipam_drivers and calls only the public REST API.
  • The driver makes a claim with a time to live (TTL). The sync confirms the claim when it sees the port. A reaper releases a claim that nobody confirms.
  • Keystone and bembel trust the same Keycloak. A Keystone project maps to a bembel team. The driver has its own service identity.
  • Each DNS zone has one writer. bembel owns the campus zones through the BIND export. Designate owns only the tenant zones.
  • The driver is on the API path of Neutron. It fails closed: when bembel is not reachable, a port create fails and no address is leaked.

Summary

OpenStack has its own address management. Neutron stores networks, subnets, ports and floating IPs in its own database. A campus IPAM that does not know this data cannot find an overlap, a double use or a stale address. bembel joins the two worlds in two steps.

  1. Phase 1 reads. bembel shows every OpenStack subnet, port and floating IP next to the campus data, and reports conflicts. Nothing in OpenStack changes.
  2. Phase 2 writes. Neutron asks bembel for each address and each subnet. bembel becomes the one place that decides which address is free.

Phase 2 is optional. A site can stay in phase 1 for ever. The two phases use the same data model: a VM is a host with kind=vm, platform=openstack and a runs_on link to its hypervisor. Debian hypervisors with libvirt use the same model (Virtual machines).

Phase 1: read-only sync

The sync worker is a job of the bembel binary. A source os-prod in the bembel config starts it. The worker needs no change in OpenStack, except one Keystone application credential. It polls the REST APIs and writes observed objects. An observed object has source=openstack:os-prod, an external_ref and managed_by=openstack-sync. A user cannot edit it in bembel; the cloud is the owner.

# /etc/bembel/bembel.yaml (excerpt)

VMs as hosts

Neutron does not store VMs. It stores ports with device_id (the Nova server UUID), binding:host_id (the hypervisor) and optional dns_name. The worker makes one VM host per device_id:

name
The port dns_name with the domain of the network (web-12.os.example.org). Without it: server-<first 8 hex of the UUID>. With nova: true the worker reads the real server name from GET /servers/detail.
kind, platform
vm, openstack.
runs_on
The host with the name binding:host_id, for example hv-os-17.example.org (kind hypervisor). When no such host exists, the worker makes it and marks it observed.
owner
The team of the project of the port.

Poll, reconcile, conflicts

  1. Every interval the worker lists ports, subnets and floating IPs. It compares revision_number with the stored value. It upserts only the objects that changed.
  2. Every full_every the worker compares the complete lists with the stored set. An object that is missing in two full lists becomes deprecated. After the grace time bembel releases it.
  3. For each new or changed subnet the worker checks the prefix tree. An overlap with a prefix that a user manages becomes a finding, not a prefix.
  4. The worker writes the run result: counts, duration and errors. The metrics bembel_sync_run_seconds and bembel_sync_errors_total carry the label source="os-prod".

Why poll first

Neutron sends notifications through RabbitMQ (port.create.end, floatingip.update.end). A consumer needs access to the broker, and a notification is lost when no queue exists. Polling needs only the REST API. It lags by minutes, which is enough for a view. Phase 3 adds a notification consumer to reduce the lag. The full list stays the source of truth.

Tenant networks can overlap. Two projects can both use 192.168.1.0/24. The database does not allow two equal prefixes in one VRF, so the worker puts each project without an address scope in its own VRF, for example os-physics-lab. A subnet with an address scope goes to the VRF of that scope. This is the VRF rule list in the config above. A subnet that still overlaps inside one VRF is stored as a finding with the raw data. The finding list shows both owners.

Phase 2: the Neutron IPAM driver

Neutron has a pluggable IPAM interface (neutron/ipam/driver.py). The option ipam_driver names a Python entry point in the group neutron.ipam_drivers. The default is internal. bembel ships the package networking-bembel with the entry point bembel. The package has no logic about addresses. It translates each call to the bembel REST API.

# setup.cfg of networking-bembel
[entry_points]
neutron.ipam_drivers =

Idempotency key

Neutron can call allocate more than once for one port. A database deadlock retries the whole request. The driver must give the same address for the same logical request. It derives the key like this:

key = sha256( cloud + "|" + subnet_id + "|" + request_id + "|" + n )

cloud       "os-prod"
subnet_id   the Neutron subnet UUID
request_id  context.request_id of the API request; a retry keeps it
n           index of the allocate call inside this request (0, 1, ...)

The driver sends the key as the header Idempotency-Key. bembel stores it for 24 h with the result. The same key gives the same response (API conventions). The driver also sends external_ref=os-prod:port-claim:<key prefix>. The sync replaces it with the real port id.

Not verified

The request object does not carry the port id. This design assumes that the request id of the oslo context reaches the driver unchanged on a deadlock retry. A test against Neutron master must prove it. If it fails, the package carries a small patch that passes the port id in the request.

Rollback, leaks and the reaper

Neutron calls the IPAM driver first and writes its own rows after that. When the write fails, Neutron calls deallocate to undo the allocation. It does this only when needs_rollback() is True. The internal driver says False because it shares the database transaction. An external driver must say True.

The rollback is best effort. It can fail, for example when bembel is not reachable at that moment. The address then stays in bembel without a port in Neutron. This is a leak. The claim with a TTL is the cure: the leaked address is a claim, not an allocated address, and it expires.

These rules keep the state clean:

  • A claim has the status claimed and expires_at. The default TTL is 10 minutes. It is longer than the longest poll interval plus two retries, so the sync can confirm a good claim first.
  • The sync confirms a claim when it finds a port with that address in that subnet. The status becomes allocated. The key is replaced by the port id in external_ref.
  • A deallocate call for an unknown address answers success. A repeated call does nothing.
  • The sync also finds the opposite case: a port with an address that bembel does not know. It makes the address with source=openstack:os-prod and writes the finding os.address-in-managed-subnet if the subnet is managed.

Timeouts and fail-closed behaviour

The driver is on the API path of Neutron. Each call holds a Neutron worker and often a database lock. The driver must be fast and must stop early.

CaseBehaviour
Connect time over 2 s, read time over 5 sThe driver retries 2 times with the same key. Then it raises IpAddressGenerationFailure. Neutron returns an error. No port is made.
5 failures in 30 sA circuit breaker opens for 20 s. The driver fails at once, without a call. This protects the Neutron workers.
bembel answers 409 (address taken)For a specific address: IpAddressAlreadyAllocated. For the next free address: the driver asks again (at most 3 times).
bembel answers 429 or 503The driver retries after the Retry-After time, within the read timeout.
The pool is emptybembel answers 409 pool.exhausted. The driver raises IpAddressGenerationFailure.
bembel is downFail closed. The driver does not fall back to the internal driver. A fallback would give two sources of truth. Existing VMs keep running. New ports wait.

Why fail closed

An address that two systems give at the same time is worse than a failed port create. The user sees an error and tries again. An address conflict stays hidden until two VMs fight for one IP. The bembel API is in HA mode (Deployment and operations), so a short outage is rare.

Subnet pools, address scopes and prefix pools

Neutron has subnet pools. Neutron carves tenant subnets from them. An address scope says that all subnet pools in the scope share one routing domain, so their prefixes never overlap. bembel has prefix pools (a container with the pool flag) in a VRF. The mapping is one to one.

NeutronbembelExample

External network, floating IPsSubnet in VRF global below the container 10.30.0.0/16 "OpenStack"10.30.128.0/20 for floating IPs
Subnet without a poolPrefix in the VRF per project (see above)os-physics-lab: 192.168.1.0/24

Neutron keeps its own copy of the pool prefixes in its database. The driver cannot hide it. The rule is: bembel owns the prefix tree and Neutron mirrors it. An operator changes the pool in bembel; the sync then updates the Neutron subnet pool through a small admin command (bembel sync openstack push-pools os-prod, a phase 2 task). A change of the pool in Neutron by hand is a finding.

Neutron allows only one IPAM driver for the whole cloud. It is not a setting per subnet pool. To start without risk, the site first runs the driver on a test cloud os-test. A cut-over on os-prod needs the existing allocations in bembel. Phase 1 already has them as observed objects. The cut-over changes their managed_by to the driver, in one step per subnet, after a check that the Neutron data and the bembel data agree.

Keystone and identity

Keystone and bembel are two clients of one IdP. Both trust the Keycloak realm main at https://id.example.org/realms/main. A user logs in once and has the same groups in both systems.

Federation

  • Keystone is a service provider with Apache mod_auth_openidc. The attribute remote_id_attribute = HTTP_OIDC_ISS names the IdP.
  • The mapping (schema 3.0, dynamic project assignment) reads the claim groups and the claim openstack-projects of Keycloak. Keystone makes the project and the role on first login.
  • bembel reads the same groups claim. The group openstack maps to the team openstack. The user s.yildiz is in it.

Project to team

A bembel team is an owner of objects. A Keystone project has a stable UUID. The mapping table is part of the source config:

    projects:                        # in the source os-prod
      default_team: openstack
      map:
        - { project: "physics-lab",  team: hpc-ops }
        - { project: "9d3f6b1e-6c3a-4f0b-8d2e-3f1c8f1a0b11", team: hpc-ops }
        - { name_prefix: "tenant-",  team: openstack }

The team gets external_ref=os-prod:project:<uuid>. A project that is not in the table gets the default_team and a finding, so an operator sees the new project. The same project name in two clouds does not collide, because the external ref has the cloud name.

Service identities

The driver has no end user. Neutron calls it for a request of a user, but the user token never reaches the driver. The driver has its own service identity and passes the project id from SubnetRequest.project_id as data. bembel trusts the driver for this statement and writes it to the audit event.

Open point

An application credential is scoped to one project. The default Neutron policy lists the ports of all projects only for an admin. The design needs a policy override that gives the role reader a read-only view on ports, subnets and floating IPs of all projects. The exact rule names are not verified. The operator checks them against the release in use.

The audit event of an allocation through the driver has: the subject svc-neutron-os-prod, the claim key, the asserted project and the Neutron request id. This is how a later question "who made 10.30.4.17" finds the Neutron request.

Designate

Designate is the DNS service of OpenStack. It has an API for zones and record sets, and it pushes the zones to name servers (BIND, PowerDNS) with mini-DNS (AXFR and NOTIFY). Neutron can call it for each port (dns_integration, dns_name, dns_domain). Its sink makes records from Nova and Neutron events.

bembel makes the campus DNS too. Two writers on one zone give lost records. There are three ways to combine them.

A. bembel readsDesignate owns its zones. bembel reads record sets (/v2/zones/{id}/recordsets) and shows them next to the addresses.Phase 3. Good for visibility and for findings.
B. bembel writes to Designatebembel pushes records through the Designate API. Designate serves them.No. Two systems keep the zone.
C. Split by zonebembel owns the campus zones. Designate owns only the tenant zones, in a sub-domain that bembel delegates.Recommended.

  • Neutron sets dns_domain = tenant-a.os.example.org. on tenant networks. The external network has no dns_domain, so Neutron writes no record into a campus zone.
  • A floating IP gets its campus name from bembel: the address in the external subnet has the FQDN fip-0c41.os.example.org or the name that a user sets in the UI. The sync never writes DNS.
  • Each zone has the field managed_by. A zone below os.example.org that the sync finds in Designate is stored as a read-only zone with managed_by=openstack-sync. A user cannot add a record to it in bembel.
  • bembel refuses to make a zone with the same name as a Designate zone that it knows. This is the rule "no two writers per zone".

Why not Designate for everything

The campus has about 62 000 DNS records (ONA mapping) and other sources than OpenStack. Hosts, switches and BMCs are not in Designate. Split-horizon views and RFC 2317 zones are core in bembel. Designate stays the right tool for tenants who create their own zones with the OpenStack API.

Ironic

Ironic manages bare metal. A physical machine in Ironic is a node with ports. A port is a NIC with a MAC (address), the flag pxe_enabled and the local_link_connection (the switch and the switch port). bembel uses Ironic in three ways.

  1. Learn MACs. The worker polls GET /v1/ports?detail=true. For each port it finds the host by MAC. If the host exists (for example cn-004.kestrel.example.org with eno1 3c:ec:ef:12:0a:44), the Ironic node becomes an attribute of the host. If not, the worker makes an observed host and an asset link candidate.
  2. Provisioning networks. The provisioning, cleaning and rescue networks of Ironic are Neutron networks. Their addresses come through the Neutron driver. No extra hook is needed.
  3. Pre-reserved addresses. bembel can set fixed_ips on the Neutron port for a given MAC. The result: a node always gets the same address in the provisioning network. This is a phase 3 option.

The node field driver_info.redfish_address (or ipmi_address) names the BMC. The worker looks it up in the VRF oob. If the address is 172.16.4.44 and the host cn-004 has the interface bmc with that address, the worker links node and host. If the address is not in a managed subnet, it writes a finding.

An Ironic port with local_link_connection data (switch id and port id from LLDP) feeds the asset link between the interface and the switch port from FNT Command. The match order stays: serial, asset tag, MAC, host name. A conflict goes to the review list.

Standalone Ironic (no Neutron, external DHCP) is a special case. There bembel is the DHCP source: the dhcpd export has a reservation for each Ironic MAC that has an address (ISC dhcpd export).
