Fabrics

An HPC site has more than one kind of network. A compute node sits on Ethernet, on InfiniBand and on a lossless Ethernet fabric for RoCEv2 at the same time. This chapter describes the fabric object, what each kind adds to the model, how IPv4 and IPv6 live together, and how bembel gives the data to OpenSM and to the tools that configure switches.

  • A fabric is the L2 technology domain of a subnet. It has the kind ethernet, ethernet-roce or infiniband.
  • Ethernet adds the VLAN and the VLAN domain. RoCEv2 adds a QoS profile: DSCP 26, PFC priority 3, ECN and CNP DSCP 48. InfiniBand adds the IB partition, the port GUID and the 20-byte IPoIB address.
  • IPv4 and IPv6 are equal. A dual-stack pair is an IPv4 subnet and an IPv6 subnet on the same VLAN or partition. bembel observes SLAAC and EUI-64 addresses. It does not allocate them.
  • bembel export opensm writes the OpenSM partitions.conf from the partitions and the interface GUIDs.
  • A rail-optimised GPU fabric has one subnet and one VLAN per rail. The fabric osprey-roce has 8 rails: 10.110.1.0/24 to 10.110.8.0/24 and VLAN 3101 to 3108.
  • Switch and host tools read the fabric data from the API. bembel is the source of the values. It does not configure devices.

Fabric kinds

A fabric is an object with a name, a kind, a site and optional settings. A subnet refers to one fabric. A prefix that is a container has no fabric. The default fabric of a subnet is ethernet, so a site that does not care about fabrics sees no change.

A fabric belongs to a site and to a team. The fabric has a default VRF. A subnet can use a different VRF, but the check fabric-vrf-mismatch warns about it. A fabric is not a VRF. A VRF separates address spaces. A fabric describes the wire.

Dual stack

IPv6 is a first-class family in bembel. An IPv4 prefix and an IPv6 prefix live in the same tree, and every feature works for both. A dual stack network is a pair of two subnets: one IPv4 and one IPv6. The pair shares the VLAN or partition, the fabric, the site and the owner. In the story, the pair for kestrel-compute is 10.20.4.0/22 and 2001:db8:4200:204::/64 on VLAN 204.

  • The link. Each subnet of the pair has the field twin_id that names the other; both rows point to each other. The twin is a subnet of the other family, and both share the VLAN or partition, the fabric and the site (model.html#prefix). The UI shows both as one network with two address tabs. A change of the VLAN on one changes the other in the same transaction, after a confirm.
  • The host. An interface has an address of each family. The host primary FQDN gets an A and an AAAA record (dns.html#derived).
  • Allocation. A static address is allocated as for IPv4. In a /64 the allocator takes the next free address in a range with the purpose static. A large space makes a linear search useless, so it also accepts strategy: "hint" with hint: "2001:db8:4200:204::44", or strategy: "random" (allocation.html#strategies).
  • SLAAC and EUI-64. A client that uses SLAAC builds its own address. bembel observes these addresses from neighbour tables (switch sync, host agent) and shows them in the status observed. An observed address does not use up an allocation, and it does not make DNS records. For cn-004 with MAC 3c:ec:ef:12:0a:44, the EUI-64 address is 2001:db8:4200:204:3eec:efff:fe12:a44. The first byte changes from 3c to 3e (the universal/local bit).
  • DHCPv6. A scope for the IPv6 subnet writes subnet6 and range6 in dhcpd6.conf. A reservation needs a DUID (dhcp.html#dhcpv6).
  • Reverse zones. The IPv6 subnet has a nibble zone 4.0.2.0.0.0.2.4.8.b.d.0.1.0.0.2.ip6.arpa (dns.html#reverse).

Ethernet

An ethernet fabric has VLANs. A VLAN has a VID from 1 to 4094 and lives in a VLAN domain. The domain is the scope in which a VID is unique. The domain campus-hall2 holds VLAN 204 (kestrel-compute), 208 (osprey-gpu) and 212 (ceph-public). Two domains can hold the same VID. This maps to the ONA table vlan_campus and to the NetBox VLAN group.

VLANVID, name, domain, status, MTU, VNIOne VLAN can carry one IPv4 and one IPv6 subnet of a dual stack pair, and more subnets in a shared network. The VNI is optional and comes from a VNI range (routing.html#vni).
Subnetfabric, VLAN, gatewayThe subnet VLAN must be in the domain of its fabric.

The port link joins the interface to a switch port from the asset mirror (assets.html). The switch port is the data that a switch tool needs: it knows the VLAN of a port from the subnets of the interfaces that are connected to it.

Ethernet with RoCEv2

RoCEv2 carries InfiniBand transport over UDP and IP on Ethernet. It needs a lossless path for the RoCE traffic class. A fabric of kind ethernet-roce has the same VLANs as Ethernet and adds a QoS profile. The profile is the one place for the values that switch config and host config must share. If the two sides differ, RoCE performance falls or the fabric drops packets.

Why the profile is data

The values are few, but the places that use them are many: every switch, every NIC and every RoCE host tool. A typical fault is one switch with another DSCP. When the profile is one object in bembel, the automation reads the same numbers everywhere, and a diff shows which device differs. bembel stores the intent. It does not push it.

Rail-optimised GPU fabrics

A GPU cluster uses a rail-optimised design. Each node has 8 RoCE NICs. NIC n on every node connects to the leaf switch of rail n. Traffic between GPUs with the same index stays on one leaf. A rail is a separate L3 network, so each rail has its own subnet and its own VLAN.

The data model for a rail fabric is plain:

  • One fabric osprey-roce with one VLAN domain with the same name.
  • 8 VLANs 3101 to 3108, and 8 subnets 10.110.n.0/24, each with its VLAN, a gateway 10.110.n.254 on the leaf and the name osprey-roce-rn. The rail number is a tag: rail=n.
  • A node address is 10.110.n.(10+k) for gpu-00k. The allocator does not force this. The request sends strategy: "hint" with the address.
  • The subnet 10.110.8.0/24 with VLAN 3108 is rail 8.

How a RoCE host gets its addresses

A RoCE NIC has a static address, not a DHCP address. The address belongs to the rail and the NIC. The steps are:

  1. The host exists with its interfaces roce1 to roce8, each with the NIC MAC and a port link to its leaf port.
  2. For each rail, an automation calls the allocation of the rail subnet for the interface.
  3. The result gives the address, the prefix length and the gateway of the rail. The host automation writes them to the NIC config with a rule for source-based routing: traffic from 10.110.n.11 leaves through roce n.
for n in 1 2 3 4 5 6 7 8; do
  curl -s -X POST \
    -H "Authorization: Bearer $BEMBEL_TOKEN" \
    -H "Idempotency-Key: gpu-001-roce$n" \
    -H "Content-Type: application/json" \
    -d "{\"interface\": {\"host\": \"gpu-001\", \"name\": \"roce$n\"},
         \"fqdn\": \"gpu-001-roce$n.kestrel.example.org\",
         \"strategy\": \"hint\", \"hint\": \"10.110.$n.11\", \"on_conflict\": \"fail\"}" \
    "https://bembel.example.org/v1/prefixes/osprey-roce-r$n/addresses:allocate"
done

The key Idempotency-Key makes the loop safe to repeat (allocation.html#idempotency). With on_conflict: "fail" a taken hint address gives 409 address.conflict, so a wrong address never goes to the NIC unnoticed. A user who prefers DHCP can add a reservation instead. The pool can be empty. The reservation then stays valid for the rail.

InfiniBand

An infiniband fabric is managed by a subnet manager (SM). OpenSM is the SM of the story (kestrel-ib, NDR). The SM gives each port a LID and applies the partitions. IP over InfiniBand (IPoIB) carries IP packets on an IB partition. For bembel, an IPoIB network is a normal subnet with the fabric infiniband and a partition. The VRF is hpc-fabric and the prefix is 10.100.0.0/16. Pure RDMA partitions have no IPoIB and no subnet.

The MTU of an IB partition is a code. The IB MTU of 2048 bytes gives an IPoIB datagram MTU of 2044. The IB MTU of 4096 gives 4092. bembel stores the IB MTU and computes the IPoIB value. The DHCP scope uses the IPoIB value for option interface-mtu (dhcp.html#export).

Partitions

An IB partition limits which ports can talk to each other. It is like a VLAN. A port that is not in a partition cannot send to the members of it. The partition key (P_Key) has 16 bits. The lower 15 bits give the partition number, the base key. The top bit is not a property of the partition. It is the membership of one port in the P_Key table of that port: 1 for full, 0 for limited.

  • bembel stores the base key: ib_partition.pkey integer NOT NULL CHECK (pkey BETWEEN 1 AND 32767), with UNIQUE (fabric_id, pkey). The allowed base keys are 0x0001 to 0x7ffe. The key 0x7fff is the default partition. bembel keeps it, because OpenSM needs it, but a user cannot change or remove it.
  • The API writes the key as a string of four hexadecimal digits, for example "0x0001" (pattern ^0x[0-9a-f]{4}$). An input with the top bit set is normalised to the base key, so one partition has one spelling.
  • The membership (full or limited) is on each member row. The 16-bit form with the top bit is only a derived value of a full member, for example in the name of the Linux child interface ib0.8001.
  • A full member talks to full and to limited members. Two limited members cannot talk to each other with that P_Key. Limited membership restricts only traffic that uses that partition's P_Key. In kestrel-lustre, cn-004 and cn-005 cannot talk to each other with P_Key 0x0002. They still talk as full members of Default (0x7fff) and of kestrel-ipoib (0x0001). A partition isolates ports only when they share no other partition where either is a full member.
  • The story partition kestrel-ipoib has the P_Key 0x0001. The interface ib0 of cn-004 is a full member, so its P_Key table entry has the top bit set.
  • The flag ipoib tells OpenSM to create the IPoIB broadcast group for the partition. A partition with this flag has a subnet. A partition without it carries RDMA only.
  • MTU and rate limit the multicast group of the partition. Every member must support them. The rate value is the minimum, not the speed of the NDR links.
{
  "kind": "ib-partition",
  "fabric": "kestrel-ib",
  "name": "kestrel-ipoib",
  "pkey": "0x0001",
  "ipoib": true,
  "mtu": 4096,
  "rate_gbps": 100,
  "default_membership": "limited",

    { "interface": "oss-01/ib0", "membership": "full" }

Membership comes from two sources. An interface with an address in an IPoIB subnet of the partition is a full member by rule. The user can add further memberships by hand, for example the limited membership of a compute node in a storage partition. The list members shows both with the source of each. The field default_membership is the membership that bembel gives a member that is added without an explicit one.

The DHCP servers dhcp1 and dhcp2 have the child interface ib0.8001 with the addresses 10.100.0.67 and 10.100.0.68, so they are full members of kestrel-ipoib by this rule. An IPoIB subnet has no router and no relay, so a client reaches a DHCP server only through such an attached interface (dhcp.html#reach). The port GUIDs 0c42a10300710067 (dhcp1) and 0c42a10300710068 (dhcp2) are therefore in the OpenSM export.

  • The GUID is written as 16 lowercase hexadecimal digits, without 0x and without colons, in the UI, the API and the text. An input with colons or 0x is accepted and normalised. bembel stores the 8 bytes. Only the OpenSM export writes the 0x form. The DHCP client identifier and the IPoIB hardware address keep their forms with colons.
  • The port GUID is unique in the fabric. The database enforces this.
  • The 20-byte hardware address and the LID are never typed by a user. The host agent sends the address. The SM sweep sends the LID with the time of the observation.
  • A GUID that appears in the SM and is unknown to bembel is listed in "unknown ports" of the fabric page.

The OpenSM export

The command bembel export opensm --fabric kestrel-ib writes the OpenSM partition file. It is the same export mechanism as for BIND and dhcpd: a deterministic render, checks, a signed bundle, and an agent on the SM host that pulls it. The delivery target is a subnet manager object of the fabric (/v1/fabrics/kestrel-ib/subnet-managers).

# partitions.conf for fabric kestrel-ib, generated by bembel
# bundle b-3a91c4. Do not edit.

Default=0x7fff, ipoib, rate=16, mtu=5, defmember=full : ALL=full ;

# kestrel-ipoib: IPoIB network 10.100.0.0/16
kestrel-ipoib=0x0001, ipoib, rate=16, mtu=5, defmember=limited :
    0x0c42a10300710067=full,    # dhcp1 ib0.8001
    0x0c42a10300710068=full,    # dhcp2 ib0.8001
    0x0c42a1030071a2b4=full,    # cn-004 ib0
    0x0c42a1030071a2c8=full,    # cn-005 ib0
    0x0c42a10300a3f160=full,    # oss-01 ib0
    0x0c42a10300a3f1a0=full ;   # oss-02 ib0

# kestrel-lustre: RDMA only, clients cannot reach each other on this key
kestrel-lustre=0x0002, rate=16, mtu=5, defmember=limited :
    0x0c42a1030071a2b4=limited, # cn-004 ib0
    0x0c42a1030071a2c8=limited, # cn-005 ib0
    0x0c42a10300a3f160=full,    # oss-01 ib0
    0x0c42a10300a3f1a0=full ;   # oss-02 ib0
  • Header. The partition name is the bembel partition name. The base key follows the name; OpenSM takes the membership from the =full and =limited suffixes, not from the key. The flags are ipoib (only if the partition has it), rate and mtu as OpenSM codes (mtu=5 is 4096 bytes), and defmember. defmember is the membership OpenSM gives to entries of this partition's list that have no =full, =limited or =both suffix. bembel writes an explicit suffix on every GUID, so the flag has no effect on listed ports. A port that is not listed, and not matched by a keyword such as ALL, ALL_CAS, ALL_SWITCHES or SELF, is not a member of the partition. bembel writes the field default_membership as defmember.
  • Members. Each member is a port GUID with =full or =limited. The comment gives the host and the interface name. The list is sorted by GUID.
  • Rate. bembel stores the rate in Gbps. The generator maps it to the IBTA rate code. A speed without a code stops the export with an error. The value 16 in the example is the code for 100 Gbps.
  • Default. The default partition is always written. Its content is a setting of the fabric. The story uses ALL=full, so every port is a full member of 0x7fff and the ports of the fabric can reach each other with that key. A fabric that wants real isolation can set a hardened Default: Default=0x7fff, rate=16, mtu=5 : ALL_SWITCHES=full, SELF=full, ALL_CAS=limited ;. It has no ipoib flag, because limited host ports cannot use the IPoIB broadcast group with each other. This is an option, not a check.
  • Only IB interfaces. An interface without a port GUID is not a member. The export writes a comment line for it, and the fabric page shows a finding.

What the record has not checked

The syntax above follows the OpenSM manual from memory. The rate codes and the exact reload behaviour were not verified in this sandbox. A golden-file test against a lab OpenSM decides the final form. The generator is the single place to fix.

Checks and delivery

OpenSM has no dry-run command for the file. bembel checks it with its own parser and rules:

  • The P_Key is in the range 0x0001 to 0x7ffe (or the default 0x7fff), and unique in the fabric.
  • The names are unique and use letters, digits, hyphen and underscore.
  • Each GUID has 16 hexadecimal digits. A GUID is listed once for each partition.
  • The MTU and rate are valid for all members, as far as bembel knows the link data.
  • A partition with an ipoib flag and no full member gives a warning.
  • The mass change guard holds a bundle that removes more than N % of the memberships.

The agent on the SM host pulls the bundle in the usual way and runs the same checks as the DNS agent (dns.html#delivery): the signature of manifest.json with the key named by key_id, the kind opensm and the name of its subnet manager, a snapshot not lower than that of the current release, and the sha256 of each file. A refused bundle leaves the current release in place. Then it swaps the release link, and sends a hang-up signal to OpenSM so that it reads the file again. The agent reports the result. A failed read leaves the old release in place.

How switch and host tools consume fabric data

bembel does not configure devices. It gives the values to the tools that do: Ansible, Nornir, vendor tools. These tools use the public REST API. The call GET /v1/fabrics/{id}/intent returns the data of one fabric in a form that a template can use.

{
  "fabric": "osprey-roce",
  "fabric_kind": "ethernet-roce",
  "mtu": 9000,
  "qos": { "roce_dscp": 26, "roce_priority": 3, "pfc_priorities": [3],
           "ecn": true, "cnp_dscp": 48, "cnp_priority": 6, "min_path_mtu": 4200 },
  "vlans": [
    { "vid": 3101, "name": "osprey-roce-r1", "subnet": "10.110.1.0/24", "gateway": "10.110.1.254", "vni": null },
    { "vid": 3108, "name": "osprey-roce-r8", "subnet": "10.110.8.0/24", "gateway": "10.110.8.254", "vni": null }
  ],
  "ports": [
    { "switch": "osp-leaf-1", "port": "Eth1/1", "vid": 3101,
      "host": "gpu-001", "interface": "roce1", "mac": "b8:3f:d2:9a:01:01" }
  ]
}

A VLAN of an EVPN overlay has its VNI in vni. The rails of osprey-roce are routed at the leaf and have no VNI. The list ports is the join of the interface, its port link and the asset mirror. The data for a switch, then, is: which port is on which VLAN, with which MTU and which QoS values. A generic template for a leaf switch:

{% for v in intent.vlans %}
vlan {{ v.vid }}
  name {{ v.name }}
{% endfor %}
{% for p in intent.ports if p.switch == inventory_hostname %}
interface {{ p.port }}
  description {{ p.host }} {{ p.interface }}
  switchport access vlan {{ p.vid }}
  mtu {{ intent.mtu }}
  qos trust dscp
  priority-flow-control priority {{ intent.qos.roce_priority }} on
{% endfor %}

The syntax is not a real vendor language. It shows which fields the template reads. A real template uses the commands of its vendor.

  • Change events. bembel sends a CloudEvents event, for example fabric.changed, to a webhook. A CI job for the network repository can build and review a change.
  • Routing and firewall. The prefix lists and the address groups come from the routing feeds (routing.html). A route target or a static route for a rail uses the same subnets.
  • Hosts. A host tool reads GET /v1/hosts/gpu-001 for the interface addresses and the QoS profile of each RoCE interface. It sets the type of service 104 and the PFC on the NIC.
  • Drift. A device scanner can compare the running VLAN or QoS values with the intent and post the result as a finding. The result is a data input to bembel, not a write to the fabric.

The story also shows why separate fabrics help the user. A search for the subnet 10.110.8.0/24 finds the fabric, the VLAN 3108, the 8 hosts on rail 8 and the leaf port of each one. A search for the GUID finds the interface, the host, the rack and the partitions of the port.
