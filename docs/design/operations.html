Deployment and operations

This chapter specifies how an admin runs bembel: the Helm chart for a highly available deployment on Kubernetes, the packages for plain VMs, the configuration, the backup, the metrics, logs and traces, the upgrade path and the security settings.

  • One static binary and one container image. The API server is stateless: at least 3 replicas behind a Service.
  • Background workers run in the same binary in every replica. They coordinate with PostgreSQL: lease rows for long work, transaction locks and SKIP LOCKED for short work. No leader election service is needed.
  • PostgreSQL 18 with the extension pgvector. The recommended HA setup is a CloudNativePG cluster with 3 instances in 3 zones, a synchronous replica, a PgBouncer pooler and point-in-time recovery to S3.
  • Migrations run as a Helm hook Job: pre-upgrade, and post-install on the first install. They follow expand and contract, so old and new pods run together.
  • Prometheus metrics on port 9090, JSON logs on stdout that Loki accepts, optional OpenTelemetry traces. The chart ships a ServiceMonitor, a PrometheusRule with tests and a Grafana dashboard.
  • Plain Debian and RPM packages with a systemd unit exist for sites without Kubernetes.

Three forms exist. They run the same binary. The chart is the main form.

High availability

The API is stateless

A request touches only PostgreSQL. UI sessions are rows in PostgreSQL (Access control), and the OIDC key sets (JWKS) are caches that each pod fills itself, so any pod can answer any request and a pod can die at any time.

ProbePathPasses when
liveness/livezThe process answers. It does not check the database, because a database outage must not restart all pods.
readiness/readyzThe pool can run SELECT 1 in 500 ms, the schema is at least the binary's min_schema, and the binary's version is at least schema_compat.min_app_version.
startup/livezUp to 60 seconds for the first start.

goose's table gives the current schema. The one-row table schema_compat (min_app_version text NOT NULL) holds the oldest release that may still run. Only a contract migration raises it. A schema that is newer than the binary knows does not fail readiness: the pod logs WARN schema ahead and sets bembel_schema_ahead to 1.

Shutdown has a budget of 60 seconds (terminationGracePeriodSeconds: 60):

  1. The preStop hook sleeps 5 seconds, so the endpoints drain before the process gets SIGTERM.
  2. On SIGTERM the pod fails /readyz.
  3. It closes every GET /v1/events/stream at once, after it sends retry: 2000. The server context of the streams is cancelled through http.Server.RegisterOnShutdown. The clients reconnect to another pod with Last-Event-ID (REST API).
  4. Assistant streams (POST /v1/assistant/chats/{id}/messages) get event: error with {"code":"server.shutdown","retry":true}.
  5. http.Server.Shutdown waits at most 30 seconds for running requests.
  6. The workers cancel their context, so their transactions roll back. They stop within 10 seconds.

The total is 5 + 30 + 10 seconds, plus 15 seconds of margin: 60 seconds.

Workers

Each pod runs the API and the background workers. No pod is the leader. A worker takes one unit of work with a lock or a lease that PostgreSQL holds, so two pods do not do the same work. Workers act as built-in subjects (system:reaper, system:export, system:subject-sync, system:sync-fnt, system:sync-os-prod, system:ona-import). They have no bindings and fixed rights, and the audit log shows via = system (Access control).

Why PostgreSQL locks and not a leader election

The database is already the one shared part. A transaction lock ends with the transaction, so a crashed pod frees it at once. A lease row ends with its TTL of 2 minutes, so a crashed pod frees long work after at most 2 minutes. A leader election service is one more thing that can fail.

Transaction locks are only for work inside one short transaction. Anything longer uses a job_lease row. The pods reach PostgreSQL through PgBouncer in transaction mode, where a session lock (pg_advisory_lock) would stay on a server connection that another client uses next.

CREATE TABLE job_lease (name text PRIMARY KEY, holder text, until timestamptz NOT NULL DEFAULT '-infinity');
-- take or renew (TTL 2 minutes); no row back: another pod holds it
UPDATE job_lease SET holder = $pod, until = now() + interval '2 minutes'
 WHERE name = $1 AND (until < now() OR holder = $pod) RETURNING until;

-- export and feed builds, inside their one read-only transaction
SET LOCAL idle_in_transaction_session_timeout = '60s';
SELECT pg_try_advisory_xact_lock(hashtextextended('export:' || $kind || ':' || $target, 0));
SELECT pg_try_advisory_xact_lock(hashtextextended('feed:' || $group_name, 0));

A long job renews its lease every 30 seconds and inside each page transaction (500 objects). A renewal that returns no row aborts the run. Each run is recorded in sync_run. The stamper numbers the outbox rows after commit. So bembelseq is a gap-free, monotonic order number, assigned after commit, and a resume with Last-Event-ID or after_seq loses nothing (REST API). Its lag shows in bembel_outbox_oldest_age_seconds.

Rollout and zones

  • RollingUpdate with maxUnavailable: 0: a new pod must be ready before an old pod stops. With maxSurge: 1 a short 2/1/1 spread is allowed.
  • One pod per zone is enforced (whenUnsatisfiable: DoNotSchedule). During a zone outage the replacement pod goes to a remaining zone (2/1), because nodeTaintsPolicy: Honor leaves the tainted nodes of the failed zone out. Each pod is sized for 50 % of the peak, so two pods carry the load. The PostgreSQL instances also sit in separate zones (required anti-affinity).
  • A pod needs about 100 MB for 105 objects in its caches. Memory use stays flat, because lists are paged in PostgreSQL and not held in memory.
  • The connection pool of a pod is 20. The pool goes through the Pooler, so the number of pods does not change the number of server connections of PostgreSQL. Each pod also holds one direct connection for LISTEN.

Backup and restore

PostgreSQL is the only state. Exports, the UI and the help are built from it. A backup of the database is a backup of bembel.

The pgvector index and the other indexes are in the backup. The embeddings can be rebuilt from the objects if a restore is old. bembel embeddings rebuild does that.

Restore

# a new cluster at a point in time (for example before a bad bulk change)
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: bembel-db-restore
spec:
  instances: 1
  bootstrap:
    recovery:
      source: bembel-db
      recoveryTarget:
        targetTime: "2026-11-04 08:55:00+00"
  externalClusters:
    - name: bembel-db
      plugin:
        name: barman-cloud.cloudnative-pg.io
        parameters: { barmanObjectName: bembel-s3, serverName: bembel-db }
  1. Scale the Deployment to 0, or point the Ingress to a maintenance page.
  2. Create the restore cluster and a Pooler for it (bembel-db-restore-pooler-rw). Wait until both are ready.
  3. Check the data: bembel --db-url … audit tail and bembel migrate status.
  4. Point db.url at the Pooler of the restore cluster (bembel-db-restore-pooler-rw) and db.direct_url at bembel-db-restore-rw. Scale the Deployment up.
  5. Run bembel export build --all. The DNS and DHCP agents pull the restored state at the next poll.

An agent refuses a bundle with a lower snapshot than its current release (DNS). A restore to an earlier time can give lower snapshots and serials. The export build after a restore therefore works as a pin: it rolls forward, with a snapshot and serials above those that the agents report.

For a plain PostgreSQL, use pgBackRest or barman with the same schedule. The runbook is the same. The runbook also asks for a restore test every month: restore into a scratch cluster, run bembel migrate status and the read-only smoke test (bembel check).

What is not in the database

The config file, the secrets, the signing key of the release and the Keycloak data. The chart keeps the first two in Git (config) and in the secret store. Keycloak has its own backup.

Observability

Metrics

Prometheus metrics are on :9090/metrics, a separate port that the Ingress does not expose. The Go runtime and process collectors are on too. Label values are bounded: the label route is the route pattern (/v1/prefixes/{id}), never the real path. This table is the single list of bembel metrics. Other chapters use these names.

The freshness gauges (export, sync and feed) and the claim gauges come from database state, not from variables in the process. On each scrape every pod reads them in one query from the export target, source, address group and address rows (for example source.last_success_at and export_target.last_checked_at). BembelReplicasLow has three cases: 3 targets that are all down, no up series at all, and 1 of 3 targets up. Each case fires after 5 minutes. The or vector(0) makes the rule fire when no target is left.

Logs

bembel writes one JSON object per line on stdout (Go log/slog). Promtail and Grafana Alloy pick the lines up from the container log. Loki stores them. The format is the same for all components. Audit events are not logs: they stay in the database. An optional sink streams them to Loki or a SIEM (exports.audit_stream).

{"ts":"2026-11-04T09:13:02.771Z","level":"WARN","msg":"export check failed","app":"bembel","component":"export","kind":"dhcpd","target":"dhcp-a","reason":"dhcpd -t: duplicate fixed-address"}
{"ts":"2026-11-04T09:15:00.004Z","level":"ERROR","msg":"sync run failed","app":"bembel","component":"sync","source":"fnt","mode":"delta","error":"401 after re-login"}
{"ts":"2026-11-04T18:02:41.208Z","level":"INFO","msg":"request","app":"bembel","component":"api","request_id":"req_01JAZ4KQ9T","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","subject":"kc:a.berger","route":"POST /v1/prefixes/{id}/addresses:allocate","status":201,"duration_ms":14}
{"ts":"2026-11-04T18:02:41.210Z","level":"INFO","msg":"address allocated","app":"bembel","component":"api","request_id":"req_01JAZ4KQ9T","address":"10.20.4.213","prefix":"10.20.4.0/22","lock_wait_ms":3}
FieldRule
ts, level, msgAlways. ts is RFC 3339 in UTC with milliseconds. level is DEBUG, INFO, WARN, ERROR.
app, componentAlways. component is api, export, sync, reaper, outbox, assistant, migrate.
request_id, trace_idOn every line of a request. The request_id is also in the response header X-Request-Id and in the problem body.
subject, route, status, duration_msOn the request line. route is the pattern.

No log line holds a token, a password, a cookie, a prompt or an LLM answer. A line that logs a body logs only its size.

Loki labels

Use labels only for values with few distinct values: app, component, level (and namespace, pod from Kubernetes). Keep subject, route, request_id and trace_id in the line, and filter at query time with | json. A label for request_id would create a stream for each request and would make Loki slow.

# Alloy: promote three fields to labels
loki.process "bembel" {
  forward_to = [loki.write.default.receiver]
  stage.json   { expressions = { level = "level", component = "component", app = "app" } }
  stage.labels { values = { level = "", component = "", app = "" } }
}

# LogQL: server errors in the last hour, by route
sum by (route) (count_over_time({app="bembel", component="api"} | json | status >= 500 [1h]))

# LogQL: follow one request from a user report
{app="bembel"} | json | request_id="req_01JAZ4KQ9T"

Traces

bembel can send OpenTelemetry traces over OTLP (gRPC or HTTP). It is off until tracing.otlp_endpoint is set. A trace starts at the HTTP handler and covers the SQL queries (the otelpgx tracer), the calls to FNT Command and to the LLM service, and the export builds. bembel reads and writes the W3C header traceparent. The log field trace_id links the logs to the trace in Grafana. The default sample ratio is 5 %. Errors are always kept (tail sampling in the collector).

Upgrades

An upgrade must not stop the service. The old and the new version run together for a few minutes, so every schema change follows expand and contract.

  1. Read the release notes. Check the supported version path (one minor release at a time, or the stated range).
  2. Take a backup and wait until it ends: kubectl cnpg backup bembel-db --method plugin --plugin-name barman-cloud.cloudnative-pg.io --backup-name bembel-pre-1-1-0, then kubectl wait backup/bembel-pre-1-1-0 --for=jsonpath='{.status.phase}'=completed --timeout=30m.
  3. Run helm upgrade bembel oci://ghcr.io/dennisklein/charts/bembel --version 1.1.0 -f values.yaml.
  4. The hook Job runs bembel migrate up on db.direct_url. goose takes a session lock (pg_try_advisory_lock) on that direct connection, so a second Job waits.
  5. The rolling update replaces the pods. Watch kubectl rollout status deploy/bembel.
  6. Run helm test bembel (a smoke test: login with a test token, allocate and release in a test VRF).
RuleReason
A migration adds only: nullable columns, columns with a constant default, new tables and new indexes (CREATE INDEX CONCURRENTLY, outside a transaction).The old code still runs against the new schema.
A column leaves in two steps: stop to read and write it in release N, drop it in N+1 or later.Old pods can run while the Job drops the column.
A change of a column type is a new column, a backfill by a worker, a switch, and a later drop.No long lock on a large table.
A transactional migration starts with SET LOCAL lock_timeout = '3s'. A NO TRANSACTION migration runs SET lock_timeout = '3s' on the direct session. The Job retries (backoffLimit: 3).A queue behind a long query must not stop the API.
/readyz checks two things: the schema is at least the binary's min_schema, and the binary's version is at least schema_compat.min_app_version. CI runs the tests of release N against the schema of N+1.Old pods stay ready after an expand migration. A contract migration stops only the releases it breaks.
No down migrations in production. Roll back with the previous image; the schema stays. The previous image stays ready until a later contract migration raises min_app_version.A down migration loses data. Expand-only changes are safe for the old code.

The REST API is versioned under /v1 and changes only by addition (REST API). So an older bembel CLI, a bembel-agent or the Neutron driver works with a newer server. The agent also works one minor version behind. A PostgreSQL major upgrade uses the CloudNativePG procedure (imageName change with an in-place upgrade, or a new cluster by logical import). Test it on a restored copy first.

Security

AreaDesign
TLS to clientsThe Ingress terminates TLS with a cert-manager certificate (TLS 1.2 or 1.3). The pod can also serve TLS itself (tls.cert_file, tls.key_file) for the package form. HSTS is on.
TLS to the databasesslmode=verify-full with the CA of the CloudNativePG cluster, for the Pooler and for the direct connection. The user bembel owns the schema. No superuser at run time.
SecretsKubernetes secrets mounted as files, filled by External Secrets or sealed secrets. The config file holds only file names. The session key, the OIDC client secrets, the database URLs, the export signing key and the export tokens rotate without a release: bembel re-reads the files on SIGHUP and every 5 minutes. Rotating the session key ends the live UI sessions; users log in again.
Export signingbembel signs the manifest of each bundle with an Ed25519 key (exports.signing). An agent trusts up to two public keys, each named by its key_id (trust.keys), and checks signature, identity, snapshot and hashes (DNS). To rotate: add the new public key to every agent, switch signing to the new key, then remove the old key from the agents. The signature protects the transport and the ingress path. It does not protect against a compromised bembel pod that holds the key.
AgentsDefault: OIDC client credentials (a service identity at Keycloak, short tokens). Option: mTLS, with a client certificate from cert-manager and a CA that the config names. The agent can write only the VMs of its own source: a vm-provisioner binding on the subnets of its bridges, plus the source guard. See Access control.
Export pullA DNS, DHCP or OpenSM agent pulls the signed bundle of its own server with a token for that server. The token gives read access to that one bundle. The bundle URL has an ETag, so an unchanged bundle costs almost nothing.
Rate limitsA token bucket per subject: 50 requests per second, and 10 per second for :allocate. An anonymous client (the login and the health paths) is limited per IP to 20 per second. The answer is 429 with Retry-After. The limits are in the config.
Body and time limits4 MiB per request, 30 s per request (imports use an operation resource and a worker).
UI headersA strict Content Security Policy (below), X-Content-Type-Options: nosniff, Referrer-Policy: same-origin, Cross-Origin-Opener-Policy: same-origin. The session cookie bembel_session is HttpOnly; Secure; SameSite=Lax. Write calls carry the X-Bembel-Csrf header and get an Origin check.
AssistantThe LLM host is on the organisation's network. The assistant tools run with the rights of the user. No data goes to a third party (Assistant and help).
PodsNon-root user, read-only root file system, no capabilities, seccomp RuntimeDefault, no service account token mounted, a NetworkPolicy as above.
AuditEach change and each deny is an audit event in the database. Deletes of audit events are not possible through the API. The optional stream copies them to a SIEM.

Supply chain

  • SBOM. goreleaser makes an SPDX SBOM for the binary and for the image (with syft). The SBOM is a release asset and an OCI attestation.
  • Signed images and charts. The release workflow signs the image, the chart and the SBOM with cosign (keyless, OIDC identity of the GitHub workflow). It adds SLSA provenance.
  • Verify. cosign verify ghcr.io/dennisklein/bembel:1.0.0 --certificate-identity-regexp '^https://github.com/dennisklein/bembel/' --certificate-oidc-issuer https://token.actions.githubusercontent.com. A Kyverno or policy-controller rule can enforce this in the cluster.
  • Packages. The Debian and RPM repositories are signed with the release key.
  • Dependencies. govulncheck and pnpm audit run in CI. The base image is distroless and is rebuilt weekly.
