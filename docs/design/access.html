Access control

bembel is API first, so every client passes the same gate: an OpenID Connect identity, a set of scoped bindings and one SQL predicate. This chapter shows how a user or a service logs in, what a binding grants, how the database decides, and how dangerous changes get a second pair of eyes.

  • Authentication is outside: Keycloak for users, trusted issuers for services (Kubernetes, GitLab, GitHub). bembel stores no password.
  • Authorization is inside the database: roles are sets of kind:verb permissions, bindings give a role to a subject in a scope. Allow only in v1.
  • One predicate filters lists and checks single objects. It uses GiST containment on inet and ltree, so counts and pages are right.
  • A hidden object gives 404. A visible object without the permission gives 403 with the missing permission.
  • Four-eyes: a change request holds deleting a prefix tree, deleting a zone, bulk changes over 50 objects, a DHCP restart override, and creating, deleting or changing a privileged binding or role.
  • The audit log is append-only and records denies and the assistant as origin.

Principles

The rules below are binding for the design. Each one removes a class of error.

  1. One gate. The web UI, the CLI, the Neutron driver, the Kubernetes controllers and the assistant call the public REST API. There is no second path to the data.
  2. Identity from the IdP. bembel trusts a fixed list of issuers. It checks signature, issuer, audience and expiry. It keeps no password and no user directory.
  3. Permission is data. Roles, bindings and scopes are rows in PostgreSQL. A history table keeps every version. "Who could do what on this day" has an answer.
  4. Allow only. A request is allowed when at least one binding allows it. There is no deny rule in v1. A narrower binding is the way to limit access.
  5. The scope is a closed list. Seven scope types, each one a typed column with an index. There are no free expressions.
  6. Least surprise for lists. A list shows only what the user may read. Totals and pages are correct. Nothing leaks through counts, search or vectors.
  7. Grant only what you hold. A user can give a role only if the user holds it, and only inside the own scope.

Why not OpenFGA, SpiceDB, Cedar or OPA

The hard part of an IPAM is list filtering over a CIDR tree. Relationship services return lists of ids (OpenFGA caps them at 1 000 by default) and cannot test CIDR containment. Cedar has no partial evaluation in Go, and OPA compiles only a part of Rego to a filter. In the database the filter is a join. The code stays behind an Authorizer interface, so Cedar can add conditional rules later (v2).

Login: users, CLI and services

All paths end in the same thing: a verified token with an issuer, a subject id and (for users) groups. The API accepts Authorization: Bearer with a JWT of a trusted issuer or with a personal access token (tokens). Browser sessions are the exception: the cookie leads to a token in the server.

Browser: BFF session

The SvelteKit UI is static files. The Go binary serves it and acts as the backend for frontend (BFF). It is a confidential OIDC client of Keycloak (bembel-ui). It does the code exchange, keeps the tokens server side and gives the browser one cookie.

  • The cookie bembel_session is HttpOnly, Secure and SameSite=Lax, with Path=/. JavaScript cannot read it.
  • Each write call needs the header X-Bembel-Csrf with a value from GET /v1/me. The server also checks Origin.
  • The session lasts 8 hours idle and 24 hours absolute. bembel refreshes the access token with the refresh token. At each refresh it reads the groups again, so a removed group works at once after the refresh (at most 5 minutes).
  • Logout deletes the session row and calls the end-session endpoint of Keycloak.

The session store is a table in PostgreSQL. The cookie holds only a random id. The pods keep no session data, so any pod can answer any request.

CREATE TABLE ui_session (
  id_hash      bytea PRIMARY KEY,        -- sha256 of the cookie value (32 random bytes, base64url)
  subject_id   uuid NOT NULL REFERENCES subject(id),
  issuer       text NOT NULL,
  tokens       bytea NOT NULL,           -- access, refresh, ID token; AES-256-GCM, key auth.session.key_file
  csrf         bytea NOT NULL,           -- value of X-Bembel-Csrf
  created_at   timestamptz NOT NULL DEFAULT now(),
  last_seen_at timestamptz NOT NULL DEFAULT now(),   -- updated at most once per minute
  expires_at   timestamptz NOT NULL      -- created_at + absolute_timeout
);
  • The idle timeout is last_seen_at + PT8H. The absolute timeout is created_at + PT24H.
  • The built-in worker system:reaper deletes expired rows. A new session key ends the live sessions, and the users log in again.

CLI: device authorization grant

bembel login uses the device grant (RFC 8628). It works on a server without a browser: the user opens the URL on any device. A loopback code flow with PKCE (RFC 8252) is the fallback with --browser.

The CLI is a public client (bembel-cli), so it holds no secret. For scripts the user makes a personal access token and sets BEMBEL_TOKEN.

Services: trusted issuers

A service sends a JWT that its own platform issued. bembel validates it directly with the keys of the issuer (JWKS). There is no token exchange and no secret in the pod. The same code serves every case in the table below. A Keycloak client with client credentials is the exception for services outside a platform: it has a secret (Keycloak setup).

Prefer federation to long tokens

A projected service account token lives one hour and rotates. A CI token lives for one job. A personal access token lives for months. Use OIDC federation when the platform offers it.

Trusted issuers

The list of issuers is static configuration in /etc/bembel/bembel.yaml. bembel reloads it on SIGHUP and at each pod start. An unknown issuer gives 401. Why the audience is mandatory

A Kubernetes token for the default audience is valid for the API server of the cluster. Any pod could pass it to bembel if bembel accepted it. A dedicated audience bembel limits the token to this one use.

The libraries are coreos/go-oidc and lestrrat-go/jwx. The validator interface can accept cnf claims (DPoP, mTLS) later. v1 does not need them, because tokens are short and the BFF hides them from the browser.

Keycloak setup

Keycloak does not put the audience bembel in a token by default, and its group mapper writes the full group path by default. The realm main therefore needs this setup.

A client-credentials token belongs to the service-account user of the client. Its sub is the id of that user, and its preferred_username is service-account-<client id>. bembel applies a rule for the issuer kc: when preferred_username starts with service-account- and azp is not bembel-ui or bembel-cli, the subject has kind service, the key kc: + azp and the external id sub. So the client svc-agent-hv-03 gives the subject kc:svc-agent-hv-03, never a user subject.

Subjects

A subject is who acts. Bindings point at subjects. A request has several effective subjects: the user and each group of the token.

KindKeyMade fromExample
user<prefix><username>issuer + sub; the key shows preferred_usernamekc:d.klein
group<group_prefix><name>entry of the groups claim at each requestkc:netops
service<prefix><sub>issuer + sub of a machine token; kc: + azp for a Keycloak client-credentials token; svc:<name> for a local subject that owns a PAT; system:<worker> for a built-in workerk8s:prod-1:capi-system:capi-ipam, kc:svc-agent-hv-03, svc:fw-pan-01, system:reaper
CREATE TABLE subject (
  id          uuid PRIMARY KEY DEFAULT uuidv7(),
  kind        text NOT NULL CHECK (kind IN ('user','group','service')),
  issuer      text NOT NULL,            -- name from auth.issuers, or local, or system
  external_id text NOT NULL,            -- sub, the group name, or the local name
  key         text NOT NULL UNIQUE,     -- kc:d.klein, kc:netops, k8s:prod-1:...
  display     text,
  last_seen   timestamptz,
  disabled_at timestamptz,              -- set by system:subject-sync (see tokens)
  UNIQUE (issuer, kind, external_id)
);
  • A user row appears at the first login. A group row appears when a binding names it. bembel does not store group members. It reads groups from the token, or, for a PAT, from the IdP at use time (cached at most 5 minutes). So the IdP stays the one owner of membership.
  • A local service subject has the issuer local and a key svc:<name>, for example svc:fw-pan-01. It exists only to own personal access tokens. A caller with token:admin makes it with POST /v1/tokens and the field owner.
  • The built-in workers run inside bembel: system:reaper, system:export, system:subject-sync, system:sync-fnt, system:sync-os-prod and system:ona-import. They have no login and no bindings. Each has a fixed set of rights in code, and the audit log shows via = system. The sync and import workers write origin sync; the reaper, the export and the subject sync write origin system.
  • A binding for a service may end in * for the last segments, for example k8s:prod-1:capi-system:*. Users and groups take no wildcard.
  • Each team (hpc-ops) is also a group in the IdP. The team owns objects. The group kc:hpc-ops holds bindings. Both use the same name by convention, and the link is only the name.
  • Human users get their rights through groups where possible (kc:hpc-ops: b-0002, b-0003). A direct user binding is for exceptions.

The verb list is read create update delete allocate release traverse confirm build sync link apply approve revoke admin use. Nothing else exists: there is no write, reject, operate, claim, expire or run verb (claim is a kind), and there is no reservation kind (a DHCP reservation is a flag of an address).

  • *:read covers every kind except role, binding, token, audit, change-request, draft and vpn-session.
  • Claim actions. An allocate with claim_ttl and :renew need claim:create. :confirm needs claim:confirm. :release of a claimed address, and the expiry by the reaper, need claim:release. A direct allocate needs address:allocate. :release of an allocated or reserved address needs address:release.
  • traverse is an implied permission. Any binding that reaches a descendant gives traverse on its ancestors. The user then sees the parent as a stub (id, cidr, name) so the tree has a path. A stub shows no tags, no owner and no counts.
  • global only means that a narrower scope never matches. A binding with a vrf term gives nothing for view:read. The rule is safe by default: a term that does not apply to a kind makes the binding silent for that kind.
  • A permission string is stable API. The UI reads the list from GET /v1/roles to draw the role editor.

Source guard

An integration may change only the objects of its own source. Each row of the table source names at most one external service subject plus its own built-in worker.

  • A write by such a subject to an object whose source is another value gives 409 resource.managed.
  • A write to an object of a source by any subject that the source does not name also gives 409 resource.managed.

Bindings

A binding says: this subject has this role in this scope. It may have a start time and an expiry. The list of bindings of a subject is its rights.

CREATE TABLE binding (
  id            uuid PRIMARY KEY DEFAULT uuidv7(),
  subject_id    uuid NOT NULL REFERENCES subject(id),
  role_id       uuid NOT NULL REFERENCES role(id),
  -- scope terms: NULL means "no limit on this axis"; all NULL = global
  scope_vrf_id  uuid REFERENCES vrf(id),
  scope_cidr    cidr,
  scope_zone    ltree,            -- reversed labels: example.org = org.example
  scope_site    ltree,            -- site.building.floor.room...
  scope_team_id uuid REFERENCES team(id),
  scope_tag     jsonb,            -- {"role":"login"}
  not_before    timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz,
  suspended_at  timestamptz,      -- set when the binding fails the delegation test again
  reason        text,
  created_by    uuid NOT NULL REFERENCES subject(id),
  created_at    timestamptz NOT NULL DEFAULT now(),
  revision      bigint NOT NULL DEFAULT 1
);

The terms of one binding are joined by AND. Many bindings are joined by OR. At most one term of each type is allowed in one binding.

Delegation: grant only what you hold

The permission binding:create is not enough. bembel tests three more rules on each new binding. This stops privilege escalation by a person who manages bindings.

  1. The creator holds every permission of the role. The test uses the grants of the creator in the scope of the new binding.
  2. The new scope lies inside one grant of the creator for those permissions. A scope S' lies inside S when each term of S has a term in S' that is equal or narrower (a longer cidr, a deeper zone, the same team).
  3. The creator does not bind the own subject, and the expiry is not longer than the grant of the creator.

A team lead can therefore give allocator on 10.20.8.0/24 to a colleague, if the lead holds allocator on 10.20.0.0/16 with a binding:create role. The lead cannot give allocator on 10.30.0.0/16. A binding whose role holds a privileged permission always needs a change request.

  • A binding of a role that holds change-request:approve to a service subject is refused with 422 binding.approver-service. Approval is for a human user.
  • When a role changes, bembel tests each binding of that role again against the current grants of its creator. A binding that fails gets suspended_at = now(). It grants nothing, bembel sends the event binding.suspended, and the UI shows the warn pill "suspended".

Evaluation

The check for one object and the check for a list use the same function. The function takes the permission and the effective subjects and returns an SQL fragment.

  1. Read the grants: the bindings of the effective subjects that include the permission and are active.
  2. If one grant is global, the fragment is TRUE.
  3. Else, drop the grants whose terms do not apply to the kind, and join the rest by OR. Each grant becomes an AND of its terms.
  4. The caller adds the fragment to the query: WHERE ... AND (fragment). For one object it adds AND p.id = $id.
-- step 1: grants of the effective subjects for one permission
SELECT b.id, b.scope_vrf_id, b.scope_cidr, b.scope_zone, b.scope_site,
       b.scope_team_id, b.scope_tag
FROM binding b
JOIN role_permission rp ON rp.role_id = b.role_id
WHERE b.subject_id = ANY ($1::uuid[])
  AND rp.permission IN ('prefix:read', '*:read')
  AND b.not_before <= now()
  AND (b.expires_at IS NULL OR b.expires_at > now())
  AND b.suspended_at IS NULL;

SELECT p.*
FROM prefix p
WHERE p.vrf_id = $1                                     -- b1 vrf os-provider
   OR (p.vrf_id = $2 AND p.cidr <<= $3 AND p.owner = $4)  -- b2
   OR p.tags @> '{"role":"login"}'                      -- b3

CREATE INDEX prefix_tags      ON prefix USING gin  (tags jsonb_path_ops);

PostgreSQL combines the three branches with a BitmapOr over the indexes. A record query joins the zone: JOIN zone z ON z.id = r.zone_id WHERE z.path <@ 'org.example'. The cursor, the sort and the search filter stay in the same statement, so a page has no holes and the count is right. A guard caps the number of grants in one predicate (default 64). Above the cap, the grants go in a CTE with a lateral join.

allowed_actions

Each object in an answer has allowed_actions, for example ["read","update","allocate"]. The UI uses it to show buttons. The server checks again for each call. The list is made by one query per page with the grants as a table. It uses the same predicate builder (authz.Predicate) and the same grant rows as the list and point checks, after the narrowing of a PAT. A NULL term means no limit. A term that does not apply to the kind (here zone) makes the grant silent. This is the query for prefixes:

WITH g(verb, vrf_id, cidr, site, team_id, tag) AS (
  SELECT split_part(rp.permission, ':', 2), b.scope_vrf_id, b.scope_cidr,
         b.scope_site, b.scope_team_id, b.scope_tag
  FROM binding b JOIN role_permission rp ON rp.role_id = b.role_id
  WHERE b.subject_id = ANY ($1)
    AND (rp.permission LIKE 'prefix:%' OR rp.permission LIKE '*:%')
    AND b.scope_zone IS NULL                 -- zone does not apply to prefixes: silent
    AND b.not_before <= now()
    AND (b.expires_at IS NULL OR b.expires_at > now())
    AND b.suspended_at IS NULL
)
SELECT p.id,
       (SELECT array_agg(DISTINCT g.verb) FROM g
         WHERE (g.vrf_id  IS NULL OR g.vrf_id  = p.vrf_id)
           AND (g.cidr    IS NULL OR p.cidr    <<= g.cidr)
           AND (g.site    IS NULL OR p.site_path <@ g.site)
           AND (g.team_id IS NULL OR g.team_id = p.owner)
           AND (g.tag     IS NULL OR p.tags    @> g.tag)) AS allowed_actions
FROM prefix p
WHERE p.id = ANY ($2);

Caching

  • Grants are cached per replica, keyed by the set of subject ids and the binding epoch. The epoch is a counter that a trigger increments in the transaction of each binding or role change. The trigger sends NOTIFY binding_changed. Each replica listens on one dedicated direct connection (db.direct_url, not through PgBouncer, which does not pass LISTEN in transaction mode) and drops its cache. On a reconnect the replica listens again and reads the epoch once. While the listener is down, the replica reads the epoch every 30 seconds.
  • Decisions are not cached. The predicate runs in the same transaction and snapshot as the data it protects.
  • JWKS keys are cached until an unknown kid appears.
  • The directory answer for a PAT owner (enabled, groups) is cached per subject for at most 5 minutes (tokens).
  • An IdP group change takes effect at the next token refresh, and for a PAT within the directory cache (at most 5 minutes). A deleted binding takes effect in milliseconds while the listener is up, and within 30 seconds when it is down.

A differential test runs the predicate builder, the allowed_actions query and permissions:check against a plain Go function check(grants, object) on random data. A property test also runs the delegation rule. The explainer below shows the whole path for one request.

Explain a decision

POST /v1/me/permissions:check with "explain": true returns, for each check, every binding that bembel tested: its id, the subject it came through (via), the role, whether the role holds the permission, and the first scope term that failed (failed_term, or null). It also names the four-eyes rule that would hold the call (held_by) and the four-eyes state (four_eyes: ok, self or null). A user can explain the own identity. Change requests (four-eyes)

Some actions are hard to undo. bembel holds them in a change request until a second subject approves. bembel checks three times:

  • Proposal. A held call needs only the permission of the held action. bembel creates the request in the name of the caller. No other permission is needed to propose.
  • Approval. The approver needs change-request:approve on the target, and must be a human user (see below).
  • Execution. bembel checks the current grants of the proposer again, in the transaction that runs the call.
Action (rule code)Holds whenImpact shown to the approver
Delete a prefix (prefix.delete-with-children)The prefix has child prefixes or addressesCount of prefixes, addresses, records and reservations that go
Delete a zone (zone.delete)AlwaysCount of records, the servers that serve it
Bulk change (bulk.threshold)More than 50 objects in one call (access.change_request.bulk_threshold, default 50)Counts per kind, a diff of the first 20
Grant or remove a privileged binding (binding.privileged)Create or delete a binding whose role holds any permission in the privileged setSubject, role, scope, expiry, the privileged permissions
Change a role (role.privileged)POST /v1/roles or PUT /v1/roles/{name} that results in a role with a privileged permission; any PUT or DELETE /v1/roles/{name} of a role with active bindingsPermission diff, the affected bindings and subjects
DHCP restart override (dhcp.restart-override)POST /v1/dhcp-failover-pairs/{name}/restart-tickets with override: true (needs dhcp-server:update)Partner state, MCLT, impact (DHCP)

The privileged set is role:create, role:update, role:delete, binding:create, binding:delete, token:admin, source:update, audit:read and change-request:approve. The test runs after bembel expands *, so a custom role with binding:* is privileged too. A role edit also starts the delegation test of its bindings again (delegation).

The admin can add rules in the config (for example "delete a VRF"). The six rules above are the default and cannot be switched off.

  1. A user sends the call, for example DELETE /v1/zones/{id}. bembel sees that the action is held.
  2. bembel stores the request (method, path, body, the revision of the target) and answers 202 Accepted with the change request and a Location header.
  3. An event change-request.created goes to the approvers (UI badge, webhook, mail).
  4. An approver reads the impact and calls POST /v1/change-requests/{id}:approve. bembel refuses the call in these cases:
    • The approver is the proposer: 403 change-request.self-approval. A SQL check also rejects it: CHECK (approver_id IS DISTINCT FROM proposer_id).
    • The approver is not a human user: 403 change-request.approver-kind. change-request:approve is effective only for a subject of kind user with token_kind session or oidc, and never for a Keycloak client-credentials token. bembel tests this on the effective grants, so it also covers admin and wildcard service bindings. This closes the case of one person who controls a user and a CI or service identity.
    • The call runs inside a draft apply or has origin=assistant: 403 change-request.origin. The same rule applies to :reject.
  5. bembel runs the stored call in one transaction, as the proposer. First it evaluates the current grants of the proposer for the held permission on the target: bindings, groups, expiry, suspension, a disabled subject and the narrowing of a PAT. If they no longer give the permission, the state becomes failed with 409 change-request.proposer-forbidden and nothing changes. If the target revision changed since the proposal, the state becomes failed with 409 change-request.stale and nothing changes. The proposer then submits a new request.
  6. The audit event names the proposer, the approver and the change request.

The states are pending, approved, executed, failed, rejected, withdrawn and expired. A client that cannot handle 202 sends Bembel-Change-Request: never. It then gets 409 change-request.required. A request waits 7 days (expired). The proposer can withdraw it with :withdraw. When a subject is disabled, all its pending requests become failed with change-request.proposer-forbidden. The assistant never approves, and a PAT never approves.

Break-glass access

All logins go through the IdP. When the IdP is down, no one can log in, and a PAT of a user also fails closed (503 auth.directory-unavailable). A break-glass session is the way in for that case.

$ sudo -u bembel bembel admin break-glass --user d.klein --reason "Keycloak down, INC-4471"
break-glass session for local:breakglass:d.klein
  role admin, scope global, expires 2026-11-05T15:42:00Z (1 h)
  open https://ipam.example.org/break-glass#bgs_Qm9…  (shown once)
  • The command runs on a bembel server host as the service user. It needs the database credentials of the config file, so it needs shell access to the host. No API call can make a break-glass session.
  • The session belongs to the subject local:breakglass:<name> of kind user and issuer local. It has the built-in role admin with global scope, a life of 1 hour (maximum 4 hours with --ttl) and no refresh.
  • The reason is required. The audit log shows via = break-glass and the reason on every call of the session.
  • The alert BembelBreakGlassUsed fires at the start of the session and goes to all admins by mail (alerts).
  • The session does not skip change requests. A second person with a break-glass session can approve, because the approver is a different human user.
  • bembel admin break-glass --revoke-all ends all break-glass sessions. Do this when the IdP is back.

The audit log has two levels of read:

  • With audit:read (global): every event and every filter. network-admin and admin have it.
  • Without it: only allow and pending events whose resource the caller can read now (<resource_kind>:read on the current row; events of deleted objects are not returned). The answer has no deny events, and the actor filter may name only the caller. A query for decision=deny or another actor gives 403 permission.denied. The dashboard, the history of an object and the assistant use this mode: GET /v1/audit-events?resource_kind=address&resource_id={id}.
  • The application role has INSERT only. A trigger blocks UPDATE and DELETE. A second role reads.
  • Partitions are monthly. The default keeps 13 months online. Older partitions detach and go to cold storage.
  • An optional hash chain per partition proves that no row went missing. An optional stream sends each event as JSON to Loki or a SIEM. The audit events are not application logs.
