Access control

bembel is API first, so every client passes the same gate: an OpenID Connect identity, a set of scoped bindings and one SQL predicate. This chapter shows how a user or a service logs in, what a binding grants, how the database decides, and how dangerous changes get a second pair of eyes.

  • Authentication is outside: Keycloak for users, trusted issuers for services (Kubernetes, GitLab, GitHub). bembel stores no password.
  • Authorization is inside the database: roles are sets of kind:verb permissions, bindings give a role to a subject in a scope. Allow only in v1.
  • One predicate filters lists and checks single objects. It uses GiST containment on inet and ltree, so counts and pages are right.
  • A hidden object gives 404. A visible object without the permission gives 403 with the missing permission.
  • Four-eyes: a change request holds deleting a prefix tree, deleting a zone, bulk changes over 50 objects and changing an admin binding.
  • The audit log is append-only and records denies and the assistant as origin.

Principles

The rules below are binding for the design. Each one removes a class of error.

  1. One gate. The web UI, the CLI, the Neutron driver, the Kubernetes controllers and the assistant call the public REST API. There is no second path to the data.
  2. Identity from the IdP. bembel trusts a fixed list of issuers. It checks signature, issuer, audience and expiry. It keeps no password and no user directory.
  3. Permission is data. Roles, bindings and scopes are rows in PostgreSQL. A history table keeps every version. "Who could do what on this day" has an answer.
  4. Allow only. A request is allowed when at least one binding allows it. There is no deny rule in v1. A narrower binding is the way to limit access.
  5. The scope is a closed list. Seven scope types, each one a typed column with an index. There are no free expressions.
  6. Least surprise for lists. A list shows only what the user may read. Totals and pages are correct. Nothing leaks through counts, search or vectors.
  7. Grant only what you hold. A user can give a role only if the user holds it, and only inside the own scope.

Why not OpenFGA, SpiceDB, Cedar or OPA

The hard part of an IPAM is list filtering over a CIDR tree. Relationship services return lists of ids (OpenFGA caps them at 1 000 by default) and cannot test CIDR containment. Cedar has no partial evaluation in Go, and OPA compiles only a part of Rego to a filter. In the database the filter is a join. The code stays behind an Authorizer interface, so Cedar can add conditional rules later (v2).

Login: users, CLI and services

All paths end in the same thing: a verified token with an issuer, a subject id and (for users) groups. The API accepts Authorization: Bearer with a JWT of a trusted issuer or with a personal access token (tokens). Browser sessions are the exception: the cookie leads to a token in the server.

Browser: BFF session

The SvelteKit UI is static files. The Go binary serves it and acts as the backend for frontend (BFF). It is a confidential OIDC client of Keycloak (bembel-ui). It does the code exchange, keeps the tokens server side and gives the browser one cookie.

  • The cookie is HttpOnly, Secure and SameSite=Lax. JavaScript cannot read it.
  • Each write call needs the header X-Bembel-Csrf with a value from GET /v1/me. The server also checks Origin.
  • The session lasts 8 hours idle and 24 hours absolute. bembel refreshes the access token with the refresh token. At each refresh it reads the groups again, so a removed group works at once after the refresh (at most 5 minutes).
  • Logout ends the session and calls the end-session endpoint of Keycloak.

CLI: device authorization grant

bembel login uses the device grant (RFC 8628). It works on a server without a browser: the user opens the URL on any device. A loopback code flow with PKCE (RFC 8252) is the fallback with --browser.

The CLI is a public client (bembel-cli), so it holds no secret. For scripts the user makes a personal access token and sets BEMBEL_TOKEN.

Services: trusted issuers

A service sends a JWT that its own platform issued. bembel validates it directly with the keys of the issuer (JWKS). There is no token exchange and no secret in the pod. The same code serves four cases.

Prefer federation to long tokens

A projected service account token lives one hour and rotates. A CI token lives for one job. A personal access token lives for months. Use OIDC federation when the platform offers it.

Trusted issuers

The list of issuers is static configuration in config.yaml. bembel reloads it on SIGHUP and at each pod start. An unknown issuer gives 401. Trust is per issuer, so the same service account name in two clusters gives two different subjects.

Why the audience is mandatory

A Kubernetes token for the default audience is valid for the API server of the cluster. Any pod could pass it to bembel if bembel accepted it. A dedicated audience bembel limits the token to this one use.

The libraries are coreos/go-oidc and lestrrat-go/jwx. The validator interface can accept cnf claims (DPoP, mTLS) later. v1 does not need them, because tokens are short and the BFF hides them from the browser.

Subjects

A subject is who acts. Bindings point at subjects. A request has several effective subjects: the user and each group of the token.

KindKeyMade fromExample
user<prefix><username>issuer + sub; the key shows preferred_usernamekc:d.klein
group<group_prefix><name>entry of the groups claim at each requestkc:netops
service<prefix><sub>issuer + sub of a machine token, or the owner of a personal access tokenk8s:prod-1:capi-system:capi-ipam
CREATE TABLE subject (
  id          uuid PRIMARY KEY DEFAULT uuidv7(),
  kind        text NOT NULL CHECK (kind IN ('user','group','service')),
  issuer      text NOT NULL,            -- name from auth.issuers
  external_id text NOT NULL,            -- sub, or the group name
  key         text NOT NULL UNIQUE,     -- kc:d.klein, kc:netops, k8s:prod-1:...
  display     text,
  last_seen   timestamptz,
  UNIQUE (issuer, kind, external_id)
);
  • A user row appears at the first login. A group row appears when a binding names it. bembel does not copy group members. It reads the groups from each token, so the IdP stays the one owner of membership.
  • A binding for a service may end in * for the last segments, for example k8s:prod-1:capi-system:*. Users and groups take no wildcard.
  • Each team (hpc-ops) is also a group in the IdP. The team owns objects. The group kc:hpc-ops holds bindings. Both use the same name by convention, and the link is only the name.
  • Human users get their rights through groups where possible (kc:netops). A direct user binding is for exceptions.

A role is a named set of permissions. Seven roles are built in and cannot change. An admin can add custom roles with the same permission strings.

Admin is not a bypass

admin still has a scope, and it does not skip change requests. Delete of a zone needs a second subject also for an admin. The first bootstrap admin comes from the config key auth.bootstrap_admins and is audited.

A custom role is a row set. The libvirt agent of a hypervisor uses one. It may take addresses and make VM hosts, and nothing else.

Bindings

A binding says: this subject has this role in this scope. It may have a start time and an expiry. The list of bindings of a subject is its rights.

CREATE TABLE binding (
  id            uuid PRIMARY KEY DEFAULT uuidv7(),
  subject_id    uuid NOT NULL REFERENCES subject(id),
  role_id       uuid NOT NULL REFERENCES role(id),
  -- scope terms: NULL means "no limit on this axis"; all NULL = global
  scope_vrf_id  uuid REFERENCES vrf(id),
  scope_cidr    cidr,
  scope_zone    ltree,            -- reversed labels: example.org = org.example
  scope_site    ltree,            -- site.building.floor.room...
  scope_team_id uuid REFERENCES team(id),
  scope_tag     jsonb,            -- {"role":"login"}
  not_before    timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz,
  reason        text,
  created_by    uuid NOT NULL REFERENCES subject(id),
  created_at    timestamptz NOT NULL DEFAULT now(),
  revision      bigint NOT NULL DEFAULT 1
);

The API shows the scope as a list of typed terms. Here is the binding of a.berger.

POST /v1/bindings
{
  "subject": "kc:a.berger",
  "role": "allocator",
  "scope": [
    {"type": "prefix", "value": "10.20.0.0/16", "vrf": "global"},
    {"type": "team",   "value": "hpc-ops"}
  ],
  "expires_at": "2027-11-04T00:00:00Z",
  "reason": "HPC operations of Hall 2"
}

The terms of one binding are joined by AND. Many bindings are joined by OR. At most one term of each type is allowed in one binding.

Delegation: grant only what you hold

The permission binding:create is not enough. bembel tests three more rules on each new binding. This stops privilege escalation by a person who manages bindings.

  1. The creator holds every permission of the role. The test uses the grants of the creator in the scope of the new binding.
  2. The new scope lies inside one grant of the creator for those permissions. A scope S' lies inside S when each term of S has a term in S' that is equal or narrower (a longer cidr, a deeper zone, the same team).
  3. The creator does not bind the own subject, and the expiry is not longer than the grant of the creator.

A team lead can therefore give allocator on 10.20.8.0/24 to a colleague, if the lead holds allocator on 10.20.0.0/16 with a binding:create role. The lead cannot give allocator on 10.30.0.0/16. A binding with the role admin always needs a change request.

  • An address or a claim takes the owner of its subnet when the request gives no owner. The server writes the value, so the team term works on each row without a join.
  • A record takes its scope from its zone. A derived record (A, AAAA, PTR) is also under the scope of the address that made it. Only manual records are writable.

Evaluation

The check for one object and the check for a list use the same function. The function takes the permission and the effective subjects and returns an SQL fragment.

  1. Read the grants: the bindings of the effective subjects that include the permission and are active.
  2. If one grant is global, the fragment is TRUE.
  3. Else, drop the grants whose terms do not apply to the kind, and join the rest by OR. Each grant becomes an AND of its terms.
  4. The caller adds the fragment to the query: WHERE ... AND (fragment). For one object it adds AND p.id = $id.
-- step 1: grants of the effective subjects for one permission
SELECT b.id, b.scope_vrf_id, b.scope_cidr, b.scope_zone, b.scope_site,
       b.scope_team_id, b.scope_tag
FROM binding b
JOIN role_permission rp ON rp.role_id = b.role_id
WHERE b.subject_id = ANY ($1::uuid[])
  AND rp.permission IN ('prefix:read', '*:read')
  AND b.not_before <= now()
  AND (b.expires_at IS NULL OR b.expires_at > now());

The next query shows the result for a user with three bindings: vrf=os-provider; prefix=10.20.0.0/16 AND team=hpc-ops; tag=role:login. Go builds the text from typed values. It passes every value as a parameter.

SELECT p.*
FROM prefix p
WHERE p.vrf_id = $1                                     -- b1 vrf os-provider
   OR (p.vrf_id = $2 AND p.cidr <<= $3 AND p.owner_team_id = $4)  -- b2
   OR p.tags @> '{"role":"login"}'                      -- b3
ORDER BY p.cidr, p.id
LIMIT 101;

-- supporting indexes
CREATE INDEX prefix_vrf_cidr  ON prefix USING gist (vrf_id, cidr inet_ops);  -- btree_gist
CREATE INDEX prefix_tags      ON prefix USING gin  (tags jsonb_path_ops);
CREATE INDEX prefix_owner     ON prefix (owner_team_id);
CREATE INDEX zone_path        ON zone   USING gist (path);                    -- ltree
CREATE INDEX host_site_path   ON host   USING gist (site_path);

PostgreSQL combines the three branches with a BitmapOr over the indexes. A record query joins the zone: JOIN zone z ON z.id = r.zone_id WHERE z.path <@ 'org.example'. The cursor, the sort and the search filter stay in the same statement, so a page has no holes and the count is right. A guard caps the number of grants in one predicate (default 64). Above the cap, the grants go in a CTE with a lateral join.

allowed_actions

Each object in an answer has allowed_actions, for example ["read","update","allocate"]. The UI uses it to show buttons. The server checks again for each call. The list is made by one query per page with the grants as a table. A NULL term means no limit.

WITH g(verb, vrf_id, cidr, team_id, tag) AS (
  SELECT split_part(rp.permission, ':', 2), b.scope_vrf_id, b.scope_cidr,
         b.scope_team_id, b.scope_tag
  FROM binding b JOIN role_permission rp ON rp.role_id = b.role_id
  WHERE b.subject_id = ANY ($1) AND rp.permission LIKE 'prefix:%' AND (b.expires_at IS NULL OR b.expires_at > now())
)
SELECT p.id,
       (SELECT array_agg(DISTINCT g.verb) FROM g
         WHERE (g.vrf_id  IS NULL OR g.vrf_id  = p.vrf_id)
           AND (g.cidr    IS NULL OR p.cidr    <<= g.cidr)
           AND (g.team_id IS NULL OR g.team_id = p.owner_team_id)
           AND (g.tag     IS NULL OR p.tags    @> g.tag)) AS allowed_actions
FROM prefix p
WHERE p.id = ANY ($2);

Caching

  • Grants are cached per replica, keyed by the set of subject ids and the binding epoch. The epoch is a counter that a trigger increments in the transaction of each binding or role change. The trigger sends NOTIFY binding_changed. Each replica listens and drops its cache. A replica that loses the connection reads the epoch every 30 seconds.
  • Decisions are not cached. The predicate runs in the same transaction and snapshot as the data it protects.
  • JWKS keys are cached until an unknown kid appears.
  • An IdP group change takes effect at the next token refresh (at most 5 minutes). A deleted binding takes effect in milliseconds.

A differential test runs the predicate builder against a plain Go function check(grants, object) on random data. A property test also runs the delegation rule. The explainer below shows the whole path for one request.

Explain a decision

POST /v1/me/permissions:check with "explain": true returns the grants that matched and, for the first failed grant, the first term that failed. A user can explain the own identity. An admin can pass "subject". The UI "Explain my access" button and the assistant use it.

The intersection works on grant rows. For each grant of the owner, bembel keeps the verbs that the token lists. For each scope axis, it takes the narrower term. When the two terms do not overlap (cidr 10.20.0.0/16 and a token cidr 10.30.0.0/16), the grant drops out.

Change requests (four-eyes)

Some actions are hard to undo. bembel holds them in a change request until a second subject approves. The check at proposal needs the normal permission. The check at approval needs change-request:approve on the target.

ActionHolds whenImpact shown to the approver
Delete a prefixThe prefix has child prefixes or addressesCount of prefixes, addresses, records and reservations that go
Delete a zoneAlwaysCount of records, the servers that serve it
Bulk changeMore than 50 objects in one call (access.change_request.bulk_threshold)Counts per kind, a diff of the first 20
Change a binding with role adminCreate, change or deleteSubject, scope, expiry

The admin can add rules in the config (for example "delete a VRF"). The four rules above are the default and cannot be switched off.

  1. A user sends the call, for example DELETE /v1/zones/{id}. bembel sees that the action is held.
  2. bembel stores the request (method, path, body, the revision of the target) and answers 202 Accepted with the change request and a Location header.
  3. An event change-request.created goes to the approvers (UI badge, webhook, mail).
  4. An approver reads the impact and calls POST /v1/change-requests/{id}:approve. A SQL check rejects the same subject: CHECK (approver_id IS DISTINCT FROM proposer_id).
  5. bembel runs the stored call in one transaction. If the target revision changed since the proposal, the state becomes failed and nothing changes.
  6. The audit event names the proposer, the approver and the change request.

A client that cannot handle 202 sends Bembel-Change-Request: never. It then gets 409 change-request.required. A request waits 7 days (expired). The proposer can withdraw it. The assistant never approves, and a PAT never approves.

Audit log

An audit event is an append-only record. bembel writes it in the transaction of the change, so a change without an event cannot exist. It also records each deny.

Walk-through 1: a.berger allocates, and one request is hidden

  1. a.berger runs bembel address allocate --prefix 10.20.4.0/22. The call is POST /v1/prefixes/{id}/addresses:allocate.
  2. The token passes. The effective subjects are kc:a.berger and kc:hpc-ops.
  3. The grants for address:allocate: binding …a1, role allocator, scope prefix 10.20.0.0/16 AND team hpc-ops.
  4. The predicate on the prefix row 10.20.4.0/22 is true: the VRF is global, the cidr lies inside 10.20.0.0/16, the owner is hpc-ops. The allocation runs. The address is 10.20.4.44.
  5. Now she tries the subnet 10.20.8.0/24 (osprey-gpu, owner gpu-ops). The cidr term is true, the team term is false. No grant allows prefix:read on the row, so the answer is 404. The audit log records a deny.

Walk-through 2: capi-ipam in the wrong place

  1. The controller sends POST /v1/claims for the prefix 10.30.4.0/24 with a service token. The scope is prefix 10.30.0.0/16: allowed, 201.
  2. A fault in a cluster object makes it ask for a claim in 10.20.4.0/22. The cidr is outside 10.30.0.0/16, so the service cannot read the prefix. The answer is 404 and the problem type is resource.not-found.
  3. The controller then sends DELETE /v1/prefixes/{id} for 10.30.4.0/24. It can read the prefix (allocator has prefix:read) but not prefix:delete. The answer is 403 permission.denied with "required_permission": "prefix:delete".

Walk-through 3: delete a zone with four eyes

  1. d.klein sends DELETE /v1/zones/{id} for kestrel.example.org. He holds zone:delete through network-admin.
  2. The zone has 1 204 records, so the action is held. bembel answers 202 with change request cr-0412 and the impact.
  3. d.klein opens POST /v1/change-requests/cr-0412:approve. The answer is 403: the approver must differ from the proposer, and he has no approver role.
  4. m.huber holds approver on zone example.org. The zone kestrel.example.org lies under that path. He reads the impact and approves.
  5. bembel checks the revision of the zone, deletes it and its records in one transaction, and removes the zone from the next BIND export. The audit event names d.klein as proposer, m.huber as approver and cr-0412.

Test the rights before you grant them

Run bembel access check --as kc:a.berger address:allocate prefix/10.20.8.0/24 (needs audit:read). The answer lists the grants and the first term that failed.
