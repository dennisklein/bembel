Routing and firewall

This chapter specifies how bembel serves the routing and firewall teams. bembel owns the values: AS numbers, route distinguishers, route targets, static routes, announced prefixes and groups of addresses. It does not own device config. It exports the values in formats that the existing tools read.

  • bembel stores ASNs with ranges, VRF route distinguishers and route targets, static routes, and the announce flag with tags on prefixes.
  • bembel export prefix-list --format frr|bird|junos|eos writes the prefix lists of the prefixes with the announce flag. The API gives a JSON routing intent for each VRF.
  • An address group is a named, dynamic set of addresses and prefixes, defined by a filter. Examples: login-nodes, ceph-public.
  • An address group is served as a feed: an nftables set file, a firewalld ipset XML, a plain text list for Palo Alto, OPNsense and FortiGate, or JSON.
  • Feeds use HTTPS, a token or mutual TLS, and ETag. Safety guards stop an empty list or a large sudden change.
  • Firewall policy, route maps and BGP sessions stay in Ansible, Nornir and the vendor tools.

Scope: values, not config

Network teams already have a way to push config. They use Ansible, Nornir or vendor tools. These tools need numbers and lists that a person types today: the AS number of a cluster, the prefixes that a router announces, the addresses that a firewall rule allows. These values are already in the IPAM, or should be. bembel is the source of truth for them. A generator in the automation reads them and renders device config.

bembel ownsThe network automation owns
ASN numbers and ASN ranges, who uses whichBGP sessions, neighbours, route maps, communities policy

The consumers have different needs. A router change needs a review by a user, so the automation pulls the export, shows a diff and applies it with a commit-confirm. A firewall address list changes often and by itself (a new login node), so the firewall pulls its feed on a timer. Both paths use the same safety rules (feeds).

AS numbers

An ASN object has the number, a name, a kind and an owner team. The kind is private, public or peer. An ASN range is a named span of numbers with a purpose and an owner. A range lets bembel allocate the next free number, like it does for addresses.

RangeSpanKindOwnerUse
campus65010private (2 byte)networkThe campus network. One number.
cluster-private4200000000 to 4294967294private (4 byte, RFC 6996)hpc-opsOne ASN for each cluster fabric, or one for each leaf switch.
peers64496 to 64511peer (documentation range, RFC 5398)networkUpstream and peer networks. The example uses the documentation range.
 
$ bembel asn allocate --range cluster-private --name kestrel-fabric --owner hpc-ops
allocated AS4200000001  kestrel-fabric   range cluster-private   owner hpc-ops
$ bembel asn allocate --range cluster-private --name osprey-fabric --owner hpc-ops
allocated AS4200000002  osprey-fabric    range cluster-private   owner hpc-ops

4200000002  osprey-fabric    hpc-ops  fabric osprey-roce, 8 hosts

An ASN is linked to other objects:

VRF
default_asn: the local AS of the VRF, if all routers of the VRF use one.
Host
bgp_asn: the local AS of a router or a switch. The default is the ASN of the VRF.
Prefix
origin_asn: the AS that announces it. The default is the ASN of the VRF. Needed for RPKI or IRR exports later.
Fabric
asn: the ASN of a fabric, for example osprey-roce.

The checks are simple. A number must lie in a range, or the user must say --no-range. A number is unique. A private number cannot be used for a prefix with the status announce in the VRF global without an ASN of the kind public in the path (a warning, not an error, because the border router may remove the private AS).

VRF, route distinguisher and route targets

A VRF is an independent address space. For a router it is also a routing table. Two more values describe the VRF in MPLS or EVPN networks: the route distinguisher (RD), which makes the prefixes of different VRFs unique in BGP, and the route targets (RT), which say which VRFs import and export which routes.

VRFRDExport RTImport RTDefault ASN
globalnone (default table)65010:1 (shared-services, through the border leak policy)none65010
hpc-fabric65010:10065010:10065010:1004200000001
oob65010:90065010:90065010:90065010
os-provider65010:30065010:30065010:300, 65010:165010
  • An RD has the form ASN:number (2 byte ASN, 4 byte number), IPv4:number or 4byteASN:number (4 byte ASN, 2 byte number). bembel checks the form and the range of the numbers.
  • An RD is unique. A second VRF with the same RD is an error.
  • A route target is an object with a value, a name and an owner. A VRF has a list of import RTs and a list of export RTs. One RT can belong to many VRFs. The RT 65010:1 is named shared-services. The border leak policy exports the shared-services prefixes of global with it, so bembel stores it on global as an export RT. The VRF os-provider imports it.
  • The VRF global has no RD: it is the default table. A site that exports global routes in a VPN gives it one.

Leaks and overlaps

The database allows the same CIDR in two VRFs. A route target that leaks routes between the two VRFs makes the overlap a real conflict. bembel checks this: if VRF A imports an RT that VRF B exports, and both have an equal or overlapping prefix, the check gives the finding vrf.leak-overlap with both prefixes. The check runs on every change of an RT list or a prefix.

Static routes and announced prefixes

Static routes

A static route is data, not config. It has these fields:

FieldMeaning
vrfThe VRF of the route.
destinationA prefix, IPv4 or IPv6. It does not need to be an object in the tree, but if it is, bembel links it.
next_hopAn address, or blackhole, or an interface name of a host. An address must lie in a subnet of next_hop_vrf.
next_hop_vrfDefault: the VRF of the route. A different VRF makes a leak.
metricOptional number. The automation maps it to a distance.
owner, tags, descriptionAs for all objects.
 
- vrf: hpc-fabric
  destination: 10.110.0.0/16            # osprey-roce, reached through the border pair
  next_hop: 10.100.0.2
  metric: 10
  owner: hpc-ops
  description: kestrel to osprey, via ib-gw-a01
- vrf: global
  destination: 10.200.0.0/16            # OpenStack tenant space (VRF os-provider)
  next_hop: 10.30.128.5                 # the OpenStack router, in the floating subnet
  tags: { announce: campus-bgp }
  owner: openstack
- vrf: oob
  destination: 0.0.0.0/0
  next_hop: 172.16.4.1
  owner: network

The checks: the next hop is reachable (inside a subnet of the VRF, and not a network or broadcast address), the next hop is not inside the destination (no loop), and no two routes with the same VRF and destination have the same metric (a warning). A static route with a next hop that is an address of a managed host shows the host name in the UI.

Announce flag and tags

A prefix has the boolean announce and tags. The tag announce=NAME names the announcement set: the group of prefixes that go to the same BGP peers. The flag says "this prefix should leave the VRF". The tag says where.

A prefix with announce=true and no tag is a finding, so nobody announces something by mistake. A load-balancer pool that the Kubernetes manager reserves can carry the tag too (load-balancer pools).

Prefix lists

A prefix list export turns the announced prefixes into the filter list of a router. The definition is an object:

name: campus-bgp
vrf: global
select:
  announce: true
  tags: { announce: campus-bgp }
  status: [active, reserved]
options:
  include_containers: true       # a container with announce=true is an aggregate
  ge: none                       # exact match; or: { v4: 24, v6: 64 }
  le: none
  seq_start: 10
  seq_step: 10

The export has a fixed order (family, then address, then length), so the same input always gives the same bytes. The API path is GET /v1/exports/{id}/artifact?format=frr|bird|junos|eos&family=4|6, where {id} is the export id or its name, for example GET /v1/exports/campus-bgp/artifact?format=frr&family=4. The CLI does the same and can show a diff against the last revision:

$ bembel export prefix-list campus-bgp --format frr --family 4 --diff
revision 57 → 58   (etag "5b0e1c")
+ ip prefix-list BEMBEL-CAMPUS-BGP-V4 seq 40 permit 10.20.20.0/24
1 entry added, 0 removed, 3 unchanged

The syntax above is a short form. The vendor documents are the reference, and the format tests of bembel run each file through the check tool of its platform (vtysh -C, bird -p, commit check on a lab device, an EOS container). The ge and le options render as ge 24 le 32 in FRR and EOS, and as {24,32} in BIRD. A Junos prefix list has no ranges, so the junos format writes a route-filter-list with prefix-length-range when ge or le is set. That list also carries replace: and is loaded with load replace. The Junos format test loads revision N, then revision N+1 with one prefix removed, on a lab vMX. The prefix must be gone from show configuration policy-options.

The lists carry no policy. A route map or a filter in the device config uses them by name. The names (BEMBEL-CAMPUS-BGP-V4) are stable, so the policy does not change when the content changes.

Address groups

An address group is a named set of addresses and prefixes. A filter defines it. The set is not a list that a person edits. bembel computes it from the data, so it is always right: a new login node is in the group as soon as its host has the tag.

# login-nodes: all addresses of hosts with the tag role=login in the VRF global
name: login-nodes
owner: hpc-ops
description: Login nodes of all clusters
families: [4, 6]
members:
  - from: hosts
    where: { tags: { role: login }, vrf: global }
    take: addresses                    # all addresses of all interfaces in this VRF
exclude:
  - { address: 10.20.4.99 }            # the shared login VIP, not a node
limits: { min: 2, max: 200 }
---
# ceph-public: the subnet
name: ceph-public
owner: hpc-ops
families: [4]
members:
  - from: prefixes
    where: { name: ceph-public, vrf: global }     # 10.20.12.0/24
---
# admin-targets: the BMC subnets of VRF oob plus the login nodes of VRF global (two VRFs on purpose)
name: admin-targets
owner: network
cross_vrf: true
members:
  - from: prefixes
    where: { vrf: oob, prefix_kind: subnet, tags: { role: bmc } }     # 172.16.4.0/22
  - include: login-nodes
Field of whereSelects
vrfRequired. A group's members share one VRF unless the group sets cross_vrf: true.
tagsObjects with all given tags.
teamObjects that the team owns.
role, host_kind, prefix_kindHost role (login, compute), host kind (physical, vm), prefix kind (container, subnet).
siteObjects at the site or below it.
name, fabric, statusName of a prefix, fabric of a subnet, status of the object. The default status excludes planned and deprecated.

The rules of the evaluation:

  1. All terms in one where must be true (AND). Several entries in members are joined (OR).
  2. take: addresses collects the addresses of the interfaces of the hosts. take: prefixes takes the prefix of the object itself.
  3. include adds the members of another group. bembel refuses a cycle. If the included group has another VRF, bembel refuses it (address-group.vrf-mismatch) unless the group sets cross_vrf: true. A cross-VRF group gives the finding address-group.cross-vrf-overlap when two members overlap, and its JSON entries carry "vrf".
  4. exclude removes addresses and prefixes.
  5. The result is sorted and without duplicates. With aggregate: true adjacent entries merge into larger CIDRs (default: off, because a firewall log should show the real addresses).
  6. SLAAC and other observed addresses are not members, unless observed: true.

The result for login-nodes before the example below: 10.20.4.101, 10.20.4.102, 2001:db8:4200:204::101, 2001:db8:4200:204::102 (hosts login-01 and login-02). The permission to see the members is address-group:read. A user who can read the group but not a prefix still sees the members (the group has an owner and its own scope).

Feeds

A feed is a group, rendered in one format and served at a stable URL. The firewalls and hosts pull it. bembel makes a new revision only when the content changes.

nftables

The admin declares the sets once in the ruleset. The feed file only replaces their content, in one transaction:

# ruleset (written by the firewall team, once)
table inet filter {
  set login_nodes_v4 { type ipv4_addr; flags interval; }
  set login_nodes_v6 { type ipv6_addr; flags interval; }
  chain input {
    type filter hook input priority filter; policy accept;
    ip saddr @login_nodes_v4 tcp dport 22 accept
    ip6 saddr @login_nodes_v6 tcp dport 22 accept
    tcp dport 22 drop
  }
}

# feed (login-nodes.nft, revision 42)
# bembel address-group login-nodes, revision 42, 2026-11-04T09:12:00Z
flush set inet filter login_nodes_v4
add element inet filter login_nodes_v4 { 10.20.4.101, 10.20.4.102 }
flush set inet filter login_nodes_v6
add element inet filter login_nodes_v6 { 2001:db8:4200:204::101, 2001:db8:4200:204::102 }

The chain must declare type filter hook input, or no packet traverses it. The feed file only flushes and fills the sets. The firewall team keeps its own management access path ahead of the drop rule. nft -c -f login-nodes.nft checks the file. nft -f login-nodes.nft applies it. The kernel applies a file as one transaction, so a rule never sees a half-empty set. The package bembel-feed (a small shell script and a systemd timer) does fetch, check and apply.

Palo Alto can use basic authentication or a client certificate for an EDL. FortiGate can use basic authentication for an external connector. OPNsense and pfSense URL tables are plain downloads (not verified). The path token exists for this last case.

Update flow and safety

A feed is never built while the user waits. A worker builds it after a change.

GuardDefaultWhat it does
Empty-list guardonA group that would become empty keeps the last non-empty revision. The new revision is held. limits.min sets a higher minimum. allow_empty: true turns the guard off for one group.
Maximum changemax(ceil(0.25 × n_last), 2), where n_last is the entry count of the last published revisionA revision is held when added + removed is larger than the limit. limits.max_change sets another limit for one group.
Size limitlimits.maxA list that is too large for the firewall is held, not cut.
Syntax checkonEach format is parsed again before it is stored (for example with the nft grammar of the tests). A failure holds the revision and raises an alert.
Family checkonNo IPv6 entry in an IPv4 feed.
Dry runalways availablebembel export address-group NAME --diff shows the change to the last revision before anything changes.

A held revision creates a change request. An approver (for example m.huber) reads the diff and approves or rejects. The four-eyes rule is the same as for other dangerous changes (Access control). An admin can undo a published revision with bembel feed revert NAME --to 41.

Why guards

A firewall list is a high-impact object. A bug in a filter, a wrong tag edit, or a failed sync can make a group empty. A deny rule with an empty source list could cut all admins off. A rule with an allow list that is too large could open a service. The change limit and the empty-list guard cost one approval in rare cases. They give the firewall team a clear promise: a feed changes slowly, or a user sees it.

The metrics help to see problems early: bembel_feed_revision, bembel_feed_entries, bembel_feed_held and bembel_feed_last_success_timestamp_seconds for each group (operations.html#metrics). The alerts BembelFeedStale and BembelFeedHeld fire when a build is overdue for 15 minutes or a revision is held for an hour. A consumer should alarm on a feed that did not change for longer than expected (header Last-Modified).

Example

On 2026-11-04 the network admin d.klein brings a new subnet and a new login node online. This is the route that the values take.

  1. d.klein sets announce=true with the tag announce=campus-bgp on the subnet kestrel-services (10.20.20.0/24, VLAN 220) in VRF global. These are routing values that only bembel holds, so d.klein can set them during the parallel run.
  2. The outbox event reaches the feed builder. The prefix list campus-bgp gets revision 58. The diff has one new line.
  3. The Nornir job of the network team pulls the export with its token, renders the FRR file of the border routers and shows the diff in the merge request.
  4. a.berger installs login-03 and adds it in ONA with the addresses 10.20.4.103 and 2001:db8:4200:204::103 and the tag role=login. The import at 17:52 brings the host into bembel. ONA is the writer of hosts until the cutover (migration.html#plan).
  5. The group login-nodes grows from 4 to 6 entries. The limit is max(ceil(0.25 × 4), 2) = 2, and the change is 2. No guard trips.
  6. The firewalls pull the new revision within their poll interval. The Palo Alto EDL has the new addresses after its next refresh.
$ bembel export prefix-list campus-bgp --format frr --family 4 --diff

+ ip prefix-list BEMBEL-CAMPUS-BGP-V4 seq 40 permit 10.20.20.0/24
1 entry added, 0 removed, 3 unchanged
