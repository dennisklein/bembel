Virtual machines

This chapter specifies how bembel handles virtual machines. OpenStack is one source of VMs. Many sites also run plain Debian hypervisors with libvirt. bembel has one VM model for both, and for any other platform. This chapter gives the libvirt path in detail: the agent, the prepare command, the hook and the lifecycle.

  • A VM is a host with kind=vm, a platform (libvirt, openstack, other) and a runs_on link to its hypervisor host.
  • On a Debian hypervisor, the Go daemon bembel-agent reads the libvirt domains over the read-only local socket. It reports them as observed VMs with source=libvirt:<hypervisor>.
  • bembel vm prepare claims the addresses, makes the DNS records and the DHCP reservation, and prints the MAC and a cloud-init NoCloud network config.
  • The libvirt hook /etc/libvirt/hooks/qemu confirms the claim on prepare. The agent does the rest. A bembel outage never stops a VM start.
  • The address lifecycle is: claimed, allocated, deprecated, released after a grace time (default 7 days). A live migration changes only runs_on.
  • OpenStack VMs use the same model. Only the source and the way of allocation differ.

One VM model

A VM is a host, like a server or a switch. It has interfaces with MACs, and the interfaces have addresses. Three fields set the VM apart.

kind
vm. The other kinds are physical, hypervisor, appliance and container-node.
platform
libvirt, openstack or other (for example VMware or Proxmox, made by hand or by Terraform).
runs_on
A link to the hypervisor host. The hypervisor is a host with kind=hypervisor. It can be a physical server with an asset link to its FNT device.

Two rules keep the model clean. They are the observed or managed rules (details below).

  • An observed VM is a fact that a source reported. The source owns it: the agent for libvirt:hv-03, the sync for openstack:os-prod. A user cannot edit its identity (name, UUID, MACs). A user can add tags and notes.
  • A managed VM is a plan that a user made before the VM exists (bembel vm prepare). The user owns the name, the address and the DNS name. The source only confirms the facts and sets runs_on and the state.

libvirt on Debian

The example hypervisors are hv-01 to hv-06.example.org. They run Debian with libvirt-daemon-system and KVM. Each hypervisor has VLAN bridges, for example br204 on VLAN 204 (subnet kestrel-compute) and br220 on VLAN 220 (subnet kestrel-services, 10.20.20.0/24 and 2001:db8:4200:220::/64). A domain connects to a bridge. This is the part of its XML that bembel reads:

<domain type='kvm'>
  <name>vm-build-07</name>
  <uuid>6f1d6a2e-8a1c-4c76-b0a5-3b1d2f9c7e10</uuid>
  <memory unit='GiB'>8</memory>
  <vcpu>4</vcpu>
  <devices>
    <interface type='bridge'>
      <mac address='52:54:00:5e:3a:b1'/>
      <source bridge='br220'/>
      <model type='virtio'/>
    </interface>
  </devices>
</domain>

An interface can also be type='network' (a libvirt network, with <source network='...'/>) or type='direct' (macvtap on a NIC). The agent reads the type, the MAC and the source name. It maps the bridge to a subnet in this order:

  1. The agent config has a table bridges (for example br220 to kestrel-services).
  2. If the table has no entry, bembel looks for a subnet with the VLAN id in the bridge name (br220 gives VLAN 220).
  3. If both fail, the interface has no subnet. The VM is shown with a warning.

An interface of type hostdev (SR-IOV virtual function) has a PCI address and a MAC. The agent reports it as a normal interface with the tag sriov=true. A passed-through InfiniBand function is reported with its port GUID if the domain XML shows it (not verified for all drivers).

bembel-agent

The agent is a small Go daemon in a Debian package. It runs on each hypervisor. It has three jobs: it reads the domains, it reports them and it answers the hook.

Package and service

The Debian package bembel-agent has the binary /usr/bin/bembel-agent, the unit file, the example config and the hook script. It depends on libvirt-daemon-system | libvirt-daemon. The post-install script makes the user bembel-agent and adds it to the group libvirt. This group may open the read-only socket.

# /lib/systemd/system/bembel-agent.service
[Unit]
Description=bembel agent (libvirt inventory)
After=libvirtd.service network-online.target
Wants=network-online.target

[Service]
Type=notify
User=bembel-agent
Group=libvirt
RuntimeDirectory=bembel-agent
ExecStart=/usr/bin/bembel-agent --config /etc/bembel/agent.yaml
Restart=on-failure
RestartSec=5
ProtectSystem=strict
ProtectHome=true
NoNewPrivileges=true
ReadWritePaths=/run/bembel-agent /var/lib/bembel-agent

[Install]
WantedBy=multi-user.target
# /etc/bembel/agent.yaml
server: https://ipam.example.org
hypervisor: hv-03.example.org        # the host name in bembel
source: libvirt:hv-03                # source name of every VM it reports
auth:
  method: oidc-client-credentials    # or: token (a personal token for small sites)
  token_url: https://id.example.org/realms/main/protocol/openid-connect/token
  client_id: svc-agent-hv-03
  client_secret_file: /etc/bembel/agent.secret
libvirt:
  uri: qemu:///system
  read_only: true
  report_every: 5m                   # full inventory; events go at once
  guest_agent: false                 # true: read guest IPs with qemu-guest-agent
bridges:
  br204: kestrel-compute
  br220: kestrel-services
hook:
  socket: /run/bembel-agent/hook.sock
  enforce: warn                      # off | warn | deny (see hook)
  timeout: 3s

A Go library without cgo reads the socket (candidate: digitalocean/go-libvirt). The agent stays one static binary.

What the agent reports

The agent subscribes to the libvirt lifecycle events (defined, undefined, started, stopped, migrated). It sends a full inventory on start and every report_every. It also sends each event at once. The report is idempotent: bembel replaces the set of VMs of this source.

{
  "source": "libvirt:hv-03",
  "hypervisor": "hv-03.example.org",
  "reported_at": "2026-11-04T09:31:07Z",
  "vms": [
    {
      "name": "vm-build-07",
      "uuid": "6f1d6a2e-8a1c-4c76-b0a5-3b1d2f9c7e10",
      "state": "running",
      "persistent": true,
      "interfaces": [
        { "mac": "52:54:00:5e:3a:b1", "type": "bridge", "source": "br220", "model": "virtio" }
      ]
    }
  ]
}
FieldUse in bembel
uuidThe identity of the VM host. It stays the same in a live migration (external_ref=libvirt:uuid:…).
nameThe domain name. It is the host name when the VM is new. A prepared VM keeps the name it has.
stateAttribute power_state (running, shut off, paused, crashed). It does not change the address status.
persistentA transient domain has no definition. It cannot come back after a stop.
interfaces[]Interface rows by MAC. The bridge selects the subnet.

The agent does not see the IP inside the guest. Three sources fill this gap. First, a prepared VM has its address from bembel. Second, with guest_agent: true the agent asks the QEMU guest agent for the guest interfaces (works only if the guest runs it). Third, the DHCP lease file of the DHCP servers shows the address that a MAC uses (DHCP chapter). An address that the agent or a lease shows in a managed subnet without a claim is a finding (vm.address-without-claim).

The agent has a service identity. In Keycloak this is a client svc-agent-hv-03 with client credentials. bembel gives it the custom role hypervisor-agent (permissions host:write, interface:write, address:confirm) in the scope of the site. A personal token is possible for a small site, but it must expire. The agent can only write VMs of its own source. bembel refuses a report for another source name.

Prepare a VM

bembel vm prepare does the planning work before the VM exists. The command (or POST /v1/vms:prepare) does these steps in one transaction:

  1. It makes the host vm-build-07.kestrel.example.org with kind=vm, platform=libvirt and the owner team.
  2. It generates a MAC (--mac auto) in the QEMU range 52:54:00, or it checks the MAC that the user gave. Duplicate MACs are refused.
  3. It claims one address for each family of the subnet. The claim has a TTL (default 24 h).
  4. It sets the FQDN on the addresses, so the A, AAAA and PTR records are derived.
  5. If the subnet has a DHCP scope, it makes the reservation (MAC to address).
  6. It renders the cloud-init network config and the meta-data.
$ bembel vm prepare --name vm-build-07 --subnet kestrel-services \
    --mac auto --hypervisor hv-03 --out ./vm-build-07
prepared vm-build-07.kestrel.example.org
  host     vm-build-07   kind vm · platform libvirt · owner hpc-ops
  runs_on  hv-03.example.org (planned)
  mac      52:54:00:5e:3a:b1   generated, unique
  claim    10.20.20.37/24              claimed, expires 2026-11-05T09:20:00Z
  claim    2001:db8:4200:220::37/64    claimed, expires 2026-11-05T09:20:00Z
  dns      A, AAAA, PTR   derived, in the next export (about 30 s)
  dhcp     reservation on dhcp-a, scope kestrel-services
wrote ./vm-build-07/network-config
wrote ./vm-build-07/meta-data
next:
  virt-install --name vm-build-07 --network bridge=br220,mac=52:54:00:5e:3a:b1 ...
  The claim is confirmed when the domain is created on hv-03.

Options of the command:

OptionDefaultMeaning
--namerequiredHost name (short). The FQDN uses the dnsZone of the subnet.
--subnetrequiredA subnet name, or a subnet pair for dual stack. A repeat of the option adds an interface.
--macautoauto or a MAC.
--hypervisornoneSets the planned runs_on. The agent sets the real one.
--configstaticstatic puts the address in the network config. dhcp leaves the guest to ask DHCP. The reservation exists in both cases.
--ttl24hLife of the claim.
--outstdoutDirectory for network-config and meta-data.

The command is idempotent for one name: a second call with the same arguments returns the same result. It needs the permissions prefix:allocate and host:write in the subnet.

cloud-init network config

The files use the NoCloud data source of cloud-init. The network config is version 2 (Netplan style). It matches the interface by MAC, so the name inside the guest does not matter.

# ./vm-build-07/network-config
version: 2
ethernets:
  eth0:
    match:
      macaddress: "52:54:00:5e:3a:b1"
    set-name: eth0
    addresses:
      - 10.20.20.37/24
      - 2001:db8:4200:220::37/64
    routes:
      - to: 0.0.0.0/0
        via: 10.20.20.1
      - to: "::/0"
        via: 2001:db8:4200:220::1
    nameservers:
      search: [kestrel.example.org, example.org]
      addresses: [10.0.0.53, 10.0.0.54]
# ./vm-build-07/meta-data
instance-id: 0193a8f2-7c11-7d2e-9b41-6c5d0f3a8e02    # the host id in bembel
local-hostname: vm-build-07

The gateway comes from the subnet. The resolvers and the search list come from the DHCP options of the scope (domain-name-servers, domain-search), so DHCP and static guests get the same values. With --config dhcp the file has only dhcp4: true and dhcp6: true for the matched interface.

The admin then builds the seed image and creates the domain:

cloud-localds -N vm-build-07/network-config \
  /var/lib/libvirt/images/vm-build-07-seed.iso user-data vm-build-07/meta-data

virt-install --connect qemu+ssh://root@hv-03.example.org/system \
  --name vm-build-07 --memory 8192 --vcpus 4 --import --osinfo debian13 \
  --disk path=/var/lib/libvirt/images/vm-build-07.qcow2 \
  --disk path=/var/lib/libvirt/images/vm-build-07-seed.iso,device=cdrom \
  --network bridge=br220,mac=52:54:00:5e:3a:b1,model=virtio \
  --noautoconsole

Check the options of your virt-install version. Newer versions can also take the files directly with --cloud-init.

The libvirt hook

libvirt calls the script /etc/libvirt/hooks/qemu for every QEMU domain. It passes four arguments: the guest name, the operation, a sub-operation and an extra argument. The domain XML is on standard input. The two events that bembel uses are:

CallWhenAction of the hook
qemu NAME prepare begin -Before the resources of the domain are set upSend the XML to the agent. The agent confirms the claim by MAC.
qemu NAME release end -After the domain stopped and the resources are freeTell the agent. If the domain is gone (transient, or undefined), the agent starts the grace time.
 
#!/bin/sh
# /etc/libvirt/hooks/qemu  (installed by: bembel-agent install-hook)
# libvirt calls: qemu GUEST OPERATION SUB-OPERATION EXTRA   (domain XML on stdin)
guest="$1"; op="$2"; sub="$3"
sock=/run/bembel-agent/hook.sock

call() {  # call PATH ; the XML on stdin goes to the agent
    curl -sS --max-time 4 --unix-socket "$sock" -o /dev/null -w '%{http_code}' \
         -X POST -H 'Content-Type: application/xml' --data-binary @- \
         "http://agent/hook/$1?name=$guest"
}

case "$op/$sub" in
  prepare/begin)
    code=$(call prepare) || code=000
    case "$code" in
      200) ;;                                    # claim confirmed, or not needed
      403) echo "bembel: no claim for $guest" >&2; exit 1 ;;   # enforce: deny
      *)   logger -t bembel-hook "prepare $guest: agent answered $code (ignored)" ;;
    esac ;;
  release/end)
    code=$(call release) || code=000
    [ "$code" = 200 ] || logger -t bembel-hook "release $guest: agent answered $code" ;;
esac
exit 0

The agent decides on the policy, not the script. For prepare it looks up the MACs of the domain. If it finds a claim for a MAC, it calls POST /v1/addresses/{id}:confirm and answers 200. If it finds no claim, the answer depends on hook.enforce:

enforceNo claim for the MACs
offAnswer 200. The agent only reports the VM later.
warn (default)Answer 200. The agent writes a finding vm.no-claim.
denyAnswer 403. The hook exits 1 and libvirt does not start the domain. The message says: run bembel vm prepare.

Why the hook fails open

The Neutron driver fails closed, because two systems must not give one address. A hypervisor is different. A VM that already has its address must start when bembel is down, for example after a power loss that also took the network. If the agent does not answer, the hook logs the problem and lets the domain start. The agent confirms the claim later, when it can reach bembel. The claim TTL of 24 h is long enough for this.

What the hook cannot see

libvirt has no hook for "define" or "undefine". The release event comes at every stop. A stopped but defined domain is not deleted. Therefore the hook only informs the agent, and the agent decides: it deprecates the address only when the domain is transient or when a libvirt undefined event comes. After the first install of the hook, restart libvirtd once. Running domains stay up. A site that already uses hooks puts the script in /etc/libvirt/hooks/qemu.d/10-bembel (libvirt 6.5 and later).

Lifecycle

The VM and its addresses have separate states. The address status follows the domain.

EventSeen byResult
vm preparebembelAddresses claimed, DNS and DHCP reservation made.
Domain with a claimed MAC is createdHook prepare or the agent reportClaim confirmed: allocated. runs_on is set to the reporting hypervisor.
Domain without a claim appearsAgentObserved VM (source=libvirt:hv-03). Finding vm.no-claim. If the MAC matches an existing reservation, bembel links them.
Domain stopsHook release, agent eventOnly power_state changes. The address stays allocated.
Domain is undefined, and no hypervisor reports the UUID within two report cycles (10 min)AgentAddresses deprecated with deprecated_at. DNS records and the reservation stay.
Grace time ends (vm.release_grace, default 7 d)ReaperAddresses released. Records and reservation removed. The host becomes deprecated, then it is deleted by the retention rule of the host kind.
A domain with the same MAC returns in the grace timeAgentAddresses allocated again. Same IP.
Live migration from hv-02 to hv-03Both agentsThe UUID is on hv-03. runs_on and source change. Nothing else.
bembel vm release vm-build-07 --nowUserSkips the grace time. Needs a confirmation.

Why a grace time

A defined domain disappears by mistake more often than an address is reused at once. A VM that an admin undefined by accident, and defined again an hour later, must get its old IP and its old DNS name. The grace time also keeps the DNS name from being taken at once. After 7 days the address is free for the next VM.

Live migration

The VM host is identified by the libvirt UUID, not by the hypervisor. During a live migration the UUID is on two hypervisors for a short time. After the migration the source agent sees the domain disappear (undefined or inactive). The target agent reports it. bembel does this:

  1. The target report names a UUID that belongs to a VM with another source. bembel moves the VM: runs_on is the target and source is libvirt:hv-03.
  2. The "undefined" event of the source comes later. bembel sees that the UUID lives on another hypervisor. It does not deprecate the addresses.
  3. If the source event comes first, bembel waits two report cycles (10 min) before it deprecates. The report of the target is in this time.

A user sees all three kinds in one list: the hosts with kind=vm. The filter platform=libvirt or runs_on=hv-03 selects a part. The page of a hypervisor lists its VMs, whatever the platform is.
