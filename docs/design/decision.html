Decision

The organisation uses OpenNetAdmin (ONA) for addresses, DNS and DHCP. ONA works, but its model and its interface stop the next steps: IPv6, VRFs, InfiniBand, self-service for teams and automation from OpenStack and Kubernetes. This chapter records the problems, the requirements, the options and the decision to build bembel.

  • ONA keeps its data integrity in PHP code. The database has no foreign keys, IPv6 is stored as a decimal number and permissions are global verbs without scope.
  • The requirements are API first, OIDC access control with scopes, IPv4 and IPv6 as equals, InfiniBand and RoCEv2 fabrics, BIND and ISC dhcpd exports, assets from FNT Command, and a safe migration from ONA.
  • Five options were scored: NetBox, Nautobot, phpIPAM, a commercial DDI suite and a new tool. NetBox is the strongest product, but its DNS and DHCP story, its access model and its migration path fit worse than a focused new tool.
  • The decision is a new tool, bembel: Go, PostgreSQL 18, SvelteKit, one binary, Apache-2.0.
  • The name comes from the Hessian stoneware jug that holds the apple wine and pours it out, as an IPAM holds addresses and gives them out.

ONA today

The organisation runs ONA 19.0.x on MariaDB. ONA holds about 41 000 hosts, 1 900 subnets and 62 000 DNS records. The network team edits data in the ONA web UI and with dcm.pl. Two plugins write the BIND zone files and dhcpd.conf each night. Shell scripts copy the files to the name servers and the DHCP servers.

Other systems hold parts of the same truth. FNT Command holds the racks, devices and cables. OpenStack Neutron allocates addresses in its provider networks without ONA. Kubernetes clusters take load balancer addresses from ranges in spreadsheets. The InfiniBand partitions are in a hand-edited partitions.conf on the subnet manager.

Security

Issue #210 reports an eval() on user input in the tag_add module, reachable before login, and an SQL injection in the search. The research confirmed the eval() in the cloned source. Until the migration ends, the ONA web server must be reachable only from the admin network.

Options

The research examined five options. Each option is described with what it gives and what it does not give for the requirements.

NetBox 4.7 (Apache-2.0)
The reference product for IPAM and DCIM. Rich model: VRF, prefix, IP range, IP address, VLAN groups, racks, devices, cables, VMs. REST and read-only GraphQL. Object permissions with ORM filter constraints. OIDC through python-social-auth. DNS and DHCP are not in core: plugins exist, netbox-plugin-dns for zones and records, and netbox-plugin-dhcp (beta, Kea-oriented, NetBox 4.7+) for DHCP. Each plugin is a separate project on its own release train. No plugin writes an ISC dhcpd export with failover. Its own DCIM overlaps with FNT Command. A migration from ONA needs a custom script.
Nautobot (Apache-2.0)
A NetBox fork with jobs, a GraphQL API and apps. It shares the model and the permission design of NetBox. It adds a larger platform to run (Celery, Redis) and a second plugin ecosystem.
phpIPAM (GPL-3.0)
A PHP IPAM with sections, subnets and a simple API. It has a light DNS (PowerDNS) link. It has no fabric model, a weak API and the same PHP risk class as ONA.
Commercial DDI (for example Infoblox, EfficientIP, BlueCat)
Complete DNS, DHCP and IPAM with appliances and support. High license cost per object or per appliance. It replaces BIND and ISC dhcpd, which the organisation does not want to replace now. InfiniBand is not in its model.
New tool (bembel)
A focused IPAM, DNS and DHCP source of truth with exports to the existing servers. It mirrors assets from FNT Command and does not repeat DCIM. Its model, access control and migration are designed for this organisation. Cost: the development and the maintenance by the team.

Choice

The organisation builds bembel. The decision has three reasons and one condition.

  1. The special parts are the daily work. InfiniBand partitions, RoCEv2 rails, BIND views and dhcpd failover are not edge cases here. In NetBox they are plugins or custom fields that the database does not check.
  2. FNT Command stays the DCIM. NetBox would be a second DCIM next to FNT Command, with two sources for racks and devices. bembel only mirrors the assets and links hosts to devices.
  3. The migration is the risk. A tool that knows the ONA model can import it, compare the exports byte by byte and switch over without a flag day (migration.html#parallel-run).

Condition: stay small

bembel is an IPAM, DNS and DHCP source of truth. It is not a DCIM, not a DNS server, not a DHCP server, not a firewall manager and not a config generator for routers. Each feature request outside this scope needs a decision record. The NetBox mapping (map-netbox.html) keeps a way open: if bembel fails, its data exports to NetBox.

The stack is decided in architecture.html#backend: Go instead of Rust, PostgreSQL 18, SvelteKit, mise. The requester proposed Rust. Go wins because the server, the CLI, the Kubernetes controllers, the Cluster API provider and the external-dns webhook share one language and one module, and because the other tools of the author (brig, sind, repoctl, radar) are Go.
