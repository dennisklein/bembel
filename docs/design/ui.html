Web UI

The web UI is a dense tool for users who work in it every day. It shows the state of the address space first and makes the common changes fast. This chapter gives the rules for all pages. The chapters Addressing pages, DNS and DHCP pages, Asset pages and Access and integration pages describe each page with its mockup.

  • One shell for all pages. A top bar holds the VRF switcher, the jump box, the change request chip, the assistant and the help. A sidebar has six groups.
  • Each page uses the public API only. Each action shows the CLI command that does the same.
  • Each page follows one template: screenshot, purpose, parts, states, URL, API and CLI. All screenshots show one story moment.
  • The UI shows what the user cannot do, and why. A disabled button tells the missing permission and the binding that would give it.
  • Colours have a meaning: one colour per domain, and fixed state colours. The UI never uses colour as the only signal.
  • Keys for all frequent actions. / opens the jump box, ? opens the help pane, Shift A opens the assistant, a opens the Allocate dialog. No single key allocates, deletes or approves.
  • Light and dark themes with the same tokens as the design record. Readable on a phone for on-call lookups.

Common parts of all pages

The page head holds the title, one line of facts, a CLI toggle, at most one assistant button and at most one filled button. A UI page chapter describes only the parts of its own page.

The pages are responsive with a container query on main. When the drawer is open, main is narrower. The tables then drop their least important columns first: source, then team and fabric, then kind and VLAN.

Colours and type

The UI and the design record follow the GSI design system. They share one set of tokens (docs/design/mockups/assets/bembel.css for the UI, docs/assets/site.css for the record), in light and in dark. Two rules apply:

  • The brand colours are decoration. The house orange #FABE5D marks the line under the top bar, the brand mark, the active sidebar item, square bullets and the primary button. The primary button has black text on orange (10.4:1). The house orange is never text on a light surface.
  • Everything that a user reads uses the AA-safe GSI web palette: text, links, icons, small badges, focus and form states. Each text or badge colour has at least 4.5:1 against the background it sits on: white, the surface, or its own -bg tint.

The utilisation meter is ok below 70 %, warn from 70 % to 90 % and failed above 90 %. The thresholds are the same on every page and are not settings.

Surfaces
White and neutral greys (#f6f6f6, #ededed, #dddddd hairlines). The dark theme uses the navy of the GSI master (#131519, #20242b, #292d35). The footer of the design record is the navy bar.
Type
Helvetica, then Arial. Headings are bold. Addresses, ids and code use a monospaced font (IBM Plex Mono in the UI, JetBrains Mono in the record), because GSI has no monospaced font.
Shape
Radii of 2, 4 and 6 px, 1 px hairlines, flat cards, no gradients. A page head uses the GSI pattern: eyebrow (the breadcrumbs), a short orange line, the heading.
Racks
The rack views use their own tokens (--rk-*) and the condensed Barlow font, in the style of rackplanner. The tape labels use the house orange. The team colours of the device faces come from the data.

Permissions in the UI

The UI asks the API what the user can do. The API returns, with each object, the list of allowed verbs for the current user (allowed_actions: ["read","update","allocate"], access.html#allowed-actions). The UI uses it as follows:

  • An allowed action is a normal button.
  • An action that needs a change request keeps its label (for example "Delete…") and shows the note "Needs a change request". It opens the form with a reason field, and the confirm button of the form is "Request approval". A second user with approver in scope approves (change requests).
  • A denied action is a disabled button (aria-disabled) with a "why not" text in its title. The text names the missing permission, the scope and the teams that can give it. A hidden button leaves the user to guess; the text tells the user whom to ask. Example: "Needs the permission record:create. Roles with it: dns-editor, network-admin, admin."
  • The UI never hides an object that the user can read. It hides actions only on objects that the user cannot change at all, to keep the page calm.

Mobile

The UI is for desks first. On call, a user needs fast lookups on a phone. Below 760 px the shell changes:

  • The sidebar becomes a menu button. The top bar keeps the brand, the jump box and the user menu.
  • Tables show the key columns only (IP, name, state). A row opens the object page.
  • The address map of a prefix becomes a list of ranges with counts.
  • Read pages work fully. Edit dialogs work, but bulk actions and the rack editor are desktop only.
  • The assistant, the help and a drawer open as full-screen sheets.

Pages with data-shot-mobile in the mockups also get a phone screenshot at 390 × 844 px.
