Kubernetes

This chapter specifies how Kubernetes clusters use bembel. A small manager, bembel-k8s, runs in the cluster. It has a few controllers. Each controller talks to the public bembel API with a service account token. bembel itself does not depend on any cluster.

  • One Helm chart installs bembel-k8s. Each controller is optional: the Cluster API IPAM provider, the load-balancer pool sync and the external-dns webhook.
  • The Cluster API provider is built on ipamutil. An IPAddressClaim in Kubernetes becomes an allocated address in bembel, with no bembel claim. The external_ref is cluster/namespace/name, not the UID, so clusterctl move adopts the old address.
  • A load-balancer pool is a whole range with the purpose lb-pool that bembel reserves inside a subnet. The controller renders it as a MetalLB or Cilium pool object. The load balancer then gives the single addresses.
  • bembel has no CNI IPAM plugin. A pod start must not need a remote call. bembel gives only node CIDRs and pool ranges.
  • The external-dns webhook writes records only into zones that bembel owns and that the service may write.
  • A pod proves its identity with a projected service account token with the audience bembel. bembel trusts the issuer of each cluster.
  • A Terraform and OpenTofu provider reaches everything that is not in Kubernetes.

Summary

Clusters need addresses in four places. Each place has a different owner and a different speed.

The manager lives in its own repository and chart. bembel itself needs no Kubernetes. The manager uses controller-runtime, the same language and tools as the server (Go). The chart sets the leader election lease, so two replicas are safe. The values file chooses the controllers:

Cluster API IPAM provider

Cluster API has a contract for IP address management (group ipam.cluster.x-k8s.io). An infrastructure provider that supports it creates an IPAddressClaim for each machine and pool. An IPAM provider answers with an IPAddress. CAPV (vSphere) does this today with addressesFromPools. Metal3 has its own IPAM and also reads the contract. Other providers vary and are not verified here.

The reference implementation is cluster-api-ipam-provider-in-cluster. Its package pkg/ipamutil does the generic work: it checks that the cluster is not paused, sets the finalizers and sets the owner references. The provider implements two small interfaces:

type ProviderAdapter interface {
    SetupWithManager(ctx context.Context, b *ctrl.Builder) error
    ClaimHandlerFor(c client.Client, claim *ipamv1.IPAddressClaim) ClaimHandler
}
type ClaimHandler interface {
    FetchPool(ctx context.Context) (client.Object, *ctrl.Result, error)
    EnsureAddress(ctx context.Context, address *ipamv1.IPAddress) (*ctrl.Result, error)
    ReleaseAddress(ctx context.Context) (*ctrl.Result, error)
}

The pool object

The pool is a CRD of bembel. BembelPrefixPool points at a subnet in bembel. It does not copy the subnet. It only says which subnet, which range and which defaults.

apiVersion: bembel.example.org/v1alpha1   # placeholder group, see open questions
kind: BembelPrefixPool
metadata:
  name: kestrel-k8s-v4
  namespace: capi-kestrel
  labels:
    cluster.x-k8s.io/cluster-name: kestrel-k8s     # needed by clusterctl move
spec:
  prefix:
    vrf: global
    cidr: 10.20.64.0/22                            # subnet kestrel-k8s, VLAN 264
  range: kestrel-k8s-nodes                         # a static range in the subnet, 10.20.64.20-10.20.64.250
  gateway: 10.20.64.1                              # default: the subnet gateway
  dnsZone: kestrel.example.org                     # name the address from the Machine
  tags: { cluster: kestrel-k8s, role: k8s-node }
  releaseGrace: 1h                                 # Go duration; the provider sends "grace": "PT1H"
status:
  conditions:
    - type: Ready
      status: "True"
      reason: PrefixFound
  free: 998

A claim for an IPv6 address uses a second pool of the same kind, with cidr: 2001:db8:4200:264::/64. The contract is single stack, so a machine with two stacks has two claims.

Claim to address

The provider watches each IPAddressClaim whose poolRef has kind BembelPrefixPool. For each claim it does these steps:

  1. ipamutil checks that the cluster of the claim exists and is not paused. Then it adds the finalizer ipam.cluster.x-k8s.io/ReleaseAddress.
  2. FetchPool reads the pool. When the subnet is missing, it sets the condition PoolNotReady and tries again later.
  3. EnsureAddress calls POST /v1/prefixes/{id}/addresses:allocate with the header Idempotency-Key: k8s:kestrel-mgmt:5f4e0c0a-2c1d-4b3c-9d44-0a55f3c1e0b7 (cluster id and claim UID) and the body below. The body has no claim_ttl, so bembel allocates the address at once. Cluster API makes no bembel claim.
  4. bembel answers with the address: 201 for a new one, 200 for an address that it adopts by external_ref. ipamutil creates the IPAddress with the same name as the claim, sets the owner references and the protection finalizer ipam.cluster.x-k8s.io/ProtectAddress, and writes claim.status.addressRef.
{
  "range": "kestrel-k8s-nodes",
  "fqdn": "kestrel-k8s-cp-0.kestrel.example.org",
  "external_ref": "k8s:kestrel-mgmt:ipaddressclaim/capi-kestrel/kestrel-k8s-cp-0-eth0",
  "tags": { "cluster": "kestrel-k8s", "role": "k8s-node" },
  "attributes": { "claim_uid": "5f4e0c0a-2c1d-4b3c-9d44-0a55f3c1e0b7" }
}

The external_ref is the cluster id, the namespace and the name of the claim. It is not the UID. A claim keeps its name when clusterctl move recreates it in another cluster. The UID changes. An external_ref with the UID would give a second address. The Idempotency-Key has the UID, so it covers only the retries of one claim object. bembel finds the address of a recreated claim by its external_ref (adoption).

The hostname comes from the Machine. The provider walks the owner references of the claim up to the Machine (at most 5 steps) and builds the FQDN from the machine name and the dnsZone of the pool. This is the same method as the Infoblox provider. The address gets its A and PTR records (DNS chapter).

clusterctl move copies the objects with the label cluster.x-k8s.io/cluster-name to a new management cluster. The pool has this label (see the example). In the new cluster the claim has a new UID and no IPAddress. The provider calls allocate. The external_ref is the same, so bembel returns the old address with 200. The provider PATCHes the new UID into claim_uid. The address does not change.

The clusterId is a value in the Helm values, not a host name. After a move, the new management cluster gets the same clusterId, so the external refs stay the same. The trusted-issuer entry of the new management cluster keeps the subject prefix k8s:kestrel-mgmt: (below); the operator replaces its issuer URL or key set during the move. The subject and the source stay the same.

Lifecycle of a claim

Load-balancer pools

MetalLB and Cilium allocate the addresses of Services of type LoadBalancer from a pool. They do this locally and report nothing back. bembel does not allocate each Service address. A per-Service call is the wrong layer for a load balancer that already gives addresses. bembel reserves the whole range for the pool, so that nobody uses an address of the range elsewhere.

The controller pool-sync handles the CRD BembelLoadBalancerPool:

apiVersion: bembel.example.org/v1alpha1
kind: BembelLoadBalancerPool
metadata:
  name: kestrel-lb
  namespace: metallb-system
spec:
  type: metallb                      # metallb | cilium
  allocate:                          # one lb-pool range per entry
    - { prefix: { vrf: global, cidr: 10.20.64.0/22 },            size: 64,    hint: 10.20.66.0 }
    - { prefix: { vrf: global, cidr: "2001:db8:4200:264::/64" }, size: 65536, hint: "2001:db8:4200:264:ffff::" }
  tags: { cluster: kestrel-k8s, role: lb-pool }
  serviceSelector:
    matchLabels: { pool: kestrel-lb }
status:
  ranges: ["10.20.66.0-10.20.66.63", "2001:db8:4200:264:ffff::-2001:db8:4200:264:ffff::ffff"]
  rendered: IPAddressPool/metallb-system/kestrel-lb

The controller does these steps:

  1. It calls POST /v1/prefixes/{id}/ranges:allocate for each entry, with size, purpose: lb-pool, name, hint and the tags of the spec. The key and the external_ref are k8s:kestrel-mgmt:lbpool/metallb-system/kestrel-lb/v4 and …/v6. bembel makes the lb-pool range 10.20.66.0–10.20.66.63 (name kestrel-lb-v4) in the subnet kestrel-k8s, and the range kestrel-lb-v6 in 2001:db8:4200:264::/64. The allocator skips lb-pool ranges, so no node address lands in them.
  2. It renders the native pool object and applies it with the label app.kubernetes.io/managed-by: bembel-k8s.
  3. It watches the native object. If somebody edits it by hand, the controller overwrites the change and writes an event. It also raises a metric.
# rendered for type: metallb
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: kestrel-lb
  namespace: metallb-system
  labels: { app.kubernetes.io/managed-by: bembel-k8s }
spec:
  addresses: [10.20.66.0/26, "2001:db8:4200:264:ffff::/112"]
  autoAssign: true
  serviceAllocation:
    serviceSelectors:
      - matchLabels: { pool: kestrel-lb }
---
# rendered for type: cilium
apiVersion: cilium.io/v2
kind: CiliumLoadBalancerIPPool
metadata: { name: kestrel-lb }
spec:
  blocks:
    - { cidr: 10.20.66.0/26 }
    - { cidr: "2001:db8:4200:264:ffff::/112" }
  serviceSelector:
    matchLabels: { pool: kestrel-lb }

MetalLB also needs an L2Advertisement or a BGPAdvertisement. The controller does not create it. That object belongs to the network (and to the BGP values in Routing and firewall). The pool can have the tag announce=campus-bgp, so the prefix list of the campus router includes the range.

Why a range and not each Service

A Service address is created and deleted at the speed of a deployment. MetalLB and Cilium already track them with no external call. If bembel were in that path, a bembel outage would block a Service. A reserved range is a coarse, rare allocation. Optional: the controller can mirror the Service addresses as read-only observed addresses (source=k8s:kestrel-mgmt). They do not count for the pool.

external-dns webhook

external-dns creates DNS records for Services and Ingresses. For a provider that is not in its source tree it has a webhook protocol. bembel ships a small sidecar, bembel-k8s external-dns, that implements it. The sidecar runs in the pod of external-dns and listens on localhost:8888.

Method and pathPurposeSuccessbembel call
GET /Negotiation. Returns the domain filter.200GET /v1/zones?writable=true: the zones that the service may write.
GET /recordsReturns all endpoints.200GET /v1/records?zone=…&managed_by=external-dns:kestrel-k8s, with paging.
POST /recordsApplyChanges: Create, UpdateOld, UpdateNew, Delete.204POST /v1/records:batch, one transaction, with If-Match on each revision.
POST /adjustendpointsProvider rules for the endpoints.200None. The sidecar sets the TTL minimum of the zone and drops record types that the zone does not take.
  • The media type is application/external.dns.webhook+json;version=1, in Accept and in Content-Type.
  • external-dns retries only on a 5xx answer. The sidecar answers 5xx for a bembel outage and 4xx for a permanent error, for example a zone it may not write.
  • The sidecar writes complete response bodies. The limit of a response is 32 MiB (--webhook-provider-max-body-size).

The TXT records of the external-dns ownership registry are normal records. The sidecar stores them as manual TXT records with the same source. The annotation namespace for per-record options is external-dns.kubernetes.io/webhook-bembel-.

Rule

  • The webhook writes only into zones that bembel owns. A zone is writable when the service has the role dns-editor with the scope zone=k8s.example.org. The domain filter shows exactly these zones.
  • A record with managed_by=external-dns:… is read-only for users. They see it in the UI with its source.
  • A name that has a derived record (an address with this FQDN) is refused with 409. The names of hosts stay under the control of the address.
  • Several clusters can write into one zone only with different managed_by values and different TXT owner ids. Each cluster sees only its own records.

This is the same split as for OpenStack: one writer for each zone (Designate). The zone k8s.example.org is a delegated sub-zone of example.org. bembel exports it with the other zones (DNS chapter). The record reaches the name servers on the next build, so the time to a visible name is the build interval of the export (default 30 s). If the site wants a faster name, it keeps a small DNS server for the cluster (for example CoreDNS or PowerDNS) and does not use the webhook.

CNI

A CNI plugin gets a call for each pod start (ADD). The call is in the critical path, runs for seconds at most, must work when the control plane is down and scales with pod churn. A plugin that calls a remote IPAM breaks all three needs. It also creates a start-up cycle: the IPAM runs on the cluster network that it must configure. All usual CNIs allocate in two levels. The control plane gives each node a block. The node gives pod addresses from the block, with no network call.

bembel follows the same split and works only on the first level:

CNIObject that pool-sync rendersWhat bembel gives
Cilium (cluster-pool, multi-pool)CiliumPodIPPool or the operator value clusterPoolIPv4PodCIDRListA pod CIDR for the cluster. The operator splits it per node.
CalicoIPPool (the blockSize stays a Calico setting)A CIDR per cluster.
host-local, kubelet node CIDRThe field spec.podCIDR through the cluster configA CIDR per cluster, checked against overlaps.
Whereabouts (Multus)IPPool range or the range in a NetworkAttachmentDefinitionA range per attachment network. Whereabouts keeps the per-pod part.

Pod and service ranges that are not routed outside the cluster live in one VRF for each cluster, for example k8s-kestrel. This lets two clusters use the same CIDR without a finding. A routed pod range (BGP mode) lives in the VRF global or hpc-fabric. It carries the tag announce=campus-bgp.

Per-pod addresses are not in bembel. A later option is a read-only reflection, asynchronous and never authoritative. The ranges for a cluster that uses InfiniBand follow the fabric rules (Core model): a pod range on kestrel-ib is a subnet with the fabric infiniband.

Identity

A workload proves who it is with a projected service account token. The pod spec asks for a token with the audience bembel and a short life. The kubelet rotates it. The token is a JWT, signed by the API server of the cluster.

# in the Deployment of bembel-k8s
volumes:
  - name: bembel-token
    projected:
      sources:
        - serviceAccountToken:
            audience: bembel
            expirationSeconds: 3600
            path: token
containers:
  - name: manager
    volumeMounts: [{ name: bembel-token, mountPath: /var/run/secrets/bembel }]

Trusted issuer per cluster

bembel validates the token itself. No exchange step is needed. A trusted issuer is an entry in the bembel config or in the table of issuers (Access control):

# /etc/bembel/bembel.yaml, under auth.issuers (excerpt)
    - name: k8s-kestrel-mgmt
      issuer: https://k8s-mgmt.example.org     # the client cluster's --service-account-issuer
      audiences: [bembel]
      jwks: discovery                          # or {file: /etc/bembel/jwks/kestrel-mgmt.json} when air-gapped
      kind: service
      claims: {subject: sub}
      strip_prefix: "system:serviceaccount:"
      subject_prefix: "k8s:kestrel-mgmt:"
      max_token_age: 1h
  • bembel checks the signature, iss, aud and exp. The audience is mandatory. The default API audience is rejected.
  • bembel caches the key set and refreshes it on an unknown kid, at most once a minute.
  • An air-gapped cluster uploads its key set (jwks: {file: …}). Then bembel needs no network access to the cluster.
  • The same service account name in two clusters gives two different subjects, because the cluster id is part of the name.
  • bembel config check rejects two issuers with the same issuer URL.

Subject and binding

The subject name is k8s:<cluster id>:<namespace>:<service account>. The token claim sub is system:serviceaccount:bembel-system:bembel-k8s, so the subject is k8s:kestrel-mgmt:bembel-system:bembel-k8s. A binding gives it rights (Access control):

bindings:
  - subject: k8s:kestrel-mgmt:bembel-system:bembel-k8s
    role: k8s-integration                              # custom: allocator + range:delete
    scope: { prefix: 10.20.64.0/22, vrf: global }     # AND of two terms
  - subject: k8s:kestrel-mgmt:bembel-system:bembel-k8s
    role: k8s-integration
    scope: { prefix: "2001:db8:4200:264::/64", vrf: global }
  - subject: k8s:kestrel-mgmt:bembel-system:bembel-k8s
    role: k8s-integration
    scope: { vrf: k8s-kestrel }                       # pod and service ranges of the cluster
  - subject: k8s:kestrel-mgmt:bembel-system:bembel-k8s
    role: dns-editor
    scope: { zone: k8s.example.org }
  - subject: k8s:kestrel-mgmt:bembel-system:bembel-k8s
    role: viewer
    scope: { global: true }

The custom role k8s-integration is allocator plus range:delete (Access control). The manager can allocate addresses and lb-pool ranges only in the subnets of kestrel-k8s (10.20.64.0/22, 2001:db8:4200:264::/64) and prefixes in the VRF k8s-kestrel, write records only in k8s.example.org and read the rest. The cluster prod-1 is a separate subject: its own CAPI provider is k8s:prod-1:capi-system:capi-ipam, with an allocator binding on 10.30.12.0/24 (Access control). A pattern such as k8s:kestrel-mgmt:capi-system:* is a group of subjects, if a site wants one binding for many service accounts. The audit event stores the cluster id, the namespace, the service account and, for a CAPI call, the external_ref of the claim.

Why direct trust, not token exchange

Direct trust needs no client secret and no extra hop. The check works offline with a cached key set. It is also needed for CI systems such as GitHub Actions. RFC 8693 token exchange through Keycloak is possible later (phase 3), when a site wants one central policy and one place to revoke.

Terraform and OpenTofu

A provider for Terraform and OpenTofu reaches consumers that are not in Kubernetes: virtual machines, network gear, cloud accounts. The skeleton is generated from the OpenAPI document and written with the terraform-plugin-framework. The most important resource is the allocation of the next free address with a stable identity.

terraform {
  required_providers {
    bembel = { source = "dennisklein/bembel" }
  }
}

provider "bembel" {
  url = "https://bembel.example.org"
  # token from BEMBEL_TOKEN, or an OIDC token from the CI job:
  # oidc_token_file = "/var/run/secrets/ci/token"
}

data "bembel_prefix" "services" {
  vrf  = "global"
  name = "kestrel-services"
}

resource "bembel_address_allocation" "build07" {
  prefix_id = data.bembel_prefix.services.id
  key       = "vm-build-07"             # idempotency key, stable
  fqdn      = "vm-build-07.kestrel.example.org"
  mac       = "52:54:00:5e:3a:b1"
  tags      = { role = "build" }
}

resource "bembel_record" "build_alias" {
  zone  = "kestrel.example.org"
  name  = "ci-build"
  type  = "CNAME"
  ttl   = 300
  value = "${bembel_address_allocation.build07.fqdn}."
}

output "build07_ip" {
  value = bembel_address_allocation.build07.address
}

Crossplane can use the provider without more work from bembel, through Upjet generation, or it can use provider-http against the REST API. A native Crossplane provider is a later, optional step. The Terraform provider is its base.
